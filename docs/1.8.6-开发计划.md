# 1.8.6 开发计划：第一次给「零后端」装上服务端

> 前提：v1.8.5 已于 2026-11-26 提审（见 `docs/提审记录.md`），**本计划不动 1.8.5 已提交的任何免费行为**。
> 这份文档只回答三件事：1.8.6 做到哪、按什么顺序做、哪几件必须先由你拍板。
>
> 三态标注贯穿全文：**已核实**＝有官方文档/代码/截图依据；**推断**＝我的判断，无出处；**待确认**＝缺信息，需现场查或你决定。

## 零、一句话结论

1.8.6 **不是"加个支付按钮"**，而是这个产品第一次拥有服务端。
所以范围必须收窄成一条链路：**一个买断道具 → 一次支付 → 一个订单页**。
真正值钱的付费内容（成册导出、模板扩展包）放到 1.8.7，理由见第三节。

## 二、三个硬冲突（不解决就写不了代码）

### 2.1 文案说「无服务端、不上传、不联网」，而支付必须有服务端

现在对外的原话（`miniprogram/utils/i18n.js`）：

| 位置 | 原文 |
|---|---|
| `me:about_privacy`（:325） | 所有记录只保存在这台手机上，**不上传、不联网、不需要登录** |
| `guide:s2_b`（:381） | 只存在这台手机上。**不上传**、不同步、不用登录，也就没有服务器会看见你写了什么 |
| `guide:a2`（:390） | 不做云同步，这是刻意的……**不上传**就没有泄露的可能 |
| `index:empty_identity`（:469） | 只存在这台手机，**不上传**，也不用登录 |

接支付后，"没有服务器"这句会变成假话——这是**审核和口碑的双重风险**，不是措辞问题。

**建议口径（需你确认）**：把"没有服务器"降级为"你的记录没有服务器"。
记录、录音、照片的链路一行代码都不加网络请求；只有**你主动点购买**时才会联网，联网内容仅订单号与 openid，不含任何记录内容。

改法：四条文案统一为「记录不上传；只有买断时会联网确认订单」这类句式，并在 `layout.test.js` 已有断言（不许「不联网」/必须「不上传」）基础上**再加一条**：全量 i18n 里不允许出现「无服务端」这类绝对句。

> 这条不是文案洁癖。`tools/layout.test.js` 已经因为上一轮写错「不联网」被加过断言，同一个坑不踩第三次。

### 2.2 `docs/商业化预留.md` 里有一条结论已失效

`:144` 原文：「**不做永久买断**，否则后面的服务器成本没人付。」
你已决定做买断，这条必须改，否则后面每次读这份文档都会打架。

改法（本次一并改掉）：不是删原则，而是补上区分——
**订阅**用于"有持续成本的能力"（云同步、AI、转写）；**买断**只用于"零边际成本的本地能力"（成册导出、模板包），且买断范围写明"含上线时全部本地能力 + 此后 12 个月新增本地能力"。

同时 `:14`「计费点只挂在外部队列」这一条也要补一句例外：本地能力可以买断，但**不许按次/按条计费**，也不许把已免费的能力挪进付费墙。

### 2.3 `edition.js` 那套设计是订阅骨架，买断要改

`商业化预留.md` 第三节的 `entitlement` 模型是 `edition + expiresAt + quotas`（档位+到期+额度）。买断用户**没有到期时间**，硬套会出现"永久权益 3 天后过期"。

改法：
- 新增 `license` 概念，与 `entitlement` 并列：`{ productId, boughtAt, scope, schema }`，`expiresAt` 恒为 `0` 表示永久。
- `can(featureId)` 判定顺序：`license` 命中 → 放行；否则看 `entitlement`；都没有 → 按 `FEATURES.min`。
- 权益来源改成"服务端查库"而非"签名凭证下发"——因为买断是一次性事件，查一次缓存即可，比每次校验签名简单，且不需要防"改包解锁"以外的攻击面（客户端本来就不是安全边界，见 `商业化预留.md` 第七节）。

## 三、范围切分：为什么不能一版全做

| 版本 | 主题 | 内容 | 上线前提 |
|---|---|---|---|
| **1.8.6** | 支付基建 | 服务端（云函数）+ 一个买断道具 + 支付调起 + 发货入账 + 订单中心页 + 恢复购买 | 道具审核通过、订单中心 path 已填 |
| **1.8.7** | 付费内容 | 成册导出（买断主体功能）、模板扩展包 | 1.8.6 支付链路在线上跑通 |

不合并的三条理由：

1. **审核耦合**：订单中心 path 是硬门槛，页面不存在就填不了，填不了就过不了审。必须先有页面。
2. **故障隔离**：支付链路第一次上线，出问题只影响"买不了"，不影响记录。若同版塞进成册导出，出问题会同时坏掉"能买"和"买了用不了"，排查面翻倍。
3. **`商业化预留.md` 第八节第 6 条**：不要一次上三个付费点，归因不了。一个道具先跑 4 周。

> 代价：1.8.6 对用户是"看不见的版本"（只有入口没有内容）。所以 1.8.6 的商店版本描述要老实写"新增订单与购买入口，付费功能下版开放"，不要空写"优化体验"。

### T0 决策与核实（不动代码，1～2 天）

| 编号 | 任务 | 产出 | 依赖 |

| T0-1 | 进后台「虚拟支付」模块截图核实：是否有「道具管理」、是否已拿到 `offerId`、`AppKey` 是否可见、主体类型显示什么 | 一段结论 + 截图，写回本文档第一节第 6/7 条 | 无 |
| T0-2 | 确认服务端形态：微信云开发 vs 自建（见下） | 一句话决定 | T0-1 |
| T0-3 | 确认买断定价与文案边界 | 价格数字 + 一句"买断含什么" | 无 |
| T0-4 | 确认 2.1 的文案新口径 | 四条 i18n 新句 | 无 |

**T0-2 两个选项（推断，无实测）**

| 方案 | 优点 | 代价 |
|---|---|---|
| 微信云开发（云函数 + 云数据库） | 免服务器运维、免 HTTPS 域名备案、`code2Session` 在云函数里一行搞定 | 需开通云开发（有免费额度，超出按量）；项目从"纯本地"变成"有云环境" |
| 自建（一台轻量服务器 + 域名 + 证书） | 完全可控，不绑平台 | 备案、证书续期、运维全自己扛，个人主体成本不划算 |

**建议云开发**，理由是这台产品的服务端只需要三个函数（换 session_key、查订单、发货入账），没有理由为此养一台机器。

### T1 服务端（3～4 天）

| 编号 | 任务 | 关键点 |
|---|---|---|
| T1-1 | 云函数 `auth`：`code2Session` 换 `openid` + `session_key` | `session_key` 只在服务端内存里活着，用于算 `signature`，**不下发** |
| T1-2 | 云函数 `order`：生成 `outTradeNo`、算 `signData/paySig/signature` 返回前端 | 订单先落库为"未支付"；`outTradeNo` 8–32 字符，只用数字字母 |
| T1-3 | 云函数 `notify`：接收发货推送，幂等写 `entitlements` | 幂等键用 `outTradeNo`；重复推送不重复发货 |
| T1-4 | 云函数 `query`：主动查单兜底 + 按 `openid` 查已购 | 前端"恢复购买"就走这个，不依赖本地缓存 |
| T1-5 | 数据库两张表：`orders`、`entitlements` | 权限设"仅创建者可读"，不要开放全表 |

**T1 的验收不是"代码写完了"，是这三个能跑通**（沙箱 `env: 1` 先跑，正式 `env: 0` 后跑）：
① 下单返回三件套 → ② 支付成功收到推送 → ③ 关掉小程序重进，`query` 仍能查到权益。

> 注意：官方文档写明**现网版本 `env` 只能是 0**（错误码 `-15011`）。沙箱只在开发期用，别把 `env: 1` 带上线。

## 五、技术验证 Gate：成册导出走哪条路（1.8.7 的前置）

这一项**不影响 1.8.6 上线**，但决定 1.8.7 卖什么、能不能卖。建议在 1.8.6 开发期间并行做，因为它是"付费内容有没有货"的唯一变量。

| 路线 | 做法 | 已知风险 | 判定标准 |
|---|---|---|---|
| A. 客户端生成 PDF | 纯 JS 库拼 PDF 字节流，`fileSystemManager.writeFile` 落盘，`openDocument` 预览 | 小程序无 DOM、无 `Buffer`；**中文字体是死结**——完整中文字体 5–10MB，远超主包 2MB 限制，构建期子集化后仍可能 1–2MB（**推断**，未实测） | 生成一份 10 条记录的 PDF，包体增量 ≤ 800KB，真机 `openDocument` 能打开 |
| B. 客户端生成图片册 | 复用 `utils/poster.js` 现有绘制能力，加目录页、按时间/标签筛选、批量存相册 | `poster.js` 已有"单边 ≤7000 设备像素"限制（`:448`），40+ 条拼一张会爆；只能多张输出 | 40 条记录批量导出 ≤ 40 次保存，无卡死、无 OOM |
| C. 服务端生成 PDF | 云函数用 pdfkit + 中文字体 | 有边际成本（每次调用），与"买断＝零边际成本"矛盾 | 单次成本可忽略才成立，否则不能卖买断 |

**推荐：先做 B**。理由：`poster.js` 已经把版式、品牌位、小程序码都画好了，B 是"把单张变多张 + 加目录"，包体几乎不增，风险最低；A 作为 1.8.7 增强（PDF 更符合"成册"的直觉）；C 只在 A、B 都失败时才考虑，且要改成订阅而不是买断。

> 注意 `transfer.js` 已有 `deliverFile`，多张图片的交付方式（存相册 vs `shareFileMessage`）要在这里实测，不要假设。

## 六、验收标准（1.8.6 算完成的定义）

## 九、要你拍板的四件事
