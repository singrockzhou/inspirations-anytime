# 「从聊天存」多图合并为一条记录 · 设计方案分析

> 前置事实（已核对代码，非假设）：
> - 记录模型已支持多图：`type:'photo'` + `mediaPaths: string[]`，上限 `MAX_PHOTOS = 9`
> - 照片记录的 `content` 是配文，≤200 字；`tags` 由正文 `#标签` 自动解析
> - 无 `title` 字段（产品哲学：不强制命名）；无 `source` 字段
> - 文件来自聊天时用 `wx.chooseMessageFile`，**只能拿到文件本身，拿不到发送人、群名、消息时间**
> - 已有 `sniff.js` 专门处理 `chooseMessageFile` 返回路径无扩展名的问题
> - 已有 `poster.js` 多图错落成图（v1.8.3），`flashId` 新卡高亮、`store.js` 先落库后返回

---

## 一、用户动机：为什么"多张"必须合成"一条"

用户点开选择器一次勾 6 张图，这个动作本身就是一句声明：**"这 6 张是同一件事。"**

拆开存会产生三类真实损失：

1. **语境丢失**。这批图共享的语境是"谁在什么时候、为什么发给我"。存成 6 条孤立的照片记录后，这个语境彻底消失——一周后看到第 4 张，想不起来它是"主卧参考"还是"上次那个方案"。
2. **列表被淹没**。首页是按日分组的卡片流。9 张图 = 9 张卡，当天其他记录全被挤下去。而产品语义是"一条记录 = 一个念头"，一次选 9 张本来就只是**一个念头**。
3. **能力丧失**。零散 9 条做不出长图，一条 9 张可以一键成图分享。合并是后续复用的前提。

补充一个容易被忽略的动机：**"从聊天存"实际常被当作跨设备导入通道**——用户在电脑微信里把图片发到「文件传输助手」，再用手机从小程序里选进来。这条路径的存在意味着入口不能藏太深。

## 二、典型场景

| 场景 | 一次选几张 | 共享语境是什么 |
|---|---|---|
| 装修／软装参考 | 4–9 | 设计师在某次对话里发的一组参考图 |
| 客户需求 | 2–6 | 客户发来的手绘草图 + 参考截图，同一需求 |
| 采购比价 | 3–6 | 群里同一批商品的不同角度／不同供应商 |
| 旅行备忘 | 5–9 | 朋友发来的景点、行程单、民宿实拍 |
| 素材收集 | 2–4 | 同一主题的配色／排版参考 |
| 跨设备流转 | 1–9 | 自己从电脑发到手机的成组文件 |

共性：**张数多、来自同一次对话、需要一句话说明才能被未来的自己看懂。**

## 三、图片与记录的组织关系（核心决策）

### 决策 1：默认「一次选择 = 一条记录」，不做保存前确认

不在选完图后弹"是合并还是拆开"。理由：本项目所有保存路径都是"先落库、再返回、不弹成功提示"，加一个确认页等于给最快的路径加 friction，而绝大多数情况默认值就是对的。

替代方案：**保存后 24 小时内可在卡片菜单里「拆开存」**。默认合并 + 事后可拆，比事前必选更省心。

### 决策 2：顺序 = 选择器返回顺序，第一张即封面

不按时间重排、不按文件名排。用户在选择器里看到的顺序就是他心里的顺序。允许长按某张「设为封面」（改的是 `mediaPaths` 顺序，不改结构）。

### 决策 3：超过 9 张 → 明确告知，绝不静默截断

- 选择器 `count` 直接按剩余额度给（已选 9 张时给出提示而不是打开选择器）
- 若返回多于额度：提示「已选 12 张，单条最多 9 张，保留前 9 张」，并对未保留的临时文件立即 `removeAll`，不留垃圾

**是否放开到 20 张？** 建议先保持 9。原因：列表缩略是九宫格，10 张以上要重设计"第 9 格显示 +N"；同时 9 张 × 压缩后约 200–400KB 已接近用户"一条记录"的心理容量。真要做，单独排期，别和本功能一起上。

### 决策 4：一条记录只允许一种形态（硬约束）

不要把"聊天里的图片 + 对方的一段文字消息"拼成一条"混合记录"。`type` 三选一是数据模型、备份格式、卡片组件、编辑页共用同一套假设的基础，混合会连锁破坏 4 处以上。

## 四、元数据：记什么、不记什么

| 元数据 | 建议 | 理由 |
|---|---|---|
| **标题** | **不新增**。正文第一行天然承担标题功能（编辑页视觉加重即可，不改数据结构） | 强制标题 = 把 friction 加回来，违反"3 秒开记" |
| **无正文时的卡片标题** | 用「N 张图」+ 相对时间做占位（纯展示，不入库） | 不用编造标题，也不用空白卡片 |
| **描述（content）** | 保留 ≤200 字配文。保存后在卡片上给一个极轻的「补个说明」入口 | 直接决定能不能被搜到，见第六节 |
| **标签（tags）** | 沿用 `#` 解析。多图记录**尤其依赖标签**——6 张装修图靠 `#装修 #主卧` 才能和 6 张厨房图区分 | 现有能力，零成本 |
| **来源（source）** | **新增内部字段** `{kind:'chat', at, count}`，不展示成角标 | 支撑后续功能：删除时提示"仅删本地副本"、统计导入通道占比、判重 |
| **发送人／群名／消息时间** | **绝对不记** | `chooseMessageFile` 拿不到；若用文件名冒充，等于给用户一条假信息，比没有更坏 |
| **首张封面** | `mediaPaths[0]`，可手动调整 | 列表密度与识别速度 |

结论：多图记录的"上下文"不能靠自动采集，只能靠**标签 + 一句说明 + 导入时间点**三样轻量信息承载，并引导用户补那"一句说明"。

## 五、交互流程

### 入口

- **主入口**：底部主按钮「拍一张」内的三分支面板——相册 / 拍照 / **从聊天导入**。不新增第四个底部按钮（现有三按钮布局、i18n 260 键基准、copy.test 55 条都被锁死，动一个牵一片）
- **次入口**：「我的 → 数据」区一行文字入口（低频、可发现性兜底）

### 主流程（4 步，无确认页）

1. 点「从聊天导入」→ `wx.chooseMessageFile({count: 9, type:'image'})`
2. 选择器返回 → **直接落库为一条 photo 记录**，正文空、tags 空、source 标记为 chat
3. 进度反馈：底部轻提示「正在保存 3/9」，**不用全屏 loading 遮罩**（9 张压缩+落盘 2–5 秒，遮罩会让用户以为卡死并强退）
4. 保存完成 → 回首页，新卡闪一次底色（复用 `flashId`）→ 卡片上出现「补个说明」提示位

### 事后操作

- 改一改：编辑正文／标签／拖动排序／设封面
- 拆开存：拆成 N 条，正文与标签**复制到每一条**（拆开的理由是"其实不是一件事"，每条都该有完整语境），并给每条标记 `source.splitFrom`
- 删了：与现有软删 + 24 小时撤销一致

## 六、后续检索与复用（最容易漏的一环）

多图记录若正文为空，**全文搜索搜不到它**——这是本方案最大的隐性风险。

三道防线：

1. **引导补一句**：卡片上的"补个说明"占位，点进去直接聚焦 `textarea`，一句话即可
2. **按类型筛选**：搜索页加一个「只看图片」chip，作为"我懒得写字"用户的兜底
3. **重温页支持条内翻图**：现有 `flip.js` 是"上一条/下一条"，需扩展为"第 k 张 / 共 n 张"。否则重温一次只能看到封面，价值打折
4. **做成图直接受益**：v1.8.3 的多图错落排版立即可用，且可反向当作卖点——"一组图一键成图"
5. **备份完整性**：`transfer.js` 的 `mediaFiles()` 需按 `mediaPaths` 全量导出，并验证 9 张图的「导出→清空→导入」还原一致（文件数、字节数、顺序）

## 七、边界情况

| # | 情况 | 处理 |
|---|---|---|
| 1 | 用户取消选择（0 张） | 静默返回，不提示 |
| 2 | 选超额度 | 明确告知保留前 N 张 + 清理多余临时文件 |
| 3 | 单张超 10MB | 压缩；压缩失败则回落原图并计入总量预估 |
| 4 | GIF 动图 | `compressImage` 会丢动效，检测后保留原图 |
| 5 | HEIC / 少见格式 | 压缩失败 → 回落原图；仍失败 → 单张跳过，不整批失败 |
| 6 | 聊天文件已过期／读取失败 | 逐张处理，结束后汇总「9 张里 2 张读取失败」，已成功的照常保存 |
| 7 | 路径无扩展名 | 复用 `sniff.js` 判定类型（已有能力，必须走它） |
| 8 | 存储配额（200MB）不足 | 落盘前用 `Σsize` 预估，不足则提示并给出「我的 → 存储占用」跳转，不半途失败 |
| 9 | 记录总数到 1000 上限 | 明确提示先清理，不静默失败 |
| 10 | 中途退出／落盘中断 | 产生孤儿媒体文件 → 启动时做一次"目录 ∩ mediaPaths 差集"清扫；或保存流程失败即回滚已落盘文件 |
| 11 | 编辑页有草稿 | 从聊天存不得清空 `lg.draft.v1` |
| 12 | 重复导入同一批图 | 按 `size + 名称`（或内容 hash）判重，提示「其中 5 张已存过」，给「只存新的」选项 |
| 13 | 聊天里选的是表情／贴纸 | 允许（用户既然选了），但小尺寸图在卡片里不要放大糊掉 |
| 14 | 深色模式 / 长文本卡片 | 9 张图九宫格会吃掉列表密度 → 卡片图区高度封顶（3 行 = 6 张 + 第 7 格 "+3"） |
| 15 | 中英双语 | 所有新文案必须入词典、中英各一条，且不能有模块级 `i18n.t()`（`lang-audit` 会抓混排，本项目硬约束） |
| 16 | 隐私合规 | `chooseMessageFile` 选的是"文件"，部分审核口径要求在隐私指引中单列「选中的文件」而不只是「选中的照片或视频」。**上线前必须核对指引条目，缺则补**——这是会被驳回的硬项 |

## 八、必须避免的问题（按危害排序）

1. **不要假装知道来源**。"来自 XX 群""XX 发给你"都是编造，`chooseMessageFile` 无此能力。
2. **不要静默截断张数**。用户以为存了 12 张、实际 9 张，是最伤信任的失败。
3. **不要保存前弹确认页**。破坏"先落库"的一致体验。
4. **不要给每张图建一条记录**。用户意图是"一件事"，拆散即误解。
5. **不要做混合类型记录**。数据模型、备份、组件、编辑页四处连锁崩。
6. **不要让多图记录变成"搜不到的黑洞"**。必须有"补一句"引导 + 类型筛选兜底。
7. **不要用全屏 loading 遮罩**盖住 2–5 秒的保存过程。
8. **不要展示"来自微信"角标**。对用户零价值，只暴露渠道感；来源只做内部字段。
9. **不要因为多图就让卡片无限高**，列表会被撑散。
10. **不要忘记清理失败/多余的临时文件**，200MB 配额经不起反复试错。

## 九、落地顺序建议

| 阶段 | 内容 | 说明 |
|---|---|---|
| P0 | 多图落一条 + 进度提示 + 超限告知 + 逐张容错 + 清理临时文件 | 没有它功能不成立 |
| P0 | 隐私指引补「选中的文件」条目核对 | 缺了会被驳回 |
| P1 | 卡片"补个说明"引导 + 搜索页类型筛选 | 决定能否被找到 |
| P1 | 拆开存（24 小时内）+ 设封面 + 拖动排序 | 兜住默认值猜错的场景 |
| P2 | 重温页条内翻图 | 复用价值最大化 |
| P2 | 判重提示 + 孤儿媒体清扫 | 长期稳定性 |
