# 灵感随时记 · 微信小程序（本地存储版）

按《灵感随时记 · 需求分析与产品设计方案 v1.0》落地的可运行工程：原生小程序，无云开发依赖，所有数据落在 `wx.setStorageSync` + 本机用户目录，导入即可跑通「记录 → 浏览 → 查看 → 编辑 → 删除 / 撤销」全链路。

---

## 一、怎么跑起来

1. 微信开发者工具 →「导入项目」→ 目录选本文件夹（`灵感随时记-完整版/`）。
2. AppID 填自己的；没有公众号主体就点「测试号」或「不使用云服务 / 无 AppID」。
   - 工程里预置的是 `touristappid`，仅供无 AppID 预览，正式上传前必须换成自己的。
3. 编译后首屏就是卡片流，点顶部「今天想到什么？」或底部并排的「写一句 / 说一段 / 拍一张」即可记第一条。

> 不需要开通云开发，不需要配置服务器域名，不需要登录。

## 三、数据模型与存储

记录的字段刻意压到最小，够用且不给自己挖坑：

```js
{
  id: 'r1a2b3c4d5e6f',   // 本地主键，时间前缀便于排查
  type: 'text',          // text | voice | photo，一条只允许一种
  content: '',           // 文字正文 / 照片配文 / 语音备注，最多 1000（语音照片 200）
  mediaPath: '',         // 语音/照片的本机持久路径，文字为空
  duration: 0,           // 语音秒数
  size: 0,               // 媒体字节数
  createdAt: 1760000000000,
  updatedAt: 1760000000000,
  deletedAt: 0           // 非 0 即软删，列表与统计都不再计入
}
```

| 存储键 | 内容 | 说明 |
|---|---|---|
| `lg.records.v1` | 记录数组（平铺、不分片） | 1000 条上限，一次同步读写；软删记录留在数组里等清理 |
| `lg.meta.v1` | `{ firstAt }` | 「开始记录」日期 |
| `lg.draft.v1` | 文字草稿 | 300ms 防抖，关掉小程序也不丢 |

媒体文件不塞进 Storage（10MB 上限且 base64 会膨胀），统一落在 `wx.env.USER_DATA_PATH` 下，库里只存路径。

## 四、四条核心链路与关键代码

### 1. 创建（`pages/record/record.js` → `onSave`）

- 三种形态共用一页：`type` 切换时若已有内容会二次确认「刚才的X会清掉」，杜绝一条记录混两种形态。
- 文字：`textarea` 自动聚焦、`maxlength=1000`、无标题无分类。
- 语音：默认按住说话（松手即存、上滑 60px 取消），可切换为点击录音；实时计时，60s / 240s 各震一下但**不打断**；到 300s 由 `RecorderManager` 自动收尾。
- 照片：`chooseMedia` → `compressImage` → `saveFile` 落盘，配文可选。
- 保存走「先落库、再返回」，不弹"保存成功"，只在列表里让新卡片闪一次底色（`flashId` → `highlight`）。

```js
const rec = mode === 'edit' ? store.update(id, payload) : store.create(payload)
if (!rec) return                       // 失败已在数据层提示，页面不重复弹窗
this.saved = true
store.clearDraft()
getApp().globalData.flashId = rec.id   // 交给首页做一次性高亮
this.leave()
```

### 2. 浏览（`pages/index/index.js`）

- 吸顶伪输入条：1 次点击进文字态，滚动时不消失（`position: sticky`）。
- 按自然日分组（今天 / 昨天 / 11月3日），首屏 20 条，触底再 +20（`onReachBottom`）。
- 文字超 6 行折叠为「展开」，短句不出现该按钮。
- 下拉刷新用系统回弹，不额外加重试逻辑。

### 3. 查看与编辑

- 卡片点击进 `pages/detail/detail`，展示完整正文、播放录音、大图预览。
- 编辑入口有两处：详情页「改一改」、列表长按「改一改」。都复用 `record?mode=edit&id=`。
- 编辑只改 `content`（语音/照片可换媒体），**`createdAt` 永不变**，所以列表顺序不会因为改一句话而跳动；真的改过才在卡片上标「改过」。

### 4. 删除与撤销

```js
// 数据层：软删，不立刻销毁
function remove(id) { /* deletedAt = Date.now() */ }

// 首页：5 秒倒计时条 + 撤回
deleteItem(item) { store.remove(item.id); this.refresh(); this.showUndo(item.id) }
onUndo() { store.restore(this.pendingDeleteId); this.refresh() }
```

`app.js` 在启动和切后台时跑 `store.purge()`，物理清除超过 24 小时的软删记录，并顺手删掉它们的媒体文件——避免"删了但空间不还"。

| PRD 条目 | 落地情况 |
|---|---|
| 三种记录形态（文字/语音/照片）、单条单类型 | ✅ |
| 卡片流按日分组、相对时间、6 行折叠 | ✅ |
| 伪输入条 1 次点击进输入态 | ✅ |
| 长按 → 复制 / 删除 + 5 秒撤销 | ✅ |
| 空态一句话 + 直接入口 | ✅ |
| 语音不截断、计时、60s/240s 提示、300s 上限 | ✅ |
| 弱网/无网先存本机 | ✅（本地存储版本天然离线，不存在待同步态） |
| 上限 1000 条、媒体压缩 ≤300KB | ✅（压缩目标 quality 70；1000 条上限硬拦） |
| 第 7 天回访、订阅消息、回顾页 | ⛔ 本工程不做，见第六节 |
| 标签 / 搜索 / 打卡 / 分享 / AI | ⛔ 按 PRD 明确不做 |

### 两处有意偏离，需要你知道

1. **PRD 写"不做编辑"，这个版本做了。** 需求方明确要求"创建、编辑、查看、删除"，所以补上编辑。为不破坏「8 秒记一条」的产品假设，做了三点约束：编辑入口全部下沉到长按与详情页（首屏主路径仍是"写一句就存"）；编辑不改 `createdAt`，列表不跳动；卡片上加「改过」标记，让"修饰过的文字"和"原始捕捉"在视觉上可区分。
2. **记录面板从"半屏升起的 sheet"改成独立页面。** 小程序里页面级 sheet 要自己扛键盘顶起、滚动穿透、返回手势三件事，坑比收益多；当前实现是独立页 + 自绘顶部栏（取消 / 存下），键盘弹起行为与 sheet 一致，返回即回列表，观感差别很小。要真做成 overlay，可把 `record` 的 WXML 搬进 `components/record-sheet` 在首页 `wx:if` 弹出，数据层不用动。

## 六、已知限制（写在这里，避免上线后当 bug 排查）

1. **数据只在本机。** 卸载/重装小程序、清理微信存储、换手机都会丢。这是"零后端"的代价，PRD 的 1000 条容量与多端同步都需要服务端。
2. **本机媒体有配额。** `wx.saveFile` 落在用户目录，总量有限（旧版 10MB 量级），照片压缩后约 200–300KB，几十张就会触顶。触顶时 `saveFile` 失败会降级为临时路径，本次会话可见、重启后失效。要长期存图必须上对象存储（PRD 第六节）。
3. **照片/相机需在后台配置「用户隐私保护指引」。** 未配置时真机上 `chooseMedia` 会直接失败（开发者工具里一般不拦）。录音同理需要声明麦克风用途。
4. **回访链路没接。** 第 7 天订阅消息、站内回访卡、回顾页需要云函数 + 定时触发器，工作区里另一份 `灵感随时记-小程序/` 就是那套云开发实现，可作为后续合并的基础。
5. **没有全文搜索。** PRD 把它放在 v1.1（人均 >50 条再做）。当前数据量下靠日期分组翻找更快。

## 八、列表分组、删除与数据搬移（v1.1）

### 8.1 分组规则

按「由近及远」切四个时间桶，命中即止，不做二次细拆：

| 桶 | 判定 | 展示 |
|---|---|---|
| 今天 | 自然日差 ≤ 0（含手机时间超前产生的未来记录） | 卡片平铺，最上面 |
| 本周 | 与本机同一自然周（**周一为起点**），且不是今天 | 堆叠组，折叠 |
| 本月 | 同一自然月，且不在本周 | 堆叠组，折叠 |
| 今年 | 同一年，且不在本月 | 堆叠组，折叠 |
| 往年 | 更早的年份，各年一组，如「2025年」 | 堆叠组，折叠 |

边界说明：上周日不算「本周」而落到「本月」；12 月 31 日与次年 1 月 1 日一定是两个不同的年桶。

实现位置：`utils/date.js` 的 `bucketOf` / `groupBuckets`，纯函数，`now` 可注入，便于验证。

### 8.2 堆叠样式

折叠态用三层卡片边缘错落叠放（`scale` 0.90 / 0.95 / 1.00，透明度 0.45 / 0.72 / 1），最上层露出该组最新一条的角标、时间与一行摘要，右下角标「还有 N 条」。点击组头或整块堆叠即展开为完整卡片列表。

### 8.3 删除的三条路径

| 入口 | 交互 | 保护 |
|---|---|---|
| 单条 | 卡片**向左滑**，露出红色「删了」按钮，点它删除；滑不够距离自动回弹 | 5 秒撤销条 |
| 单条 | 长按卡片 → 菜单里的「删了」 | 5 秒撤销条 |
| 整组 | 组头右侧「删整组」→ 二次确认弹窗（写明分组名与条数） | 5 秒撤销条，撤回可**整组恢复** |

- 同一时刻只允许一条卡片处于左滑打开状态，由页面的 `openSwipeId` 统一调度。
- 删除是软删（打 `deletedAt`），24 小时后才由 `app.js` 的 `purge()` 连媒体文件一起物理清除。
- 批量删除只写一次盘，中途失败不会留下"删了一半"的状态。

### 8.4 换设备：导出 / 导入

入口在「我的 → 换手机」。

**导出**：把所有记录打成一个 JSON。图片和录音无法跨设备引用本地路径，因此读成 base64 内嵌。
- 单条媒体上限 2MB、总计上限 15MB，超出的只迁文字，并在结果弹窗里如实报数量。
- 手机端用 `wx.shareFileMessage` 转发到「文件传输助手」；桌面端用 `wx.saveFileToDisk` 直接存盘。

**导入**：从聊天记录里选那个 `.json`（`wx.chooseMessageFile`），校验文件头 → 还原媒体到新机沙箱 → 按 id 合并。
- **只做新增，不覆盖**：同 id 已存在则跳过，所以反复导入同一份不会产生重复，也不会冲掉新手机上刚记的内容。
- 导入后会自动把「开始记录」时间修正到更早的那条。

实现位置：`utils/transfer.js`（打包/解包）+ `utils/store.js`（`importRecords` / `removeMany` / `restoreMany`）。

## 九、检索、回顾与输入增强（v1.2）

### 9.1 数据结构的变化

记录从「单一媒体」升级为「一组媒体 + 三个新字段」：

| 字段 | 含义 |
|---|---|
| `mediaPaths: string[]` | 照片最多 9 张；语音仍只用 `mediaPath` |
| `tags: string[]` | 从正文里的 `#标签` 自动解析，最多 8 个 |
| `starred: 0\|1` | 星标，钉在「星标」筛选里 |
| `archivedAt: number` | 非 0 表示已归档，不进主列表但不算删除 |

老数据不需要迁移：`store.js` 的 `normalizeRecord()` 在读取时补齐这四个字段，`mediaPath` 会自动升级成 `mediaPaths: [mediaPath]`。

### 9.2 标签怎么写

正文里直接写 `#读书`、`#产品想法`，保存时自动归好，列表卡片上会显示前 3 个。
标签字符集：中英文数字，遇空格或 `，。！？、` 等标点即止，单个标签最长 12 字。

### 9.3 五个新入口

| 位置 | 作用 |
|---|---|
| 首页顶部放大镜 | 进搜索页：全文搜索 + 标签快捷筛选 + 命中高亮 |
| 首页筛选条 | 全部 / 星标 / 归档 / 单标签，四个维度互斥切换 |
| 首页「那年今日」卡 | 自动出现去年或前年同一天的那条，点开看全文 |
| 我的 → 随便翻一条 | 随机重温，偏向 7 天以上的旧记录，可加星、转发 |
| 首页顶部「从聊天存」 | 从微信聊天里选文件/图片，直接存成灵感（v1.6 从「我的」迁来） |

### 9.4 长图分享

卡片长按 → 「做成图」，或详情页 → 「做成图」。
`utils/poster.js` 用 Canvas 2D 排版：750 宽、高度按内容算、正文最多 26 行、带标签与页脚。
生成后可保存到相册，或走 `wx.showShareImageMenu` 直接发给朋友。

两个技术点值得记一笔：

- canvas 2d 每次改 `width/height` 都会重置上下文，所以必须「先量高 → 再定尺寸 → 再绘制」，量的时候用临时高度。
- `drawImage` 只吃 `canvas.createImage()` 出来的 Image 对象，喂路径字符串画不出来，因此 `poster.loadImage(canvas, src)` 必须先取尺寸再等 `onload`。

### 9.5 转发与接收

所有页面的转发都会带一段正文进去：`/pages/index/index?inbox=<encodeURIComponent(正文前 400 字)>`。
接收方打开小程序会看到「收到一条分享」，确认后存成自己的一条本地记录——因为数据本来就只在本机，跨设备只能靠"把内容带过去"，不能靠同步。

### 9.6 语音转文字：说清楚边界

小程序没有「给一个音频文件、还一段文字」的能力。真正可用的只有微信同声传译插件（`WechatSI`），而它是**边录边转**、不能事后转写。

所以这里的实现分两层：

- **默认可用的**：语音记录下方就是文字备注框；详情页对没有文字的语音/照片提供「补一句文字」。补上之后这条就能被搜索命中，这是"语音可检索"的实际达成路径。
- **需要额外两步的**：`utils/asr.js` 里把 `USE_PLUGIN` 改成 `true`，并在 `app.json` 增加 `plugins` 声明、在小程序后台添加该插件。启用后录音会边录边出字，最终文字直接写进正文。未启用时按钮不会出现，不会出现"点了没反应"。

### 9.7 每日提醒：只做了能做的那一半

> **本节已作废（v1.7.4）。** 一次性订阅一次授权只能发一条，工具类小程序申请不到长期订阅，
> 「每日提醒」按字面意义做不到，已整体下掉，改成首页的「今天还没记一句」。见第二十一章。

订阅消息必须由**服务端**下发。客户端能做的只有「请求授权 + 记住时间」，真正到点弹出通知要靠自建服务端或云函数按 openid 发送。

因此：

- `utils/remind.js` 顶部留了 `TMPL_ID`，填上小程序后台创建的模板 ID 才会真正请求授权；
- 没填时，点「每日提醒」会如实说明还差一步，并把时间偏好记下来；
- 我的页的「提醒时间」可以正常选，选完会持久化，等模板配好就生效。

## 十、多图错落堆叠（v1.3）

### 10.1 长什么样

一条记录带 2 张及以上照片时，卡片里不再只显示第一张 + 一个「N 张」角标，而是把照片按「散落的相纸」铺开：

- 每张照片带 10rpx 白边、18rpx 圆角、两层投影，像一叠实体照片；
- 位置、旋转（-9°～+6°）、层级各不相同，前一张压住后一张的边角；
- 2 张是「一前一后、右下压角」，3 张是「中间落底、上下错开」，4 张是「铺满整块、层层压边」；
- 超过 4 张只铺 4 张，最上面那张角标 `+N`，总张数看卡片左上角的「照片 N 张」；
- 点哪张就从哪张开始全屏预览（`previewImage` 的 `current` 跟着走）。

### 10.2 为什么不会抖

| 做法 | 解决什么 |
| --- | --- |
| 照片框尺寸、坐标、容器高度全部用固定 `rpx`，写死在 `buildStack()` 里 | 图片加载前后盒子尺寸不变，列表不会因为解码完成而跳动 |
| 容器高度按本组最底边收口（`stackH`），而不是固定一个数 | 2/3/4 张的图组下方留白一致，卡片节奏整齐 |
| 旋转角度额外算进包围盒（`sin(θ) * FRAME_W / 2`） | 斜着的照片不会压到下面的正文 |
| 堆叠位次用记录 `id` 做散列抖动（±5rpx、±1.2°） | 同一张卡片每次渲染位置一致；不同卡片不雷同，翻列表不会「全军整齐」 |
| 图片 `mode="aspectFill"` + 相纸底色占位 | 任意长宽比的照片都填满相框，未加载时是米色纸面而不是白洞 |

### 10.3 适配

全部尺寸走 `rpx`，屏幕变宽整组等比放大：手机 375pt 下相框约 165×127pt，桌面端（微信 PC 大窗口）同步放大，不会出现「手机好看、电脑散架」。没有用 `vh/vw`、没有用 `media query` 打补丁，换机型不需要再调。

- 0 张（媒体丢失）：大图位置显示米色占位，不报错。

## 十一、统一对话框（v1.4）

### 11.1 为什么不用 wx.showModal

系统弹窗的遮罩是黑色半透明、标题正文用系统字重，在暖白纸感界面里像贴了个外来件；更实际的问题是它只能改一个 `confirmColor`，**危险态和加载态做不出来**——"清空全部"和"从备份导入"长得一模一样，用户只能靠读字区分。

所以自绘一个，视觉只用 `app.wxss` 里的 token，不新增色号。

### 11.2 怎么用

页面挂一次，然后命令式调用，Promise 风格：

```html
<dialog-view />
```

```js
const dialog = require('../../utils/dialog')

dialog.alert({ title: '导出完成', text: '共 42 条' })

dialog.confirm({ title: '清空全部灵感？', text: '共 42 条，找不回来。', danger: true })
  .then(r => { if (r.confirmed) store.clearAll() })

// 异步确认：hook 返回 Promise 时自动进 loading，resolve(false) 留在原地
dialog.show({
  title: '导入备份',
  onConfirm: () => transfer.importBackup().then(r => { done(r); return true })
})
```

`utils/dialog.js` 维护一个实例栈（页面返回时上层自动出栈），**没有实例时退回 `wx.showModal`**——`store.js` 这种数据层在 App 启动阶段报"存不下了"也不会因为 UI 没挂载而静默丢失提示。

### 11.3 视觉规范（唯一基准：app.wxss）

| 项 | 取值 | 与现有组件的关系 |
| --- | --- | --- |

## 十二、"本机占用 2 KB / 10240 KB"到底在说什么

### 12.1 两个账本，别混着看

| 账本 | 存在哪 | 上限 | 装什么 |
| --- | --- | --- | --- |
| **键值存储** | `wx.setStorageSync` | **10240 KB = 10 MB**（`wx.getStorageInfoSync().limitSize`） | 记录数组、偏好、草稿、元信息，全是 JSON 文本 |
| **本地文件** | `wx.env.USER_DATA_PATH` | 约 **200 MB**（平台配额，非本 API 返回） | 照片、录音文件 |

所以截图里的 `2 KB / 10240 KB` 是**第一本账**：这个用户的全部记录索引只用了 2 KB，占 10 MB 的 0.02%。照片和录音不在这 2 KB 里，它们在第二本账里单独计。

这也解释了一个常见误会："我拍了 50 张照片，为什么占用还是 2 KB？"——因为存的是路径字符串，不是图片本身。

### 12.2 超过 10240 KB 会发生什么

1. `wx.setStorageSync` **抛异常**（`setStorage:fail exceed storage max size` / `errno` 相关），不是静默失败。
2. `store.js` 的 `writeAll()` 捕获异常 → 把内存缓存置空 → 弹「存不下了」→ 返回 `false`。
3. **已有数据不会丢**：写失败意味着旧值原样保留，丢的是这一次的新记录。
4. 不会自动清理、不会自动扩容、不会降级到别处。下次再写仍然失败。
5. 同一份存储里其它 key（偏好、草稿）也可能一起写失败。

正常情况下**碰不到 10 MB**：`MAX_RECORDS = 1000`，一条纯文本记录连字段带标签约 200–400 字节，1000 条也就 200–400 KB；就算每条都写满 1000 字，也在 2 MB 量级。真正先到的上限是"1000 条"，不是 10 MB。

### 12.3 该怎么处理

- **产品侧**（已做）：`我的` 页拆成两行——「记录索引 2 KB / 10 MB（已用 <1%）」和「图片与录音 12.4 MB · 36 个」，点任意一行弹出说明，讲清两本账。
- **预警**：索引 ≥80% 或文件 ≥150 MB 时，页面顶部出现赭色提示条，引导"先导出再清理"。
- **写入失败**：只提示、不静默丢弃；用户可以先 `导出到文件`，再清空或删旧记录。
- **媒体失败**：`saveFile` 失败会降级成临时路径（本次会话可见、重启失效），已在 `utils/media.js` 里如实提示，不假装存住了。

### 12.4 这些限制要知道

1. `currentSize` 统计的是**这个小程序**在该用户设备上的全部 key，不区分是记录还是别的；换账号/换设备不共享。
2. 用户清微信缓存、卸载小程序，存储会没——**导出是唯一保险**。
3. 10 MB 是平台给的，客户端不能申请扩容；想突破只能把大块数据挪到文件或云端。
4. 文件配额（约 200 MB）也没有官方 API 能查"还剩多少"，只能用 `statSync` 自己累加（`store.usage()` 就是这么做的，成本 O(文件数)，只在"我的"页调用）。
5. 录音、照片的元数据（时长、宽高）存在 JSON 里，文件被系统清掉后记录会"有壳没内容"，所以删除记录时同步 `unlink`，避免僵尸条目。

## 十四、缩略图网格与语音列表（v1.5）

### 14.1 照片：按张数分列，不写断点

原来的重温页遇到照片只显示一句"这条是照片，去详情里看"，卡片里是一大片空白。现在照片直接铺成缩略图：

| 张数 | 排布 | 格子比例 | 说明 |
| --- | --- | --- | --- |
| 1 张 | 整幅 | 3:2 裁切 | 一张不值得切碎，铺满更好看 |
| 2 张 | 两列一行 | 4:3 | 并排两张，比上下两张更像"一组" |
| 3 张 | 三列一行 | 1:1 | 一行放下，不留孤儿 |
| 4 张 | 2×2 | 4:3 | 比"三列 + 落单一张"整齐 |
| 5–9 张 | 三列九宫格 | 1:1 | 行数随张数增减 |
| 10 张以上 | 九宫格 + 折叠 | 1:1 | 只铺 9 张，第 9 张右下角 `+N` |

规则只看张数，不看屏宽——列数是内容决定的，屏幕只决定格子多大。

### 14.2 为什么加载不跳、两端都不散

| 做法 | 解决什么 |
| --- | --- |
| 格子宽度用百分比（50% / 33.33%），高度用 `padding-top` 百分比撑 | 高度是宽度的函数，图片解码前后盒子尺寸一致，列表不跳 |
| 图片绝对定位铺满格子 + `mode="aspectFill"` | 任意长宽比都填满，不留白边、不撑破格子 |
| `lazy-load`（前三张除外，首屏要快） | 长列表滚动时不一次性解码几十张图 |
| 加载时 0.18s 淡入 + 米色纸底占位 | 慢网下是"纸面渐显"，不是白洞闪一下 |
| `binderror` 换占位块 | 文件被系统清掉时不显示裂图 |
| 全部尺寸走 rpx + 百分比，没有 `vw`、没有 media query | 手机 375pt 与桌面大窗口是同一套规则，等比放大 |

点哪张就从哪张开始 `previewImage`，索引跟着 `data-i` 走。

### 14.3 语音：可以，而且就按列表做

录音完全可以在页面里以列表呈现，一条音频一行，行内自带播放键、进度条、状态与时长：

```
┌─────────────────────────────────────────┐
│ (▶)  ▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬         │
│      点一下听                      0:08 │
└─────────────────────────────────────────┘
```

- **一行一音频**：`voices` 是数组，现在一条记录只存一段录音所以只有一行；将来支持多段时，模板不用改，往数组里多推几个对象就是列表。
- **三态**：闲置（空心三角 + "点一下听"）、播放中（暂停图标 + 进度填充 + "正在播放"）、暂停（保留进度 + "已暂停，点一下接着听"）。
- **进度**：`InnerAudioContext.onTimeUpdate` 每 250ms 触发，只在整秒变化时 `setData`，避免白渲染；时长优先用播放器回调的 `duration`，取不到就退回记录里存的秒数。
- **互斥**：全局单例播放器，点第二条会自动停掉第一条，不会两条一起响。
- **离开就静音**：`onHide` 停播、`onUnload` 释放，重温是"看一眼"，不该带着声音走出页面。

### 14.4 适配方案

| 场景 | 处理 |
| --- | --- |
| 手机窄屏 | 行高固定 116rpx，进度条弹性伸缩（`flex:1`），横竖屏都不挤 |
| 桌面大窗口 | 行随卡片变宽，进度条按比例变长，文字与时长始终贴两端 |

### 15.2 迁移后：首页顶部，一眼能看到

```
┌──────────────────────────────────────────┐
│ 我的灵感  42 条        从聊天存  多选  我的 │
│ ┌──────────────────────────────┐  ┌───┐  │
│ │ 今天想到什么？              ✎ │  │ 🔍 │  │
```

- **为什么放头部而不是底部三入口**：底部「写一句 / 说一段 / 拍一张」是"就地产生内容"，是上一轮特意定的三等分，加第四个会把那个节奏打散；「从聊天存」是**把别处的东西收进来**，属于另一个心智，放导航同级更合适。

- **行为不变**：同一个 `transfer.importFromChat()`、同一个"处理中"遮罩、同一套成功/失败文案、取消不报错。

### 15.3 顺手修掉的一个真问题

迁过来读代码时发现：原来的 `importFromChat()` 只把文件解析成 `{type, content, mediaPaths}` 的**草稿**并 resolve，`me.js` 拿到后直接弹「已存下 N 条」——**从头到尾没有调用 `store.create()`，什么都没落库**。也就是说旧版本上点这个入口，看到"已存下"但列表里什么都不会出现。

现在补上真正的写入：逐条 `store.create()`，成功几条就报几条；因为满 1000 条或落库失败而没进去的，如实补一句「有 N 条没存下，可能已经满 1000 条了」。存完切回「全部」筛选、刷新列表，并让最上面那条闪一下。

### 15.4 左右翻：抽样规则只有一份

新增 `utils/flip.js`，把「下一条是谁」这件事从页面里抽出来：

| 函数 | 语义 |
| --- | --- |
| `enter(id)` | 进详情时对齐"当前这一条"。从重温页进来，栈顶正好是它，于是接着用那一轮历史；从列表/搜索点进来则重开一轮 |
| `next()` | 栈里还有"前一条"就先走回去（右滑过之后能原路返回），走到头再按**重温页原来的规则**抽：排除当前、优先 7 天以上、随机 |
| `prev()` | 先回退这一轮看过的；本轮到头时按时间接一条更早的，并把历史补在左边，所以再左滑能回到刚才那条 |
| `canPrev()` | 还能不能往回翻，决定"上一条"是否置灰 |
| `total()` | 记录总数，决定要不要显示翻页条 |

`pages/review` 的「再来一条」也改成走这里（`flip.enter(当前) → flip.next()`），所以**详情页左滑和重温页再来一条拿的是同一套抽样、同一条历史**，不会出现"重温页刚看过的那条，详情页左滑又抽到"之外的两套口径。

手势本身：

| 项 | 取值 | 为什么 |
| --- | --- | --- |
| 方向判定 | 前 10px 不判向，之后 `|dx| > |dy| × 1.2` 才接管 | 手指按下的抖动不会把纵向滚动抢成翻页 |
| 触发阈值 | 横向 56px | 小于这个距离当"手抖"，滑回原位 |
| 跟手 | `dx × 0.4`，上限 96px | 有阻尼、拖不飞；到头了（没上一条/只有一条）阻力加大到 0.12 |
| 换场 | 先 0.14s 滑出 → 换内容并摆到另一侧 → 0.18s 滑回 | 有"换了一张"的连续感，不是硬切 |
| 兜底 | 页面底部「‹ 上一条 / 左右滑也能翻 / 下一条 ›」 | PC 端用鼠标滑不动，箭头补上；箭头和手势调的是同一个 `go(dir)` |

**换条时状态怎么复位**（这就是"与原翻页逻辑一致"的落点）：

1. `audio.stop()` 且 `playing: false` —— 上一条的录音不会跟着新内容继续响；
2. 复用 `load()` 重新读库 —— 类型、时间、照片、星标、归档、`needText` 全部由同一段代码算，不另写一份；
3. `wx.pageScrollTo({scrollTop: 0})` —— 新的一条从页首看起；
4. `swipeDx` 归零、`_switching` 解锁 —— 连滑不会叠出两条记录。

## 十六、重温页左右滑修复（v1.6.1）

### 16.1 现象

在「重温 → 随便翻一条」页面上左滑、右滑都没有反应，内容不换，纸也不动。

### 16.2 根因：手势绑错了页面

上一版（第十五章）只在 `pages/detail` 的根节点上挂了三个事件，**重温页一行都没绑**：

| 位置 | 上一版状态 | 结果 |
| --- | --- | --- |
| `pages/detail/detail.wxml` | 根节点 `bindtouchstart/move/end` + `swipeDx` 位移 | 详情页可滑 |
| `pages/review/review.wxml` | 无任何 touch 事件，`.paper` 上无 `transform` | 滑了等于没滑 |
| `pages/review/review.js` | 只有一个 `pick(false)` 的「再来一条」入口，没有方向 | 即使绑了也无从分「上一条 / 下一条」 |
| `utils/flip.js` → `pool()` | `rest` 为空时退回全量（含自己） | 库里只有一条时 `next()` 把当前这条再发一次，表现为「滑了但没变化」 |

「再来一条」和「滑一下」是两种取数意图，而 `pick()` 把**取数**和**渲染**揉在一个方法里，
手势拿到的条目没法交给它（再调一次 `flip.next()` 会抽成另一条），所以也无法用一个入口硬接。

### 16.3 改法

1. **拆开取数与渲染**：`pick()` 只负责「对齐栈顶 → 取一条」，新的 `show(item, buzz)` 只负责铺到纸上。
   手势从 `flip` 取到条目后直接 `show()`，不再二次取数，因此"用户滑到的那条"与"渲染出来的那条"必然同一条。
2. **手势挂到 `.page` 根节点**（与详情页同一套算法）：手指落在纸、缩略图、语音行、按钮上都算，
   位移只作用在 `.paper` 上（标题与按钮不动，像把一张卡抽走），`will-change: transform` 交给合成层。
3. **方向语义**：左滑 `go(1)` → `flip.next()`；右滑 `go(-1)` → `flip.prev()`。
   与「再来一条」共用 `flip`，所以两处的"下一条是谁"永远一致。
4. **`pool()` 不再回退到含自己的全量**，只有一条时如实返回 `[]`；同时新增 `flip.only()`
   兜住"首次进页面但库里只有一条"——没别的可翻，这一条本身还是要给他看。
5. 顶部副标题从「从 5 条里抽的」改成「左右滑能翻 · 共 5 条」，把刚加的手势讲出来（只有一条时显示「就这一条」）。
6. `onUnload` 清掉动画定时器；`onShow` 同步 `total / canPrev`（从详情页删了记录返回时数字不再过期）。

### 16.4 首尾边界规则（与详情页一致）

| 情形 | 左滑（下一条） | 右滑（上一条） |
| --- | --- | --- |
| 库里 ≥ 2 条，位置居中 | 换（先走回看过的，再按 7 天以上随机抽） | 换（先回退本轮看过的，再到头按时间往前接） |
| 库里只有 1 条 | 不换，阻力 0.12 回弹，**不弹提示** | 同左 |
| 已在最早一条 | 正常前进 | 不换，阻力 0.12 回弹，提示「已经是最早的一条了」 |
| 本轮历史到头但还有更早的 | 正常前进 | 按时间接一条更早的，并补在栈底（再左滑能原路回来） |
| 拖动 < 56px | 回弹、不换条 | 回弹、不换条 |
| 纵向拖动 | 不接管，交给 `scroll-view` 滚正文 | 同左 |

## 十七、从聊天存文字 + 首页回顾位（v1.7.0）

### 17.1 为什么是"剪贴板"，而不是"读聊天"

先把平台边界写死，免得以后反复讨论：

| 想拿到 | 有没有接口 | 说明 |
| --- | --- | --- |
| 聊天里的图片 / 文件 | `wx.chooseMessageFile` | 只能给**文件**，返回临时路径 |
| 聊天里直接打的文字 | **没有** | 文字不是文件，永远不出现在选择器里 |
| 聊天语音消息 | **没有** | 同上 |
| 聊天记录 / 会话列表 | **没有** | 不存在 `getChatHistory`、`onMessage` 之类接口，与企业资质无关 |
| 别人转发进来的文字 | `onShareAppMessage` 的 path query | 需要发送方主动写进 path |
| 用户自己复制的文字 | `wx.getClipboardData` | 剪贴板属隐私接口 |

所以"保存文字"唯一合法、且用户可理解的通路是：**在聊天里长按复制 → 回到小程序点一下**。
`utils/transfer.js` 的 `fromClipboard()` 就是这一段的唯一出口。

两条硬约束写在实现里：

1. **绝不自动读**。读剪贴板在 iOS 上会弹系统提示，偷偷读会让人觉得被监视；
   必须由用户点「粘贴刚复制的文字」才触发。
2. **超长不静默丢字**。一条最多 1000 字（`transfer.MAX_TEXT`，与记录页 `maxlength` 一致），
   超出时弹窗如实说"这段有 N 字，先收了前 1000 字"，而不是悄悄截掉。

### 17.2 一个入口，两种来源

「从聊天存」不再直接拉文件选择器，改成先弹 `action-sheet`（复用现有组件），两项：

| 选项 | 走什么 | 结果 |
| --- | --- | --- |
| 选图片 / 文件 | `transfer.importFromChat()` | 图片→照片记录；txt/md/csv→文字记录；其它二进制只留文件名并计入 failed |
| 粘贴刚复制的文字 | `transfer.fromClipboard()` | 一条文字记录，失败按 `empty / denied / unsupported / read` 分别提示 |

为什么不新增一个「粘贴」按钮：首页顶部那排已经有「从聊天存 / 多选 / 我的」三个，
再加会挤；而"收进来"本来就是一件事，用一次弹层分叉比多个图标更省地方。

### 17.3 回顾位：从「我的」第 4 屏搬到首页

**判断依据**（「随便翻一条」不属于高频操作）：

- 池子优先取 7 天以上的记录 → 新用户前 7 天抽不出东西，价值随库龄增长；
- 没有推送、角标、红点，只能靠"想起来"；
- 在原位置需要 3 次点击，中间隔着统计大数字、14 周热力图、统计块；
- 不解决任何任务（不帮你找、不帮你写），是消费型/惊喜型功能，通常周级。

**但低频 ≠ 该藏起来**。它承担的是留存与情感价值，要的是"入口浅、不占主位"。

**做法**：复用已有的一栏——筛选条下方「那年今日」的位置。

```
有那年今日  → 照旧显示那年今日（点击进详情）          优先级最高，不动
没有        → 显示「随便翻一条 · 从 N 条里抽 ›」      点击进 review
一条都没有  → 都不显示
```

同时 `pages/me` 的「回顾 → 随便翻一条」整行删除（分区标题从「回顾」改成「整理」，只留归档），
保证**唯一入口**——双入口会让两边都变弱。

`reviewTotal` 用 `flip.total()` 算，与重温页口径完全一致（含归档），
所以首页写的"N 条"和进去后副标题的"N 条"永远是同一个数。

### 17.4 分享 path：400 字改 120 字

原来三处都是 `encodeURIComponent(text.slice(0, 400))`。中文经 `encodeURIComponent`
一个字膨胀成 9 个字符，400 字≈3600 字符的 path，超过微信路径上限会被截断在 `%XX` 中间，
接收端 `decodeURIComponent` 抛错，正文就变成一串 `%E4%BB%8A`。

现在统一走 `utils/share.js` 的 `card(text)`：压空白 → 截 120 字（≈1080 字符）→ 拼 path，
标题取前 30 字。首页、详情页、重温页三处共用，不会再各写一份。

## 十八、聊天图片压缩落盘（v1.7.1）

### 18.1 问题：从聊天收进来的图是原图

`transfer.importFromChat()` 的图片分支原来调 `media.saveFile(f.path, ext)`，
这是「原样搬进沙箱」——**不压缩、不缩边、不改格式**。而相册/相机那条链路走的是
`saveImage()` → `compress()`，早就压到 300KB 以内了。同一个产品里两条导入路径待遇不同。

实际后果很直接：手机截图 1~3MB，手机照片 4~10MB，从聊天里选 9 张进来能吃掉 30~60MB。
本机文件空间是 200MB 量级，几十张原图就顶掉几千条文字记录——这是当前最容易被忽略的"存储漏水点"。

### 18.2 改法：新增 `media.saveChatImage()`，两级压缩

```
原图（例如 4000×3000，5MB）
  ↓ 第 1 轮：缩小到长边 1280 + 质量 70
200~300KB 左右
  ↓ 若仍 > 300KB：只降质量到 45 再来一轮（不再缩边）
通常 < 150KB
  ↓ 仍压不动：交原件，绝不为了省空间把图弄丢
```

第 1 轮就同时给 `compressedWidth / compressedHeight`，而不是只给 `quality`——
只降质量对 4000px 的大图效果有限（尺寸才是体积的主因），先把长边压到 1280 才是关键。
宽高按原图比例算，短边不裁切、不变形。

### 18.3 为什么不直接复用 `saveFile` 或 `saveImage`

| 候选 | 为什么不行 |
| --- | --- |
| `saveFile` | 原名原图搬进去，正是要修的问题 |
| `saveImage` | 只有 `quality: 70`，无长边控制；且无法告知"原始体积 / 省了多少" |
| 在 `transfer.js` 里现写一遍 | 压缩逻辑会分裂成两份，以后调整阈值必然漏掉一处 |

现在 `compress()` 也升级为「先取尺寸、再决定是否缩边」，所以相册链路同样受益；
`saveImage` / `saveImages` 签名不变，`record` 页不用改。

### 18.4 四条边界，都写进实现里了

1. **gif 不压**。压缩会把动图变成一张静图——宁可多占点空间，也不悄悄改掉这个东西的性质。
2. **老基础库不认宽高参数**（`compressedWidth/Height` 需 2.26.0+）时，`compressImage` 会直接 fail。
   实现里捕获这次失败，退回"只给质量"再压一次，而不是把图丢掉。
3. **压不动就交原件**：没有 `wx.compressImage`、两轮都失败、或压缩后反而更大，都保留原文件。
4. **原始体积优先用选择器报的 `f.size`**，拿不到才现场 `statSync`，避免多一次 IO。

`importFromChat()` 的返回值多两个字段：`compressed`（压了几张）与 `savedBytes`（省了多少字节），
首页弹窗因此能具体说"3 张照片压到 300KB 以内，省下 12.4 MB"，而不是一句模糊的"已优化"。

### 18.5 预期效果

| --- | --- | --- | --- |
| 手机截图（1290×2796） | 1.8 MB | ~200 KB | 省 89% |
| 手机照片（4000×3000） | 5.2 MB | ~240 KB | 省 95% |
| 微信转发的小图（800×600） | 90 KB | 不再压（长边 < 1280，体积已达标） | 不变 |
| 表情 gif | 900 KB | 900 KB | 不压（保动图） |

9 张照片一次性导入：原来 45MB 左右，现在 2MB 出头。

## 十九、竖向留白归位 + 文案去代码化（v1.7.2）

### 19.1 两页的空白，不是"感觉空"，是三个写法凑出来的

**详情页（这一条）**

```
.page { min-height: 100vh; padding: 32rpx 40rpx calc(120rpx + safe); }
```

- `min-height: 100vh` 但**没有任何 flex 分配**：内容少时，剩余空间全部堆在最后一个元素之后，也就是页尾。
- `padding-bottom: 120rpx` 本来是为了别贴着系统手势条，实际变成了"再叠一层留白"。
- 三段操作（5 个按钮 / 发给朋友 / 翻页条）各占一行，`margin-top` 又给了 64/16/40rpx，
  内容只有两行字，操作区却撑到 300rpx 以上——主次是反的。

实测：两行字的记录，翻页条之后到屏底还有约 210px 什么都没有。

**重温页（随便翻一条）**

```css
.paper { flex: 1; max-height: 62vh; }
.body  { flex: 1; max-height: 46vh; }
```

- `flex: 1` 是"必须占满"：纸被拉到 62vh，正文区又被拉到 46vh，
  内容只有一张图时，图下面自然多出一大块白（约 150px）。
- 纸有 `max-height` 上限，`.page` 的剩余空间没人接住，又堆到页尾（约 150px）。
- `.foot`（时间）`text-align: right` 贴着纸底，与照片隔着一整片空白，看起来像"忘了填内容"。

### 19.2 改法：空白必须有归属

| 位置 | 改前 | 改后 | 为什么 |
| --- | --- | --- | --- |
| 详情页 `.page` | 无 flex，页尾吃空白 | `display:flex; flex-direction:column` | 剩余空间才有"归谁"的余地 |
| 详情页结构 | 内容与操作并列 | `.main`（贴顶）+ `.bottom`（`margin-top:auto`） | 内容少 → 操作条贴底，底部有锚点 |
| `.bottom` | 无边界 | 1rpx 淡线上边框 + 32rpx 内距 | 那片空白变成"内容下方留白"，被线封口，不再像页面没做完 |
| 详情页 `padding-bottom` | `120rpx + safe` | `24rpx + safe` | 安全区不该兼职留白 |
| 页内间距 | meta 56 / actions 64 / flipbar 40+32 | 40 / 0（由 bottom 承担）/ 24+24 | 收紧竖向节奏，把高度让给内容 |
| 重温页 `.paper` | `flex:1; max-height:62vh` | `flex:0 0 auto; min-height:42vh; max-height:62vh` | 高度跟内容走；42vh 保证单张图时仍像"一张纸"，不会缩成一条 |
| 重温页 `.body` | `flex:1` | `flex:0 1 auto; min-height:0; max-height:46vh` | 短内容不撑高，长内容仍在上限内滚动 |
| 重温页 `.ops` | 紧跟卡片 | `margin-top:auto` | 按钮贴底，空白收在纸与按钮之间 |

改后：详情页底部留白从 ~210px 降到 ~30px；重温页纸内空白消失（时间紧跟照片），
纸下空白从"纸内 150 + 纸下 150"合并为"纸与按钮之间一段"。

### 19.3 弹窗的问题：一段讲配置的话出现在了用户面前

原文案（v1.7.1）：

> **还差一步**
> 每日提醒要靠微信订阅消息，需要先在小程序后台创建模板，把模板 ID 填进 utils/remind.js。
> 现在可以先把想被提醒的时间记下来。
> ［算了］［选时间］

四个问题，性质不同：

1. **混入代码**：`utils/remind.js` 是源码路径，`模板 ID` 是后台术语。用户不但看不懂，
   而且这件事他根本做不到——那是开发者在自己机器上改文件。
2. **责任错位**："还差一步"暗示用户少做了一步，实际是功能还没接通。
3. **伪承诺**：点「选时间」会走 `pickTime()`，而它只弹一句 toast「点右侧时间设置」——
   按钮承诺了一个不会发生的跳转，是最容易让人失去信任的那类交互。
4. **状态与文案不一致**：选完时间后 toast 说「记下了 21:00」，
   但开关仍是关的；用户会以为"提醒已经设成 21 点了"，到了点却没有通知。

### 19.4 上线发布时怎么处理

**原则：没接通的能力，不进发布包的用户可见路径。**
不是"写一段说明告诉用户为什么用不了"，而是"用不了就不出现"。

具体三层：

| 层 | 做法 | 代码 |
| --- | --- | --- |
| 版本门控 | 发布版（`envVersion === 'release'`）且未配模板 → 整块（含「习惯」标题）不渲染；开发版/体验版照常显示，方便联调和评审 | `utils/remind.js` 的 `visible()` / `status().visible`，`pages/me/me.wxml` 用 `wx:if="{{remindShow}}"` 包住 |
| 上线前置检查 | 发布前必须确认：① 后台已申请订阅消息模板并填好 `TMPL_ID`；② 隐私保护指引已勾选剪切板/相册；③ 真机走一遍"开启→到点收到通知"。三者缺一，提醒入口在发布版里自动消失 | 人工 checklist |
| 文案守卫 | UI 文案里出现 `utils/`、`.js`、`模板 ID`、`小程序后台`、`openid` 直接判失败 | `tools/design-lint.js` 第 6 条 |

第 6 条 lint 只扫"会被念给用户听"的地方：`dialog.alert/confirm` 的实参块，
以及命名以 `_ERR / _TEXT / _COPY / _MSG / _TIP` 结尾的文案常量对象。
不全文扫——源码注释里出现的真实路径是给开发者看的，不该报错。

### 19.5 面向用户的写法：三条规则

1. **说"现在能做什么"，不说"你需要去配什么"**
   改后文案：「提醒还没开通 / 每日提醒要用微信的订阅消息，还差最后一步才能真的发出通知。
   可以先把时间选好，开通后就会按这个点提醒你。」——不出现模板、后台、文件名。
2. **按钮的动词必须真的会发生**
   删掉「选时间」这个伪动作，改成单按钮「知道了」；时间就在下面那行，想选随时可点。
   `pickTime()` 一并删除。
3. **状态与文案必须对齐**
   行副标题与右侧值做成三态一致：`未开通 / 未开通`、`还没开 / 关`、`到点提醒你记一条 / 已开`。
   时间 toast 也分开说：已开通时「提醒时间改成 21:00」，未开通时「记下 21:00，开通后按点提醒」。

## 二十、聊天文件认不出类型导致"没存成"（v1.7.3）

### 20.1 现象

从聊天里选文件，弹「没读成 / 文件读不出来，可能已经损坏」，一个都没存下。
列表里还躺着一条正文为「来自「78a4bca059cff70d66e6b33621a75d18_26439…」」的记录。

两件事同源：**程序没认出这个文件是什么，就用最保守的方式处理了它**。

### 20.2 根因：三个问题叠在一起

**① 只按路径猜后缀。** `extOf(f.path)` 要求路径以 `.jpg` 这样结尾：

```js
function extOf(path) {
  const m = /\.([a-zA-Z0-9]+)$/.exec(path || '')
  return m ? m[1].toLowerCase() : 'dat'
}
```

而 `wx.chooseMessageFile` 给的 `tempFilePath` 经常**没有扩展名**：

| 平台 | 典型 tempFilePath |
| --- | --- |
| iOS | `wxfile://tmp_9f8a7b2c` |
| 安卓 | `http://tmp/xxx` |
| 带参数 | `wxfile://tmp_abc.jpg?size=1024`（这个连正则都匹配不上） |

于是截图被判成 `dat`，既不是图片也不是文本，直接掉进"二进制"分支。

**② 二进制分支写了一条没用的记录。** 原逻辑为了"至少留点东西"，把文件名写进正文：

```js
body = '来自「' + name + '」'
```

而 `f.name` 在某些场景就是那串哈希。结果列表里多出一条谁也看不懂、也搜不到的空壳。

**③ 失败只报一句"可能已经损坏"。** 实际有四种原因（认不出类型 / 读不出内容 / 存不进来 / 环境不支持），
却统一变成 `failed++`，最后 `reject({code:'read'})`。用户拿到的信息量是零，
而且**已经处理成功的文件也被一起丢弃**——因为 `reject` 不带 records。

### 20.3 改法一：新增 `utils/sniff.js`，四路判断

```
1. 文件名后缀（f.name）——用户看到的那个名字，最可信
2. 路径后缀         ——去掉 ?query / #hash 再取
3. 读开头 512 字节看魔数
   FFD8FF=jpg  89504E47=png  47494638=gif  RIFF…WEBP=webp  424D=bmp
   25504446=pdf  504B0304=zip/docx/xlsx
4. 还不是，就看这段字节像不像 UTF-8 文本（有 0x00 或控制字符就不是）
5. 都不是 → 二进制，如实说"认不出"
```

这套判断顺带解决了另一个老问题：**带 query 的路径**。`suffix()` 先 `split('?')[0]`，
`wxfile://tmp_abc.jpg?size=1024` 现在能正确取到 `jpg`。

### 20.4 改法二：一个文件失败，不连累其它

返回值从 `{records, failed}` 扩成：

| 字段 | 含义 |
| --- | --- |
| `records` | 待入库的记录 |
| `shells` | 只留下文件名的条数（PDF/Word 打不开正文，仍留着让用户补一句） |
| `skipped` | 完全没存下的，`[{name, reason, ext}]`，reason 取 `read` / `save` / `type` |
| `failed` | `shells + skipped.length`，兼容旧调用 |

只有 `records` 为空时才 `reject`，并且把 `skipped` 一起带出去：

```js
reject({ code: 'read', skipped: skipped })
```

于是页面能说清"是哪几个、为什么"，而不是一句"可能已经损坏"。

### 20.5 改法三：图片三级降级

```
saveChatImage（压缩后落盘）
  ↓ 失败
persist（原件直接搬进来）
  ↓ 失败
skipped.push({reason:'save'})
```

压缩失败不该等于图片丢掉。这条以前是 `failed++` 静默吞掉，现在至少会退到原件；
真存不进来才如实报，且原因写"可能是空间不够"。

### 20.6 改法四：机器名不进正文，也不进提示

`sniff.readableName()` 判三种机器名，命中就返回空串：

| 形态 | 例子 |
| --- | --- |
| 16 位以上连续十六进制 | `78a4bca059cff70d66e6b33621a75d18_26439` |
| `tmp_` / `tmp-` 前缀 | `tmp_9f8a7b2c` |
| 10 位以上纯数字 | `1699999999999` |

于是：

- 照片：正文留空，详情页自动出现「+ 补一句文字，这条就能被搜到」（`needText` 只看有没有正文，不分类型）；
- 二进制 + 有可读名：留「来自「会议纪要.pdf」」；
- 二进制 + 机器名：**不入库**，进 `skipped({reason:'type'})`，提示里只说"1 个认不出名字的文件"。

宁可少一条垃圾，也不要多一条看不懂的记录。

### 20.7 文案：把"为什么"和"接下来做什么"写出来

失败弹窗从一句话变成结构化：

```
这次没存成

选中的 3 个文件都没能存下来。

· 会议纪要.pdf（读不出内容）
· 一个认不出的文件（看不出是什么文件）

换成截图，或者在聊天里长按复制文字，这两种更稳。
```

部分成功时：

```
已存下 2 条，就在最上面。
1 张照片压到 300KB 以内，省下 4.2 MB。
1 个文件只留下了名字（PDF、Word 这类打不开文字），可以自己补一句。
还有 1 个没存下：会议纪要.pdf。
```

同时顺手堵住一个同类漏洞：`onRemind` 的失败分支原来写 `text: err.message`，
那会把 `requestSubscribeMessage:fail xxx` 这种原始错误串摆给用户。
现在改走 `REMIND_ERR` 码表，`design-lint` 也加了第 7 条：
UI 文案里出现 `err.message` / `err.errMsg` 直接判失败（已用探针验证）。

### 20.8 订阅消息接通之后，用户会依次看到什么

这是"配好模板之后会怎么提示"的完整链路，写下来免得每次重新推：

| 阶段 | 用户看到什么 | 出处 |
| --- | --- | --- |
| 进入「我的」 | 「每日提醒 / 还没开，点一下开启 / 关 ›」 | `me.wxml` |
| 点这一行 | **微信原生弹窗**：「灵感随时记 申请发送以下消息 · 记录提醒」+ 拒绝 / 允许 | `wx.requestSubscribeMessage` |
| 点允许 | toast「已开，明天 21:00 提醒你」；行变成「21:00 提醒你 / 已开 ›」 | `me.js` |
| 点拒绝 | toast「没授权，提醒不会来」，开关保持关闭 | `me.js` |
| 已开时再点 | 弹「关掉每日提醒？」→ 确认后 toast「已关掉」 | `me.js` |
| 到点 | 微信「服务通知」里一条卡片 | **服务端** `subscribeMessage.send` |
| 点通知 | 直接打开小程序指定页 | 下发时传 `path` |

**两个硬限制，必须在动手前知道：**

1. **通知不由小程序发**。`requestSubscribeMessage` 只完成"用户同意"，
   真正那条消息要自己的服务端/云函数按 openid 调 `subscribeMessage.send`。
   没有服务端，用户点了允许也永远不会收到——这也是 `visible()` 存在的原因：
   发布版没接通就整块不出现，而不是让人点进去等一条不会来的通知。
2. **一次性订阅 = 一次授权只能发一条**。工具类小程序申请不到"长期订阅"
   （微信只对政务民生、医疗、交通、金融、教育等线下公共服务开放）。
   所以「每日提醒」按字面意义做不到：昨天那条发完就没了。

**可行的替代，按推荐度：**

| 方案 | 成本 | 可靠性 | 说明 |
| --- | --- | --- | --- |
| A. 打开即提醒 | 零 | 100% | 进首页时若今天还没记，在回顾位那一栏显示「今天还没记一句 ›」。不依赖任何推送 |
| B. 每次记完顺手订阅 | 低 | 中 | 写完一条后问"明天这个点提醒你？"，用户点一次攒一条额度，合规但需每天配合 |
| C. 服务端 + 公众号 | 高 | 高 | 要用户关注公众号，转化损失大 |
| D. 写进系统日历 | 低 | 高 | `wx.addPhoneCalendar`，绕开订阅限制，但不在微信里 |

建议 **A 为主**，「每日提醒」这个开关等 B/C 真接通再打开——现在的门控已经保证了这一点。

## 二十一、打开即提醒 + 关于小程序（v1.7.4）

### 21.1 先把"每日提醒"这条路判死

上一版给「每日提醒」做了一半：客户端请求授权、记住时间、发布版里没接通就整块不显示。
但继续做下去没有意义，因为两道墙都不是靠写代码能翻过去的：

| 墙 | 事实 | 后果 |
| --- | --- | --- |
| 通知必须服务端发 | `requestSubscribeMessage` 只完成"用户同意"，真正那条消息要服务端按 openid 调 `subscribeMessage.send` | 没有服务端，用户点了允许也永远收不到 |
| 一次性订阅 = 一次授权发一条 | 长期订阅只对政务、医疗、交通、金融、教育等线下公共服务开放，工具类申请不到 | 「每天提醒」按字面做不到，昨天那条发完就没了 |

所以这一版把整块拿掉：`utils/remind.js` 删除，`pages/me` 的「习惯」分区删除，
连"设置一个不会生效的开关"的机会都不留。要恢复的话在 git 历史里（`git show d43c41d:miniprogram/utils/remind.js`）。

> 这不是"少做一个功能"。一个能点、能设、却永远不会有通知的开关，比没有这个入口更伤——
> 用户会记住"它说会提醒我，但没提醒"。

### 21.2 换成"打开即提醒"：不依赖任何推送

用户打开小程序的那一刻，本来就是他最想记东西的时刻。所以提醒放在那一刻，而不是放在通知栏里：

```
进入首页 → 今天还没记 → 筛选条下面那一栏显示「今天还没记一句 · 记一句 ›」
        → 点一下进记录页（复用底栏「写一句」的同一个入口）
        → 记完返回 → 这一栏自己消失
```

它与已有的两个回顾入口共用同一栏，优先级从高到低：

| 优先级 | 显示内容 | 条件 | 点击去哪 |
| --- | --- | --- | --- |
| 1 | 今天还没记一句 | 有记录、今天还没记、非筛选/非多选 | 记录页（写文字） |
| 2 | 那年今日 | 去年/前年同一天有记录 | 那条详情 |
| 3 | 随便翻一条 · 从 N 条里抽 | 记录 ≥ 2 条、没有那年今日 | 重温页 |
| — | 都不显示 | 一条都没记过 | 空状态本来就在说"想到什么，就说一句"，同一句话不说两遍 |

"三选一"是刻意的：这一栏高度固定，塞两样就会变成两条横幅，把列表往下推。

### 21.3 文案：按"隔了多久"和"连续几天"换，不用同一句天天念

同一句话第二天再看到就开始像催债。所以正文随状态变，标签与动作固定：

| 状态 | 正文 |
| --- | --- |
| 昨天记过、连续 ≥ 2 天 | 连续 N 天了，今天补一句就不断 |
| 昨天记过、连续 1 天 | 昨天那句还热着，今天也留一句 |
| 隔 2–6 天 | 隔了 N 天，随手一句就能接上 |
| 隔 ≥ 7 天 | 隔了 N 天，现在想点什么？ |

三条纪律写在代码注释里，也用测试钉住：

1. **不用催促词**。"应该""必须""坚持"这类词把记录变成作业，测试里直接断言文案不含这些词。
2. **连续天数只在真连续时说**。`streak` 的语义是"今天没记就从昨天往前数"，所以 `streak ≥ 2` 必然意味着昨天记过；写成 `streak >= 2 && gap === 1` 是为了不让这个判断依赖 stats 的实现细节。
3. **隔很久也不吓唬人**。40 天没记就老实说"隔了 40 天"，不写"你已经荒废了一个月"。

### 21.4 判断抽成纯函数 `utils/nudge.js`

页面里只留一句 `nudge.of(stats, { filtering, selecting })`。这么拆的理由很具体：

- **边界只能靠输入驱动**。"今天记过""手机时钟超前写下的未来记录""隔 7 天"这些分支，
  在真机上要造数据才能看到一种，而纯函数在测试里一次跑完十几种；
- **文案要能改**。以后调一句话，改一处 + 跑一次测试就知道有没有碰到边界；
- **页面不该知道"为什么"**。`pages/index` 只负责把"当前在不在筛选/多选"告诉它。

`gap <= 0` 这一条同时覆盖了两件事：今天已经记过，以及手机时钟超前写下的"未来记录"——
后者如果只判 `=== 0`，会天天催一个明明记过的人。
