# 灵感随时记 · 微信小程序（本地存储版）

按《灵感随时记 · 需求分析与产品设计方案 v1.0》落地的可运行工程：原生小程序，无云开发依赖，所有数据落在 `wx.setStorageSync` + 本机用户目录，导入即可跑通「记录 → 浏览 → 查看 → 编辑 → 删除 / 撤销」全链路。

---

## 一、怎么跑起来

1. 微信开发者工具 →「导入项目」→ 目录选本文件夹（`灵感随时记-完整版/`）。
2. AppID 填自己的；没有公众号主体就点「测试号」或「不使用云服务 / 无 AppID」。
   - 工程里预置的是 `touristappid`，仅供无 AppID 预览，正式上传前必须换成自己的。
3. 编译后首屏就是卡片流，点顶部「今天想到什么？」或底部并排的「写一句 / 说一段 / 拍一张」即可记第一条。

> 不需要开通云开发，不需要配置服务器域名，不需要登录。

## 三、数据模型与存储

记录的字段刻意压到最小，够用且不给自己挖坑：

```js
{
  id: 'r1a2b3c4d5e6f',   // 本地主键，时间前缀便于排查
  type: 'text',          // text | voice | photo，一条只允许一种
  content: '',           // 文字正文 / 照片配文 / 语音备注，最多 1000（语音照片 200）
  mediaPath: '',         // 语音/照片的本机持久路径，文字为空
  duration: 0,           // 语音秒数
  size: 0,               // 媒体字节数
  createdAt: 1760000000000,
  updatedAt: 1760000000000,
  deletedAt: 0           // 非 0 即软删，列表与统计都不再计入
}
```

| 存储键 | 内容 | 说明 |
|---|---|---|
| `lg.r.v1.0` … `lg.r.v1.9` | 记录分片，每条按 `id` 哈希落进其中一片 | 单键 1MB 上限不再是瓶颈；改一条只写一片 |
| `lg.schema.v1` | 结构版本，`2` = 分片存储 | 迁移标记。写成功后才落，决定下次还要不要搬 |
| `lg.records.v1` | 老版本的单键记录数组 | **只读一次**：首次启动迁移到分片后删除 |
| `lg.meta.v1` | `{ firstAt }` | 「开始记录」日期 |
| `lg.draft.v1` | 文字草稿 | 300ms 防抖，关掉小程序也不丢 |

> 为什么要分片：微信给**单个 key** 的上限是 1MB，10MB 是整个 Storage 的总量。原来 1000 条全塞一个 key，平均每条 800 字节就撞到单键上限——那时总量才用掉不到一成，用户却已经看到「存不下了」。分片后每片只承担十分之一（实测 1000 条 × 350 字：总量 1231KB，最大片 140KB）。
>
> 为什么按 `id` 哈希、不按下标切片：下标切片在列表中间插入或删除一条时，后面所有记录都要换片，一次改动波及大半分片，写放大比单键还差。按 `id` 哈希则一条记录永远属于同一片，新增/修改/删除通常只写 1 个键。

媒体文件不塞进 Storage（10MB 上限且 base64 会膨胀），统一落在 `wx.env.USER_DATA_PATH` 下，库里只存路径。

## 四、四条核心链路与关键代码

### 1. 创建（`pages/record/record.js` → `onSave`）

- 三种形态共用一页：`type` 切换时若已有内容会二次确认「刚才的X会清掉」，杜绝一条记录混两种形态。
- 文字：`textarea` 自动聚焦、`maxlength=1000`、无标题无分类。
- 语音：默认按住说话（松手即存、上滑 60px 取消），可切换为点击录音；实时计时，60s / 240s 各震一下但**不打断**；到 300s 由 `RecorderManager` 自动收尾。
- 照片：`chooseMedia` → `compressImage` → `saveFile` 落盘，配文可选。
- 保存走「先落库、再返回」，不弹"保存成功"，只在列表里让新卡片闪一次底色（`flashId` → `highlight`）。

```js
const rec = mode === 'edit' ? store.update(id, payload) : store.create(payload)
if (!rec) return                       // 失败已在数据层提示，页面不重复弹窗
this.saved = true
store.clearDraft()
getApp().globalData.flashId = rec.id   // 交给首页做一次性高亮
this.leave()
```

### 2. 浏览（`pages/index/index.js`）

- 吸顶伪输入条：1 次点击进文字态，滚动时不消失（`position: sticky`）。
- 按自然日分组（今天 / 昨天 / 11月3日），首屏 20 条，触底再 +20（`onReachBottom`）。
- 文字超 6 行折叠为「展开」，短句不出现该按钮。
- 下拉刷新用系统回弹，不额外加重试逻辑。

### 3. 查看与编辑

- 卡片点击进 `pages/detail/detail`，展示完整正文、播放录音、大图预览。
- 编辑入口有两处：详情页「改一改」、列表长按「改一改」。都复用 `record?mode=edit&id=`。
- 编辑只改 `content`（语音/照片可换媒体），**`createdAt` 永不变**，所以列表顺序不会因为改一句话而跳动；真的改过才在卡片上标「改过」。

### 4. 删除与撤销

```js
// 数据层：软删，不立刻销毁
function remove(id) { /* deletedAt = Date.now() */ }

// 首页：5 秒倒计时条 + 撤回
deleteItem(item) { store.remove(item.id); this.refresh(); this.showUndo(item.id) }
onUndo() { store.restore(this.pendingDeleteId); this.refresh() }
```

`app.js` 在启动和切后台时跑 `store.purge()`，物理清除超过 24 小时的软删记录，并顺手删掉它们的媒体文件——避免"删了但空间不还"。

| 标签 / 搜索 / 打卡 / 分享 / AI | ⛔ 按 PRD 明确不做 |

### 两处有意偏离，需要你知道

1. **PRD 写"不做编辑"，这个版本做了。** 需求方明确要求"创建、编辑、查看、删除"，所以补上编辑。为不破坏「8 秒记一条」的产品假设，做了三点约束：编辑入口全部下沉到长按与详情页（首屏主路径仍是"写一句就存"）；编辑不改 `createdAt`，列表不跳动；卡片上加「改过」标记，让"修饰过的文字"和"原始捕捉"在视觉上可区分。
2. **记录面板从"半屏升起的 sheet"改成独立页面。** 小程序里页面级 sheet 要自己扛键盘顶起、滚动穿透、返回手势三件事，坑比收益多；当前实现是独立页 + 自绘顶部栏（只剩「取消 / 标题」，保存改到底部主按钮，见第二十四章），键盘弹起行为与 sheet 一致，返回即回列表，观感差别很小。要真做成 overlay，可把 `record` 的 WXML 搬进 `components/record-sheet` 在首页 `wx:if` 弹出，数据层不用动。

## 六、已知限制（写在这里，避免上线后当 bug 排查）

1. **数据只在本机。** 卸载/重装小程序、清理微信存储、换手机都会丢。这是"零后端"的代价，PRD 的 1000 条容量与多端同步都需要服务端。
2. **本机媒体有配额。** `wx.saveFile` 落在用户目录，总量有限（旧版 10MB 量级），照片压缩后约 200–300KB，几十张就会触顶。触顶时 `saveFile` 失败会降级为临时路径，本次会话可见、重启后失效。要长期存图必须上对象存储（PRD 第六节）。
3. **照片/相机需在后台配置「用户隐私保护指引」。** 未配置时真机上 `chooseMedia` 会直接失败（开发者工具里一般不拦）。录音同理需要声明麦克风用途。
4. **回访链路没接。** 第 7 天订阅消息、站内回访卡、回顾页需要云函数 + 定时触发器，工作区里另一份 `灵感随时记-小程序/` 就是那套云开发实现，可作为后续合并的基础。
5. **没有全文搜索。** PRD 把它放在 v1.1（人均 >50 条再做）。当前数据量下靠日期分组翻找更快。

## 八、列表分组、删除与数据搬移（v1.1）

### 8.1 分组规则

按「由近及远」切四个时间桶，命中即止，不做二次细拆：

| 桶 | 判定 | 展示 |
|---|---|---|
| 今天 | 自然日差 ≤ 0（含手机时间超前产生的未来记录） | 卡片平铺，最上面 |
| 本周 | 与本机同一自然周（**周一为起点**），且不是今天 | 堆叠组，折叠 |
| 本月 | 同一自然月，且不在本周 | 堆叠组，折叠 |
| 今年 | 同一年，且不在本月 | 堆叠组，折叠 |
| 往年 | 更早的年份，各年一组，如「2025年」 | 堆叠组，折叠 |

边界说明：上周日不算「本周」而落到「本月」；12 月 31 日与次年 1 月 1 日一定是两个不同的年桶。

实现位置：`utils/date.js` 的 `bucketOf` / `groupBuckets`，纯函数，`now` 可注入，便于验证。

### 8.2 堆叠样式

折叠态用三层卡片边缘错落叠放（`scale` 0.90 / 0.95 / 1.00，透明度 0.45 / 0.72 / 1），最上层露出该组最新一条的角标、时间与一行摘要，右下角标「还有 N 条」。点击组头或整块堆叠即展开为完整卡片列表。

### 8.3 删除的三条路径

| 入口 | 交互 | 保护 |
|---|---|---|
| 单条 | 卡片**向左滑**，露出红色「删了」按钮，点它删除；滑不够距离自动回弹 | 5 秒撤销条 |
| 单条 | 长按卡片 → 菜单里的「删了」 | 5 秒撤销条 |
| 整组 | 组头右侧「删整组」→ 二次确认弹窗（写明分组名与条数） | 5 秒撤销条，撤回可**整组恢复** |

- 同一时刻只允许一条卡片处于左滑打开状态，由页面的 `openSwipeId` 统一调度。
- 删除是软删（打 `deletedAt`），24 小时后才由 `app.js` 的 `purge()` 连媒体文件一起物理清除。
- 批量删除只写一次盘，中途失败不会留下"删了一半"的状态。

### 8.4 换设备：导出 / 导入

入口在「我的 → 换手机」。

**导出**：把所有记录打成一个 JSON。图片和录音无法跨设备引用本地路径，因此读成 base64 内嵌。
- 单条媒体上限 2MB、总计上限 15MB，超出的只迁文字，并在结果弹窗里如实报数量。
- 手机端用 `wx.shareFileMessage` 转发到「文件传输助手」；桌面端用 `wx.saveFileToDisk` 直接存盘。

**导入**：从聊天记录里选那个 `.json`（`wx.chooseMessageFile`），校验文件头 → 还原媒体到新机沙箱 → 按 id 合并。
- **只做新增，不覆盖**：同 id 已存在则跳过，所以反复导入同一份不会产生重复，也不会冲掉新手机上刚记的内容。
- 导入后会自动把「开始记录」时间修正到更早的那条。

实现位置：`utils/transfer.js`（打包/解包）+ `utils/store.js`（`importRecords` / `removeMany` / `restoreMany`）。

## 九、检索、回顾与输入增强（v1.2）

### 9.1 数据结构的变化

记录从「单一媒体」升级为「一组媒体 + 三个新字段」：

| 字段 | 含义 |
|---|---|
| `mediaPaths: string[]` | 照片最多 9 张；语音仍只用 `mediaPath` |
| `tags: string[]` | 从正文里的 `#标签` 自动解析，最多 8 个 |
| `starred: 0\|1` | 星标，钉在「星标」筛选里 |
| `archivedAt: number` | 非 0 表示已归档，不进主列表但不算删除 |

老数据不需要迁移：`store.js` 的 `normalizeRecord()` 在读取时补齐这四个字段，`mediaPath` 会自动升级成 `mediaPaths: [mediaPath]`。

### 9.2 标签怎么写

正文里直接写 `#读书`、`#产品想法`，保存时自动归好，列表卡片上会显示前 3 个。
标签字符集：中英文数字，遇空格或 `，。！？、` 等标点即止，单个标签最长 12 字。

### 9.3 五个新入口

| 位置 | 作用 |
|---|---|
| 首页顶部放大镜 | 进搜索页：全文搜索 + 标签快捷筛选 + 命中高亮 |
| 首页筛选条 | 全部 / 星标 / 归档 / 单标签，四个维度互斥切换 |
| 首页「那年今日」卡 | 自动出现去年或前年同一天的那条，点开看全文 |
| 我的 → 随便翻一条 | 随机重温，偏向 7 天以上的旧记录，可加星、转发 |
| 首页顶部「从聊天存」 | 从微信聊天里选文件/图片，直接存成灵感（v1.6 从「我的」迁来） |

### 9.4 长图分享

卡片长按 → 「做成图」，或详情页 → 「做成图」。
`utils/poster.js` 用 Canvas 2D 排版：750 宽、高度按内容算、正文最多 26 行、带标签与页脚。
生成后可保存到相册，或走 `wx.showShareImageMenu` 直接发给朋友。

两个技术点值得记一笔：

- canvas 2d 每次改 `width/height` 都会重置上下文，所以必须「先量高 → 再定尺寸 → 再绘制」，量的时候用临时高度。
- `drawImage` 只吃 `canvas.createImage()` 出来的 Image 对象，喂路径字符串画不出来，因此 `poster.loadImage(canvas, src)` 必须先取尺寸再等 `onload`。

### 9.5 转发与接收

所有页面的转发都会带一段正文进去：`/pages/index/index?inbox=<encodeURIComponent(正文前 400 字)>`。
接收方打开小程序会看到「收到一条分享」，确认后存成自己的一条本地记录——因为数据本来就只在本机，跨设备只能靠"把内容带过去"，不能靠同步。

### 9.6 语音转文字：说清楚边界

小程序没有「给一个音频文件、还一段文字」的能力。真正可用的只有微信同声传译插件（`WechatSI`），而它是**边录边转**、不能事后转写。

所以这里的实现分两层：

- **默认可用的**：语音记录下方就是文字备注框；详情页对没有文字的语音/照片提供「补一句文字」。补上之后这条就能被搜索命中，这是"语音可检索"的实际达成路径。
- **需要额外两步的**：`utils/asr.js` 里把 `USE_PLUGIN` 改成 `true`，并在 `app.json` 增加 `plugins` 声明、在小程序后台添加该插件。启用后录音会边录边出字，最终文字直接写进正文。未启用时按钮不会出现，不会出现"点了没反应"。

### 9.7 每日提醒：只做了能做的那一半

> **本节已作废（v1.7.4）。** 一次性订阅一次授权只能发一条，工具类小程序申请不到长期订阅，
> 「每日提醒」按字面意义做不到，已整体下掉，改成首页的「今天还没记一句」。见第二十一章。

订阅消息必须由**服务端**下发。客户端能做的只有「请求授权 + 记住时间」，真正到点弹出通知要靠自建服务端或云函数按 openid 发送。

因此：

- `utils/remind.js` 顶部留了 `TMPL_ID`，填上小程序后台创建的模板 ID 才会真正请求授权；
- 没填时，点「每日提醒」会如实说明还差一步，并把时间偏好记下来；
- 我的页的「提醒时间」可以正常选，选完会持久化，等模板配好就生效。

## 十、多图错落堆叠（v1.3）

### 10.1 长什么样

一条记录带 2 张及以上照片时，卡片里不再只显示第一张 + 一个「N 张」角标，而是把照片按「散落的相纸」铺开：

- 每张照片带 10rpx 白边、18rpx 圆角、两层投影，像一叠实体照片；
- 位置、旋转（-9°～+6°）、层级各不相同，前一张压住后一张的边角；
- 2 张是「一前一后、右下压角」，3 张是「中间落底、上下错开」，4 张是「铺满整块、层层压边」；
- 超过 4 张只铺 4 张，最上面那张角标 `+N`，总张数看卡片左上角的「照片 N 张」；
- 点哪张就从哪张开始全屏预览（`previewImage` 的 `current` 跟着走）。
- 这套坐标后来抽到了 `utils/stack.js`，「做成图」的长图也用同一份数字（见第二十五章）。

### 10.2 为什么不会抖

| 做法 | 解决什么 |
| --- | --- |
| 照片框尺寸、坐标、容器高度全部用固定 `rpx`，写死在 `buildStack()` 里 | 图片加载前后盒子尺寸不变，列表不会因为解码完成而跳动 |
| 容器高度按本组最底边收口（`stackH`），而不是固定一个数 | 2/3/4 张的图组下方留白一致，卡片节奏整齐 |
| 旋转角度额外算进包围盒（`sin(θ) * FRAME_W / 2`） | 斜着的照片不会压到下面的正文 |
| 堆叠位次用记录 `id` 做散列抖动（±5rpx、±1.2°） | 同一张卡片每次渲染位置一致；不同卡片不雷同，翻列表不会「全军整齐」 |
| 图片 `mode="aspectFill"` + 相纸底色占位 | 任意长宽比的照片都填满相框，未加载时是米色纸面而不是白洞 |

### 10.3 适配

全部尺寸走 `rpx`，屏幕变宽整组等比放大：手机 375pt 下相框约 165×127pt，桌面端（微信 PC 大窗口）同步放大，不会出现「手机好看、电脑散架」。没有用 `vh/vw`、没有用 `media query` 打补丁，换机型不需要再调。

## 十一、统一对话框（v1.4）

### 11.1 为什么不用 wx.showModal

系统弹窗的遮罩是黑色半透明、标题正文用系统字重，在暖白纸感界面里像贴了个外来件；更实际的问题是它只能改一个 `confirmColor`，**危险态和加载态做不出来**——"清空全部"和"从备份导入"长得一模一样，用户只能靠读字区分。

所以自绘一个，视觉只用 `app.wxss` 里的 token，不新增色号。

### 11.2 怎么用

页面挂一次，然后命令式调用，Promise 风格：

```html
<dialog-view />
```

```js
const dialog = require('../../utils/dialog')

dialog.alert({ title: '导出完成', text: '共 42 条' })

dialog.confirm({ title: '清空全部灵感？', text: '共 42 条，找不回来。', danger: true })
  .then(r => { if (r.confirmed) store.clearAll() })

// 异步确认：hook 返回 Promise 时自动进 loading，resolve(false) 留在原地
dialog.show({
  title: '导入备份',
  onConfirm: () => transfer.importBackup().then(r => { done(r); return true })
})
```

`utils/dialog.js` 维护一个实例栈（页面返回时上层自动出栈），**没有实例时退回 `wx.showModal`**——`store.js` 这种数据层在 App 启动阶段报"存不下了"也不会因为 UI 没挂载而静默丢失提示。

### 11.3 视觉规范（唯一基准：app.wxss）

| 项 | 取值 | 与现有组件的关系 |
| --- | --- | --- |

| 状态 | 触发 | 表现 | 实现 |

## 十二、"本机占用 2 KB / 10240 KB"到底在说什么

### 12.1 两个账本，别混着看

| 账本 | 存在哪 | 上限 | 装什么 |
| --- | --- | --- | --- |
| **键值存储** | `wx.setStorageSync` | **10240 KB = 10 MB**（`wx.getStorageInfoSync().limitSize`） | 记录数组、偏好、草稿、元信息，全是 JSON 文本 |
| **本地文件** | `wx.env.USER_DATA_PATH` | 约 **200 MB**（平台配额，非本 API 返回） | 照片、录音文件 |

所以截图里的 `2 KB / 10240 KB` 是**第一本账**：这个用户的全部记录索引只用了 2 KB，占 10 MB 的 0.02%。照片和录音不在这 2 KB 里，它们在第二本账里单独计。

这也解释了一个常见误会："我拍了 50 张照片，为什么占用还是 2 KB？"——因为存的是路径字符串，不是图片本身。

### 12.2 超过 10240 KB 会发生什么

1. `wx.setStorageSync` **抛异常**（`setStorage:fail exceed storage max size` / `errno` 相关），不是静默失败。
2. `store.js` 的 `writeAll()` 捕获异常 → 把内存缓存置空 → 弹「存不下了」→ 返回 `false`。
3. **已有数据不会丢**：写失败意味着旧值原样保留，丢的是这一次的新记录。
4. 不会自动清理、不会自动扩容、不会降级到别处。下次再写仍然失败。
5. 同一份存储里其它 key（偏好、草稿）也可能一起写失败。

正常情况下**碰不到 10 MB**：`MAX_RECORDS = 1000`，一条纯文本记录连字段带标签约 200–400 字节，1000 条也就 200–400 KB；就算每条都写满 1000 字，也在 2 MB 量级。真正先到的上限是"1000 条"，不是 10 MB。

### 12.3 该怎么处理

- **产品侧**（已做）：`我的` 页拆成两行——「记录索引 2 KB / 10 MB（已用 <1%）」和「图片与录音 12.4 MB · 36 个」，点任意一行弹出说明，讲清两本账。
- **预警**：索引 ≥80% 或文件 ≥150 MB 时，页面顶部出现赭色提示条，引导"先导出再清理"。
- **写入失败**：只提示、不静默丢弃；用户可以先 `导出到文件`，再清空或删旧记录。
- **媒体失败**：`saveFile` 失败会降级成临时路径（本次会话可见、重启失效），已在 `utils/media.js` 里如实提示，不假装存住了。

### 12.4 这些限制要知道

1. `currentSize` 统计的是**这个小程序**在该用户设备上的全部 key，不区分是记录还是别的；换账号/换设备不共享。
2. 用户清微信缓存、卸载小程序，存储会没——**导出是唯一保险**。
3. 10 MB 是平台给的，客户端不能申请扩容；想突破只能把大块数据挪到文件或云端。
4. 文件配额（约 200 MB）也没有官方 API 能查"还剩多少"，只能用 `statSync` 自己累加（`store.usage()` 就是这么做的，成本 O(文件数)，只在"我的"页调用）。
5. 录音、照片的元数据（时长、宽高）存在 JSON 里，文件被系统清掉后记录会"有壳没内容"，所以删除记录时同步 `unlink`，避免僵尸条目。

## 十四、缩略图网格与语音列表（v1.5）

### 14.1 照片：按张数分列，不写断点

原来的重温页遇到照片只显示一句"这条是照片，去详情里看"，卡片里是一大片空白。现在照片直接铺成缩略图：

| 张数 | 排布 | 格子比例 | 说明 |
| --- | --- | --- | --- |
| 1 张 | 整幅 | 3:2 裁切 | 一张不值得切碎，铺满更好看 |
| 2 张 | 两列一行 | 4:3 | 并排两张，比上下两张更像"一组" |
| 3 张 | 三列一行 | 1:1 | 一行放下，不留孤儿 |
| 4 张 | 2×2 | 4:3 | 比"三列 + 落单一张"整齐 |
| 5–9 张 | 三列九宫格 | 1:1 | 行数随张数增减 |
| 10 张以上 | 九宫格 + 折叠 | 1:1 | 只铺 9 张，第 9 张右下角 `+N` |

规则只看张数，不看屏宽——列数是内容决定的，屏幕只决定格子多大。

### 14.2 为什么加载不跳、两端都不散

| 做法 | 解决什么 |
| --- | --- |
| 格子宽度用百分比（50% / 33.33%），高度用 `padding-top` 百分比撑 | 高度是宽度的函数，图片解码前后盒子尺寸一致，列表不跳 |
| 图片绝对定位铺满格子 + `mode="aspectFill"` | 任意长宽比都填满，不留白边、不撑破格子 |
| `lazy-load`（前三张除外，首屏要快） | 长列表滚动时不一次性解码几十张图 |
| 加载时 0.18s 淡入 + 米色纸底占位 | 慢网下是"纸面渐显"，不是白洞闪一下 |
| `binderror` 换占位块 | 文件被系统清掉时不显示裂图 |
| 全部尺寸走 rpx + 百分比，没有 `vw`、没有 media query | 手机 375pt 与桌面大窗口是同一套规则，等比放大 |

点哪张就从哪张开始 `previewImage`，索引跟着 `data-i` 走。

### 14.3 语音：可以，而且就按列表做

录音完全可以在页面里以列表呈现，一条音频一行，行内自带播放键、进度条、状态与时长：

```
┌─────────────────────────────────────────┐
│ (▶)  ▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬         │
│      点一下听                      0:08 │
└─────────────────────────────────────────┘
```

- **一行一音频**：`voices` 是数组，现在一条记录只存一段录音所以只有一行；将来支持多段时，模板不用改，往数组里多推几个对象就是列表。
- **三态**：闲置（空心三角 + "点一下听"）、播放中（暂停图标 + 进度填充 + "正在播放"）、暂停（保留进度 + "已暂停，点一下接着听"）。
- **进度**：`InnerAudioContext.onTimeUpdate` 每 250ms 触发，只在整秒变化时 `setData`，避免白渲染；时长优先用播放器回调的 `duration`，取不到就退回记录里存的秒数。
- **互斥**：全局单例播放器，点第二条会自动停掉第一条，不会两条一起响。
- **离开就静音**：`onHide` 停播、`onUnload` 释放，重温是"看一眼"，不该带着声音走出页面。

### 14.4 适配方案

| 场景 | 处理 |
| --- | --- |
| 手机窄屏 | 行高固定 116rpx，进度条弹性伸缩（`flex:1`），横竖屏都不挤 |
| 桌面大窗口 | 行随卡片变宽，进度条按比例变长，文字与时长始终贴两端 |
| 超长文案 | 状态文案用短句（"正在播放"），超长不会把时长挤出去（`justify-content: space-between` + `min-width:0`） |
| 无障碍 | 整行都是点击热区（≥88rpx），不要求点中 40rpx 的三角形 |

### 15.2 迁移后：首页顶部，一眼能看到

```
┌──────────────────────────────────────────┐
│ 我的灵感  42 条        从聊天存  多选  我的 │
│ ┌──────────────────────────────┐  ┌───┐  │
│ │ 今天想到什么？              ✎ │  │ 🔍 │  │
```

- **为什么放头部而不是底部三入口**：底部「写一句 / 说一段 / 拍一张」是"就地产生内容"，是上一轮特意定的三等分，加第四个会把那个节奏打散；「从聊天存」是**把别处的东西收进来**，属于另一个心智，放导航同级更合适。

- **空态补了一条文字链**：「或从聊天里存一条 →」，新用户一条都没有时也能找到这个入口，且不跟主按钮「记下第一条」抢。
- **行为不变**：同一个 `transfer.importFromChat()`、同一个"处理中"遮罩、同一套成功/失败文案、取消不报错。

### 15.3 顺手修掉的一个真问题

迁过来读代码时发现：原来的 `importFromChat()` 只把文件解析成 `{type, content, mediaPaths}` 的**草稿**并 resolve，`me.js` 拿到后直接弹「已存下 N 条」——**从头到尾没有调用 `store.create()`，什么都没落库**。也就是说旧版本上点这个入口，看到"已存下"但列表里什么都不会出现。

现在补上真正的写入：逐条 `store.create()`，成功几条就报几条；因为满 1000 条或落库失败而没进去的，如实补一句「有 N 条没存下，可能已经满 1000 条了」。存完切回「全部」筛选、刷新列表，并让最上面那条闪一下。

### 15.4 左右翻：抽样规则只有一份

新增 `utils/flip.js`，把「下一条是谁」这件事从页面里抽出来：

| 函数 | 语义 |
| --- | --- |
| `enter(id)` | 进详情时对齐"当前这一条"。从重温页进来，栈顶正好是它，于是接着用那一轮历史；从列表/搜索点进来则重开一轮 |
| `next()` | 栈里还有"前一条"就先走回去（右滑过之后能原路返回），走到头再按**重温页原来的规则**抽：排除当前、优先 7 天以上、随机 |
| `prev()` | 先回退这一轮看过的；本轮到头时按时间接一条更早的，并把历史补在左边，所以再左滑能回到刚才那条 |
| `canPrev()` | 还能不能往回翻，决定"上一条"是否置灰 |
| `total()` | 记录总数，决定要不要显示翻页条 |

`pages/review` 的「再来一条」也改成走这里（`flip.enter(当前) → flip.next()`），所以**详情页左滑和重温页再来一条拿的是同一套抽样、同一条历史**，不会出现"重温页刚看过的那条，详情页左滑又抽到"之外的两套口径。

手势本身：

| 项 | 取值 | 为什么 |
| --- | --- | --- |
| 方向判定 | 前 10px 不判向，之后 `|dx| > |dy| × 1.2` 才接管 | 手指按下的抖动不会把纵向滚动抢成翻页 |
| 触发阈值 | 横向 56px | 小于这个距离当"手抖"，滑回原位 |
| 跟手 | `dx × 0.4`，上限 96px | 有阻尼、拖不飞；到头了（没上一条/只有一条）阻力加大到 0.12 |
| 换场 | 先 0.14s 滑出 → 换内容并摆到另一侧 → 0.18s 滑回 | 有"换了一张"的连续感，不是硬切 |
| 兜底 | 页面底部「‹ 上一条 / 左右滑也能翻 / 下一条 ›」 | PC 端用鼠标滑不动，箭头补上；箭头和手势调的是同一个 `go(dir)` |

**换条时状态怎么复位**（这就是"与原翻页逻辑一致"的落点）：

1. `audio.stop()` 且 `playing: false` —— 上一条的录音不会跟着新内容继续响；
2. 复用 `load()` 重新读库 —— 类型、时间、照片、星标、归档、`needText` 全部由同一段代码算，不另写一份；
3. `wx.pageScrollTo({scrollTop: 0})` —— 新的一条从页首看起；
4. `swipeDx` 归零、`_switching` 解锁 —— 连滑不会叠出两条记录。

## 十六、重温页左右滑修复（v1.6.1）

### 16.1 现象

在「重温 → 随便翻一条」页面上左滑、右滑都没有反应，内容不换，纸也不动。

### 16.2 根因：手势绑错了页面

上一版（第十五章）只在 `pages/detail` 的根节点上挂了三个事件，**重温页一行都没绑**：

| 位置 | 上一版状态 | 结果 |
| --- | --- | --- |
| `pages/detail/detail.wxml` | 根节点 `bindtouchstart/move/end` + `swipeDx` 位移 | 详情页可滑 |
| `pages/review/review.wxml` | 无任何 touch 事件，`.paper` 上无 `transform` | 滑了等于没滑 |
| `pages/review/review.js` | 只有一个 `pick(false)` 的「再来一条」入口，没有方向 | 即使绑了也无从分「上一条 / 下一条」 |
| `utils/flip.js` → `pool()` | `rest` 为空时退回全量（含自己） | 库里只有一条时 `next()` 把当前这条再发一次，表现为「滑了但没变化」 |

「再来一条」和「滑一下」是两种取数意图，而 `pick()` 把**取数**和**渲染**揉在一个方法里，
手势拿到的条目没法交给它（再调一次 `flip.next()` 会抽成另一条），所以也无法用一个入口硬接。

### 16.3 改法

1. **拆开取数与渲染**：`pick()` 只负责「对齐栈顶 → 取一条」，新的 `show(item, buzz)` 只负责铺到纸上。
   手势从 `flip` 取到条目后直接 `show()`，不再二次取数，因此"用户滑到的那条"与"渲染出来的那条"必然同一条。
2. **手势挂到 `.page` 根节点**（与详情页同一套算法）：手指落在纸、缩略图、语音行、按钮上都算，
   位移只作用在 `.paper` 上（标题与按钮不动，像把一张卡抽走），`will-change: transform` 交给合成层。
3. **方向语义**：左滑 `go(1)` → `flip.next()`；右滑 `go(-1)` → `flip.prev()`。
   与「再来一条」共用 `flip`，所以两处的"下一条是谁"永远一致。
4. **`pool()` 不再回退到含自己的全量**，只有一条时如实返回 `[]`；同时新增 `flip.only()`
   兜住"首次进页面但库里只有一条"——没别的可翻，这一条本身还是要给他看。
5. 顶部副标题从「从 5 条里抽的」改成「左右滑能翻 · 共 5 条」，把刚加的手势讲出来（只有一条时显示「就这一条」）。
6. `onUnload` 清掉动画定时器；`onShow` 同步 `total / canPrev`（从详情页删了记录返回时数字不再过期）。

### 16.4 首尾边界规则（与详情页一致）

| 情形 | 左滑（下一条） | 右滑（上一条） |
| --- | --- | --- |
| 库里 ≥ 2 条，位置居中 | 换（先走回看过的，再按 7 天以上随机抽） | 换（先回退本轮看过的，再到头按时间往前接） |
| 库里只有 1 条 | 不换，阻力 0.12 回弹，**不弹提示** | 同左 |
| 已在最早一条 | 正常前进 | 不换，阻力 0.12 回弹，提示「已经是最早的一条了」 |
| 本轮历史到头但还有更早的 | 正常前进 | 按时间接一条更早的，并补在栈底（再左滑能原路回来） |
| 拖动 < 56px | 回弹、不换条 | 回弹、不换条 |
| 纵向拖动 | 不接管，交给 `scroll-view` 滚正文 | 同左 |

## 十七、从聊天存文字 + 首页回顾位（v1.7.0）

### 17.1 为什么是"剪贴板"，而不是"读聊天"

先把平台边界写死，免得以后反复讨论：

| 想拿到 | 有没有接口 | 说明 |
| --- | --- | --- |
| 聊天里的图片 / 文件 | `wx.chooseMessageFile` | 只能给**文件**，返回临时路径 |
| 聊天里直接打的文字 | **没有** | 文字不是文件，永远不出现在选择器里 |
| 聊天语音消息 | **没有** | 同上 |
| 聊天记录 / 会话列表 | **没有** | 不存在 `getChatHistory`、`onMessage` 之类接口，与企业资质无关 |
| 别人转发进来的文字 | `onShareAppMessage` 的 path query | 需要发送方主动写进 path |
| 用户自己复制的文字 | `wx.getClipboardData` | 剪贴板属隐私接口 |

所以"保存文字"唯一合法、且用户可理解的通路是：**在聊天里长按复制 → 回到小程序点一下**。
`utils/transfer.js` 的 `fromClipboard()` 就是这一段的唯一出口。

两条硬约束写在实现里：

1. **绝不自动读**。读剪贴板在 iOS 上会弹系统提示，偷偷读会让人觉得被监视；
   必须由用户点「粘贴刚复制的文字」才触发。
2. **超长不静默丢字**。一条最多 1000 字（`transfer.MAX_TEXT`，与记录页 `maxlength` 一致），
   超出时弹窗如实说"这段有 N 字，先收了前 1000 字"，而不是悄悄截掉。

### 17.2 一个入口，两种来源

「从聊天存」不再直接拉文件选择器，改成先弹 `action-sheet`（复用现有组件），两项：

| 选项 | 走什么 | 结果 |
| --- | --- | --- |
| 选图片 / 文件 | `transfer.importFromChat()` | 图片→照片记录；txt/md/csv→文字记录；其它二进制只留文件名并计入 failed |
| 粘贴刚复制的文字 | `transfer.fromClipboard()` | 一条文字记录，失败按 `empty / denied / unsupported / read` 分别提示 |

为什么不新增一个「粘贴」按钮：首页顶部那排已经有「从聊天存 / 多选 / 我的」三个，
再加会挤；而"收进来"本来就是一件事，用一次弹层分叉比多个图标更省地方。

### 17.3 回顾位：从「我的」第 4 屏搬到首页

**判断依据**（「随便翻一条」不属于高频操作）：

- 池子优先取 7 天以上的记录 → 新用户前 7 天抽不出东西，价值随库龄增长；
- 没有推送、角标、红点，只能靠"想起来"；
- 在原位置需要 3 次点击，中间隔着统计大数字、14 周热力图、统计块；
- 不解决任何任务（不帮你找、不帮你写），是消费型/惊喜型功能，通常周级。

**但低频 ≠ 该藏起来**。它承担的是留存与情感价值，要的是"入口浅、不占主位"。

**做法**：复用已有的一栏——筛选条下方「那年今日」的位置。

```
有那年今日  → 照旧显示那年今日（点击进详情）          优先级最高，不动
没有        → 显示「随便翻一条 · 从 N 条里抽 ›」      点击进 review
一条都没有  → 都不显示
```

同时 `pages/me` 的「回顾 → 随便翻一条」整行删除（分区标题从「回顾」改成「整理」，只留归档），
保证**唯一入口**——双入口会让两边都变弱。

`reviewTotal` 用 `flip.total()` 算，与重温页口径完全一致（含归档），
所以首页写的"N 条"和进去后副标题的"N 条"永远是同一个数。

### 17.4 分享 path：400 字改 120 字

原来三处都是 `encodeURIComponent(text.slice(0, 400))`。中文经 `encodeURIComponent`
一个字膨胀成 9 个字符，400 字≈3600 字符的 path，超过微信路径上限会被截断在 `%XX` 中间，
接收端 `decodeURIComponent` 抛错，正文就变成一串 `%E4%BB%8A`。

现在统一走 `utils/share.js` 的 `card(text)`：压空白 → 截 120 字（≈1080 字符）→ 拼 path，
标题取前 30 字。首页、详情页、重温页三处共用，不会再各写一份。

## 十八、聊天图片压缩落盘（v1.7.1）

### 18.1 问题：从聊天收进来的图是原图

`transfer.importFromChat()` 的图片分支原来调 `media.saveFile(f.path, ext)`，
这是「原样搬进沙箱」——**不压缩、不缩边、不改格式**。而相册/相机那条链路走的是
`saveImage()` → `compress()`，早就压到 300KB 以内了。同一个产品里两条导入路径待遇不同。

实际后果很直接：手机截图 1~3MB，手机照片 4~10MB，从聊天里选 9 张进来能吃掉 30~60MB。
本机文件空间是 200MB 量级，几十张原图就顶掉几千条文字记录——这是当前最容易被忽略的"存储漏水点"。

### 18.2 改法：新增 `media.saveChatImage()`，两级压缩

```
原图（例如 4000×3000，5MB）
  ↓ 第 1 轮：缩小到长边 1280 + 质量 70
200~300KB 左右
  ↓ 若仍 > 300KB：只降质量到 45 再来一轮（不再缩边）
通常 < 150KB
  ↓ 仍压不动：交原件，绝不为了省空间把图弄丢
```

第 1 轮就同时给 `compressedWidth / compressedHeight`，而不是只给 `quality`——
只降质量对 4000px 的大图效果有限（尺寸才是体积的主因），先把长边压到 1280 才是关键。
宽高按原图比例算，短边不裁切、不变形。

### 18.3 为什么不直接复用 `saveFile` 或 `saveImage`

| 候选 | 为什么不行 |
| --- | --- |
| `saveFile` | 原名原图搬进去，正是要修的问题 |
| `saveImage` | 只有 `quality: 70`，无长边控制；且无法告知"原始体积 / 省了多少" |
| 在 `transfer.js` 里现写一遍 | 压缩逻辑会分裂成两份，以后调整阈值必然漏掉一处 |

现在 `compress()` 也升级为「先取尺寸、再决定是否缩边」，所以相册链路同样受益；
`saveImage` / `saveImages` 签名不变，`record` 页不用改。

### 18.4 四条边界，都写进实现里了

1. **gif 不压**。压缩会把动图变成一张静图——宁可多占点空间，也不悄悄改掉这个东西的性质。
2. **老基础库不认宽高参数**（`compressedWidth/Height` 需 2.26.0+）时，`compressImage` 会直接 fail。
   实现里捕获这次失败，退回"只给质量"再压一次，而不是把图丢掉。
3. **压不动就交原件**：没有 `wx.compressImage`、两轮都失败、或压缩后反而更大，都保留原文件。
4. **原始体积优先用选择器报的 `f.size`**，拿不到才现场 `statSync`，避免多一次 IO。

`importFromChat()` 的返回值多两个字段：`compressed`（压了几张）与 `savedBytes`（省了多少字节），
首页弹窗因此能具体说"3 张照片压到 300KB 以内，省下 12.4 MB"，而不是一句模糊的"已优化"。

### 18.5 预期效果

| 来源 | 原始 | 落盘 | 变化 |
| --- | --- | --- | --- |
| 手机截图（1290×2796） | 1.8 MB | ~200 KB | 省 89% |
| 手机照片（4000×3000） | 5.2 MB | ~240 KB | 省 95% |
| 微信转发的小图（800×600） | 90 KB | 不再压（长边 < 1280，体积已达标） | 不变 |
| 表情 gif | 900 KB | 900 KB | 不压（保动图） |

9 张照片一次性导入：原来 45MB 左右，现在 2MB 出头。

## 十九、竖向留白归位 + 文案去代码化（v1.7.2）

### 19.1 两页的空白，不是"感觉空"，是三个写法凑出来的

**详情页（这一条）**

```
.page { min-height: 100vh; padding: 32rpx 40rpx calc(120rpx + safe); }
```

- `min-height: 100vh` 但**没有任何 flex 分配**：内容少时，剩余空间全部堆在最后一个元素之后，也就是页尾。
- `padding-bottom: 120rpx` 本来是为了别贴着系统手势条，实际变成了"再叠一层留白"。
- 三段操作（5 个按钮 / 发给朋友 / 翻页条）各占一行，`margin-top` 又给了 64/16/40rpx，
  内容只有两行字，操作区却撑到 300rpx 以上——主次是反的。

实测：两行字的记录，翻页条之后到屏底还有约 210px 什么都没有。

**重温页（随便翻一条）**

```css
.paper { flex: 1; max-height: 62vh; }
.body  { flex: 1; max-height: 46vh; }
```

- `flex: 1` 是"必须占满"：纸被拉到 62vh，正文区又被拉到 46vh，
  内容只有一张图时，图下面自然多出一大块白（约 150px）。
- 纸有 `max-height` 上限，`.page` 的剩余空间没人接住，又堆到页尾（约 150px）。
- `.foot`（时间）`text-align: right` 贴着纸底，与照片隔着一整片空白，看起来像"忘了填内容"。

### 19.2 改法：空白必须有归属

| 位置 | 改前 | 改后 | 为什么 |
| --- | --- | --- | --- |
| 详情页 `.page` | 无 flex，页尾吃空白 | `display:flex; flex-direction:column` | 剩余空间才有"归谁"的余地 |
| 详情页结构 | 内容与操作并列 | `.main`（贴顶）+ `.bottom`（`margin-top:auto`） | 内容少 → 操作条贴底，底部有锚点 |
| `.bottom` | 无边界 | 1rpx 淡线上边框 + 32rpx 内距 | 那片空白变成"内容下方留白"，被线封口，不再像页面没做完 |
| 详情页 `padding-bottom` | `120rpx + safe` | `24rpx + safe` | 安全区不该兼职留白 |
| 页内间距 | meta 56 / actions 64 / flipbar 40+32 | 40 / 0（由 bottom 承担）/ 24+24 | 收紧竖向节奏，把高度让给内容 |
| 重温页 `.paper` | `flex:1; max-height:62vh` | `flex:0 0 auto; min-height:42vh; max-height:62vh` | 高度跟内容走；42vh 保证单张图时仍像"一张纸"，不会缩成一条 |
| 重温页 `.body` | `flex:1` | `flex:0 1 auto; min-height:0; max-height:46vh` | 短内容不撑高，长内容仍在上限内滚动 |
| 重温页 `.ops` | 紧跟卡片 | `margin-top:auto` | 按钮贴底，空白收在纸与按钮之间 |

改后：详情页底部留白从 ~210px 降到 ~30px；重温页纸内空白消失（时间紧跟照片），
纸下空白从"纸内 150 + 纸下 150"合并为"纸与按钮之间一段"。

### 19.3 弹窗的问题：一段讲配置的话出现在了用户面前

原文案（v1.7.1）：

> **还差一步**
> 每日提醒要靠微信订阅消息，需要先在小程序后台创建模板，把模板 ID 填进 utils/remind.js。
> 现在可以先把想被提醒的时间记下来。
> ［算了］［选时间］

四个问题，性质不同：

1. **混入代码**：`utils/remind.js` 是源码路径，`模板 ID` 是后台术语。用户不但看不懂，
   而且这件事他根本做不到——那是开发者在自己机器上改文件。
2. **责任错位**："还差一步"暗示用户少做了一步，实际是功能还没接通。
3. **伪承诺**：点「选时间」会走 `pickTime()`，而它只弹一句 toast「点右侧时间设置」——
   按钮承诺了一个不会发生的跳转，是最容易让人失去信任的那类交互。
4. **状态与文案不一致**：选完时间后 toast 说「记下了 21:00」，
   但开关仍是关的；用户会以为"提醒已经设成 21 点了"，到了点却没有通知。

### 19.4 上线发布时怎么处理

**原则：没接通的能力，不进发布包的用户可见路径。**
不是"写一段说明告诉用户为什么用不了"，而是"用不了就不出现"。

具体三层：

| 层 | 做法 | 代码 |
| --- | --- | --- |
| 版本门控 | 发布版（`envVersion === 'release'`）且未配模板 → 整块（含「习惯」标题）不渲染；开发版/体验版照常显示，方便联调和评审 | `utils/remind.js` 的 `visible()` / `status().visible`，`pages/me/me.wxml` 用 `wx:if="{{remindShow}}"` 包住 |
| 上线前置检查 | 发布前必须确认：① 后台已申请订阅消息模板并填好 `TMPL_ID`；② 隐私保护指引已勾选剪切板/相册；③ 真机走一遍"开启→到点收到通知"。三者缺一，提醒入口在发布版里自动消失 | 人工 checklist |
| 文案守卫 | UI 文案里出现 `utils/`、`.js`、`模板 ID`、`小程序后台`、`openid` 直接判失败 | `tools/design-lint.js` 第 6 条 |

第 6 条 lint 只扫"会被念给用户听"的地方：`dialog.alert/confirm` 的实参块，
以及命名以 `_ERR / _TEXT / _COPY / _MSG / _TIP` 结尾的文案常量对象。
不全文扫——源码注释里出现的真实路径是给开发者看的，不该报错。

### 19.5 面向用户的写法：三条规则

1. **说"现在能做什么"，不说"你需要去配什么"**
   改后文案：「提醒还没开通 / 每日提醒要用微信的订阅消息，还差最后一步才能真的发出通知。
   可以先把时间选好，开通后就会按这个点提醒你。」——不出现模板、后台、文件名。
2. **按钮的动词必须真的会发生**
   删掉「选时间」这个伪动作，改成单按钮「知道了」；时间就在下面那行，想选随时可点。
   `pickTime()` 一并删除。
3. **状态与文案必须对齐**
   行副标题与右侧值做成三态一致：`未开通 / 未开通`、`还没开 / 关`、`到点提醒你记一条 / 已开`。
   时间 toast 也分开说：已开通时「提醒时间改成 21:00」，未开通时「记下 21:00，开通后按点提醒」。

## 二十、聊天文件认不出类型导致"没存成"（v1.7.3）

### 20.1 现象

从聊天里选文件，弹「没读成 / 文件读不出来，可能已经损坏」，一个都没存下。
列表里还躺着一条正文为「来自「78a4bca059cff70d66e6b33621a75d18_26439…」」的记录。

两件事同源：**程序没认出这个文件是什么，就用最保守的方式处理了它**。

### 20.2 根因：三个问题叠在一起

**① 只按路径猜后缀。** `extOf(f.path)` 要求路径以 `.jpg` 这样结尾：

```js
function extOf(path) {
  const m = /\.([a-zA-Z0-9]+)$/.exec(path || '')
  return m ? m[1].toLowerCase() : 'dat'
}
```

而 `wx.chooseMessageFile` 给的 `tempFilePath` 经常**没有扩展名**：

| 平台 | 典型 tempFilePath |
| --- | --- |
| iOS | `wxfile://tmp_9f8a7b2c` |
| 安卓 | `http://tmp/xxx` |
| 带参数 | `wxfile://tmp_abc.jpg?size=1024`（这个连正则都匹配不上） |

于是截图被判成 `dat`，既不是图片也不是文本，直接掉进"二进制"分支。

**② 二进制分支写了一条没用的记录。** 原逻辑为了"至少留点东西"，把文件名写进正文：

```js
body = '来自「' + name + '」'
```

而 `f.name` 在某些场景就是那串哈希。结果列表里多出一条谁也看不懂、也搜不到的空壳。

**③ 失败只报一句"可能已经损坏"。** 实际有四种原因（认不出类型 / 读不出内容 / 存不进来 / 环境不支持），
却统一变成 `failed++`，最后 `reject({code:'read'})`。用户拿到的信息量是零，
而且**已经处理成功的文件也被一起丢弃**——因为 `reject` 不带 records。

### 20.3 改法一：新增 `utils/sniff.js`，四路判断

```
1. 文件名后缀（f.name）——用户看到的那个名字，最可信
2. 路径后缀         ——去掉 ?query / #hash 再取
3. 读开头 512 字节看魔数
   FFD8FF=jpg  89504E47=png  47494638=gif  RIFF…WEBP=webp  424D=bmp
   25504446=pdf  504B0304=zip/docx/xlsx
4. 还不是，就看这段字节像不像 UTF-8 文本（有 0x00 或控制字符就不是）
5. 都不是 → 二进制，如实说"认不出"
```

这套判断顺带解决了另一个老问题：**带 query 的路径**。`suffix()` 先 `split('?')[0]`，
`wxfile://tmp_abc.jpg?size=1024` 现在能正确取到 `jpg`。

### 20.4 改法二：一个文件失败，不连累其它

返回值从 `{records, failed}` 扩成：

| 字段 | 含义 |
| --- | --- |
| `records` | 待入库的记录 |
| `shells` | 只留下文件名的条数（PDF/Word 打不开正文，仍留着让用户补一句） |
| `skipped` | 完全没存下的，`[{name, reason, ext}]`，reason 取 `read` / `save` / `type` |
| `failed` | `shells + skipped.length`，兼容旧调用 |

只有 `records` 为空时才 `reject`，并且把 `skipped` 一起带出去：

```js
reject({ code: 'read', skipped: skipped })
```

于是页面能说清"是哪几个、为什么"，而不是一句"可能已经损坏"。

### 20.5 改法三：图片三级降级

```
saveChatImage（压缩后落盘）
  ↓ 失败
persist（原件直接搬进来）
  ↓ 失败
skipped.push({reason:'save'})
```

压缩失败不该等于图片丢掉。这条以前是 `failed++` 静默吞掉，现在至少会退到原件；
真存不进来才如实报，且原因写"可能是空间不够"。

### 20.6 改法四：机器名不进正文，也不进提示

`sniff.readableName()` 判三种机器名，命中就返回空串：

| 形态 | 例子 |
| --- | --- |
| 16 位以上连续十六进制 | `78a4bca059cff70d66e6b33621a75d18_26439` |
| `tmp_` / `tmp-` 前缀 | `tmp_9f8a7b2c` |
| 10 位以上纯数字 | `1699999999999` |

于是：

- 照片：正文留空，详情页自动出现「+ 补一句文字，这条就能被搜到」（`needText` 只看有没有正文，不分类型）；
- 二进制 + 有可读名：留「来自「会议纪要.pdf」」；
- 二进制 + 机器名：**不入库**，进 `skipped({reason:'type'})`，提示里只说"1 个认不出名字的文件"。

宁可少一条垃圾，也不要多一条看不懂的记录。

### 20.7 文案：把"为什么"和"接下来做什么"写出来

失败弹窗从一句话变成结构化：

```
这次没存成

选中的 3 个文件都没能存下来。

· 会议纪要.pdf（读不出内容）
· 一个认不出的文件（看不出是什么文件）

换成截图，或者在聊天里长按复制文字，这两种更稳。
```

部分成功时：

```
已存下 2 条，就在最上面。
1 张照片压到 300KB 以内，省下 4.2 MB。
1 个文件只留下了名字（PDF、Word 这类打不开文字），可以自己补一句。
还有 1 个没存下：会议纪要.pdf。
```

同时顺手堵住一个同类漏洞：`onRemind` 的失败分支原来写 `text: err.message`，
那会把 `requestSubscribeMessage:fail xxx` 这种原始错误串摆给用户。
现在改走 `REMIND_ERR` 码表，`design-lint` 也加了第 7 条：
UI 文案里出现 `err.message` / `err.errMsg` 直接判失败（已用探针验证）。

### 20.8 订阅消息接通之后，用户会依次看到什么

这是"配好模板之后会怎么提示"的完整链路，写下来免得每次重新推：

| 阶段 | 用户看到什么 | 出处 |
| --- | --- | --- |
| 进入「我的」 | 「每日提醒 / 还没开，点一下开启 / 关 ›」 | `me.wxml` |
| 点这一行 | **微信原生弹窗**：「灵感随时记 申请发送以下消息 · 记录提醒」+ 拒绝 / 允许 | `wx.requestSubscribeMessage` |
| 点允许 | toast「已开，明天 21:00 提醒你」；行变成「21:00 提醒你 / 已开 ›」 | `me.js` |
| 点拒绝 | toast「没授权，提醒不会来」，开关保持关闭 | `me.js` |
| 已开时再点 | 弹「关掉每日提醒？」→ 确认后 toast「已关掉」 | `me.js` |
| 到点 | 微信「服务通知」里一条卡片 | **服务端** `subscribeMessage.send` |
| 点通知 | 直接打开小程序指定页 | 下发时传 `path` |

**两个硬限制，必须在动手前知道：**

1. **通知不由小程序发**。`requestSubscribeMessage` 只完成"用户同意"，
   真正那条消息要自己的服务端/云函数按 openid 调 `subscribeMessage.send`。
   没有服务端，用户点了允许也永远不会收到——这也是 `visible()` 存在的原因：
   发布版没接通就整块不出现，而不是让人点进去等一条不会来的通知。
2. **一次性订阅 = 一次授权只能发一条**。工具类小程序申请不到"长期订阅"
   （微信只对政务民生、医疗、交通、金融、教育等线下公共服务开放）。
   所以「每日提醒」按字面意义做不到：昨天那条发完就没了。

**可行的替代，按推荐度：**

| 方案 | 成本 | 可靠性 | 说明 |
| --- | --- | --- | --- |
| A. 打开即提醒 | 零 | 100% | 进首页时若今天还没记，在回顾位那一栏显示「今天还没记一句 ›」。不依赖任何推送 |
| B. 每次记完顺手订阅 | 低 | 中 | 写完一条后问"明天这个点提醒你？"，用户点一次攒一条额度，合规但需每天配合 |
| C. 服务端 + 公众号 | 高 | 高 | 要用户关注公众号，转化损失大 |
| D. 写进系统日历 | 低 | 高 | `wx.addPhoneCalendar`，绕开订阅限制，但不在微信里 |

建议 **A 为主**，「每日提醒」这个开关等 B/C 真接通再打开——现在的门控已经保证了这一点。

## 二十一、打开即提醒 + 关于小程序（v1.7.4）

### 21.1 先把"每日提醒"这条路判死

上一版给「每日提醒」做了一半：客户端请求授权、记住时间、发布版里没接通就整块不显示。
但继续做下去没有意义，因为两道墙都不是靠写代码能翻过去的：

| 墙 | 事实 | 后果 |
| --- | --- | --- |
| 通知必须服务端发 | `requestSubscribeMessage` 只完成"用户同意"，真正那条消息要服务端按 openid 调 `subscribeMessage.send` | 没有服务端，用户点了允许也永远收不到 |
| 一次性订阅 = 一次授权发一条 | 长期订阅只对政务、医疗、交通、金融、教育等线下公共服务开放，工具类申请不到 | 「每天提醒」按字面做不到，昨天那条发完就没了 |

所以这一版把整块拿掉：`utils/remind.js` 删除，`pages/me` 的「习惯」分区删除，
连"设置一个不会生效的开关"的机会都不留。要恢复的话在 git 历史里（`git show d43c41d:miniprogram/utils/remind.js`）。

> 这不是"少做一个功能"。一个能点、能设、却永远不会有通知的开关，比没有这个入口更伤——
> 用户会记住"它说会提醒我，但没提醒"。

### 21.2 换成"打开即提醒"：不依赖任何推送

用户打开小程序的那一刻，本来就是他最想记东西的时刻。所以提醒放在那一刻，而不是放在通知栏里：

```
进入首页 → 今天还没记 → 筛选条下面那一栏显示「今天还没记一句 · 记一句 ›」
        → 点一下进记录页（复用底栏「写一句」的同一个入口）
        → 记完返回 → 这一栏自己消失
```

它与已有的两个回顾入口共用同一栏，优先级从高到低：

| 优先级 | 显示内容 | 条件 | 点击去哪 |
| --- | --- | --- | --- |
| 1 | 今天还没记一句 | 有记录、今天还没记、非筛选/非多选 | 记录页（写文字） |
| 2 | 那年今日 | 去年/前年同一天有记录 | 那条详情 |
| 3 | 随便翻一条 · 从 N 条里抽 | 记录 ≥ 2 条、没有那年今日 | 重温页 |
| — | 都不显示 | 一条都没记过 | 空状态本来就在说"想到什么，就说一句"，同一句话不说两遍 |

"三选一"是刻意的：这一栏高度固定，塞两样就会变成两条横幅，把列表往下推。

### 21.3 文案：按"隔了多久"和"连续几天"换，不用同一句天天念

同一句话第二天再看到就开始像催债。所以正文随状态变，标签与动作固定：

| 状态 | 正文 |
| --- | --- |
| 昨天记过、连续 ≥ 2 天 | 连续 N 天了，今天补一句就不断 |
| 昨天记过、连续 1 天 | 昨天那句还热着，今天也留一句 |
| 隔 2–6 天 | 隔了 N 天，随手一句就能接上 |
| 隔 ≥ 7 天 | 隔了 N 天，现在想点什么？ |

三条纪律写在代码注释里，也用测试钉住：

1. **不用催促词**。"应该""必须""坚持"这类词把记录变成作业，测试里直接断言文案不含这些词。
2. **连续天数只在真连续时说**。`streak` 的语义是"今天没记就从昨天往前数"，所以 `streak ≥ 2` 必然意味着昨天记过；写成 `streak >= 2 && gap === 1` 是为了不让这个判断依赖 stats 的实现细节。
3. **隔很久也不吓唬人**。40 天没记就老实说"隔了 40 天"，不写"你已经荒废了一个月"。

### 21.4 判断抽成纯函数 `utils/nudge.js`

页面里只留一句 `nudge.of(stats, { filtering, selecting })`。这么拆的理由很具体：

- **边界只能靠输入驱动**。"今天记过""手机时钟超前写下的未来记录""隔 7 天"这些分支，
  在真机上要造数据才能看到一种，而纯函数在测试里一次跑完十几种；
- **文案要能改**。以后调一句话，改一处 + 跑一次测试就知道有没有碰到边界；
- **页面不该知道"为什么"**。`pages/index` 只负责把"当前在不在筛选/多选"告诉它。

`gap <= 0` 这一条同时覆盖了两件事：今天已经记过，以及手机时钟超前写下的"未来记录"——
后者如果只判 `=== 0`，会天天催一个明明记过的人。

### 21.5 关于小程序：补上作者，并把第二个按钮做成真动作

标题按需求从「关于这个小程序」改成「关于小程序」，并补上：

```
作者：zhouguoxiang
微信：不卷的迭代老爸
邮箱：77111904@qq.com
```

原来的「关于」是 `dialog.alert`——只有「知道了」，看完就没了。想联系作者的人还得手抄邮箱，
所以改成两个按钮：**知道了 / 复制联系方式**，后者一次把三行写进剪贴板（`wx.setClipboardData`），
复制后 toast「联系方式已复制」。

三行字放在 `AUTHOR / WECHAT / EMAIL` 常量里，再由 `CONTACT` 拼装，
保证弹窗里显示的和复制出去的永远是同一份——不会出现"改了邮箱只改了一处"。

顺带修了一个小毛病：「关于」这一行原来写的是 `class="row"` 而不是 `class="row tap"`，
点得动却没有按下反馈，和上面几行不一致。

## 二十二、中英文双语（v1.8.0）

### 22.1 要回答的三个问题

双语本身不难，难的是三件事说清楚，否则做出来会是"有的地方换了、有的地方没换"：

| 问题 | 这一版的答案 |
| --- | --- |
| 哪些文案要进词典 | 所有**出现在屏幕上**的字：标题、按钮、占位符、空状态、弹窗、toast、日期与分组标题、导出文件里的正文。不进词典的只有三类：品牌名（灵感随时记、公众号名）、语言自称（中文 / English）、代码里的日志 |
| 切完怎么生效 | 写盘 + `wx.reLaunch`。不逐页 `setData`：日期、统计、"已录 N″"这类句子是在 js 里拼的，逐页刷必然漏一处 |
| 系统语言不支持时 | 回退中文。理由见 22.2 |

### 22.2 语言怎么定：三级优先，只认两种结果

```
用户选过（lg.lang.v1）   →  用用户选的
没选过 → 系统语言 en*    →  英文
没选过 → 其它任何语言    →  中文
```

系统语言的取法与归一：

| `wx.getAppBaseInfo().language` | 结果 | 说明 |
| --- | --- | --- |
| `zh_CN` / `zh_TW` / `zh-Hans` | zh | 只要是 `zh` 开头都算中文，不区分简繁 |
| `en` / `en_US` / `en-GB` | en | 只要是 `en` 开头都算英文 |
| `ja` / `ko` / `ru_RU` / 空 | zh | **回退中文** |

为什么回退中文而不是英文：这个工具里存的**内容**——用户自己写的那些句子——绝大多数是中文。
界面回退到内容的语言，用户在"看不懂界面"和"看不懂自己的记录"之间至少少一层隔阂；
反过来回退英文，会出现"满屏英文按钮 + 满屏中文卡片"的分裂感。

> 判断顺序也有讲究：先 `getAppBaseInfo()`，它在新版基础库上不触发废弃警告；
> 拿不到再退 `getSystemInfoSync()`；两者都没有（Node 里 require、构建脚本）时返回 `zh`，
> 保证这个模块可以被测试和工具直接加载。

### 22.3 为什么切换用 reLaunch，以及它带来的三个坑

`wx.reLaunch` 会重建页面栈，所有页面重新 `onLoad`。但它**不会重新执行 js 模块**——
`utils/*.js` 在 app 生命周期里只执行一次。于是三种写法会在切换语言后"卡在旧语言"：

| 坑 | 症状 | 这一版怎么解 |
| --- | --- | --- |
| 模块级常量 | `const TYPE_LABEL = { text: '文字' }` 永远是中文 | 改成函数：`typeLabel(type)`，每次调用现取 |
| 页面 `data` 里的文案 | 初次渲染前的空档（如空态文案）会漏 | `data` 里留空串，一律由 `applyLang()` 塞 `i18n.pack('页面')` |
| 错误码表 | `const ERR = { nofile: '没选到文件。' }` 同上 | 改成 getter 表 `i18n.table('me', [...], 'err')`，读 `ERR[code]` 的写法完全不变 |

`table()` 的第三个参数是"短码前面那一节"：`('index', ['nofile'], 'err')` → `index:err_nofile`，
`('index', ['type','read','save'], 'skip')` → `index:skip_type`。不给就是 `前缀:短码`。

### 22.4 词典长什么样

一个文件、两份字典（`ZH_DICT` / `EN_DICT`），键名统一 `命名空间:键`：

| 命名空间 | 覆盖 | 例子 |
| --- | --- | --- |
| `common` | 通用词 | `common:ok` 好 / OK |
| `date` | 星期、相对时间、分组标题 | `date:month_day` `{m}月{d}日` / `{m}/{d}` |
| `nudge` / `backup` | 两条横幅的正文与动作 | `nudge:keep` `连续 {n} 天了…` |
| `me` / `index` / `record` / `detail` / `review` / `search` / `poster` | 各页文案 | `record:voice_recorded` `已录 {n}″ · 点这里听` |
| `card` | 组件内文案 | `card:listen` 点一下听听 |
| `media` / `store` / `dialog` / `asr` / `share` / `transfer` | 数据层与传输层 | `store:full_title` `满 {n} 条了` |

三种取词方式，各管一处：

| 方式 | 用在哪 | 写法 |
| --- | --- | --- |
| `i18n.t(key, params)` | js 里拼句子 | `i18n.t('date:min_ago', { n: 5 })` |
| `i18n.pack('页面')` | wxml 里的静态文案 | `data.t = i18n.pack('me')` → `{{t.row_backup}}` |
| `i18n.table(前缀, 短码, kind)` | 错误码表（要保留 `ERR[code]` 写法） | `IMPORT_ERR[err.code]` |

`pack()` 以中文词典的键为全集，保证两种语言的字段集合一致——英文漏了一个键，wxml 里会显示空白而不是崩溃，
但这种"看起来正常"的错误最难发现，所以有测试专门盯它（见 22.6）。

### 22.6 两条守卫，防止以后悄悄退化

**一、`tools/i18n.test.js`（41 条）** 不看界面，只查静态一致性：

| 组 | 钉住什么 |
| --- | --- |
| 1 | 中英键集合完全相同；没有"只有中文"的键 |
| 2 | 同一个键的 `{n}` / `{m}` 占位符两边数量一致（写丢一个，数字就凭空消失） |
| 3 | 英文值里不许有汉字（白名单：品牌名、语言自称、导出文件名） |
| 4–5 | 空值、占位符替换 |
| 6 | 系统语言 10 种分支（`zh_TW` / `en_US` / `ja` / `ko` / 空 …） |
| 7 | 用户选择优先且持久化；非法值回退 |
| 8 | `pack()` 只给自己那一份，且不含别的命名空间 |
| 9 | 没有 `wx` 时安全降级（构建脚本要 require 它） |
| 10 | **引用即存在**：代码里 `i18n.t('x')` 和 `i18n.table(ns, [...], kind)` 用到的键必须都在词典里 |
| 11 | wxml 里的 `{{t.xxx}}` 与 `pack('页面')` 对得上（对不上不报错，只会渲染成空白） |

第 10 组是这一版现抓出来的：`table()` 最初拼的是 `index:unsupported`，而词典里叫 `index:err_unsupported`，
`t()` 取不到就把键名原样返回——界面上会直接显示 `index:unsupported`。断言加上之后这类错跑一次就露。

**二、`tools/design-lint.js` 第 7 条**：wxml 里出现中文字面量、js 里出现中文文案字面量，构建即失败。
逐行判断而不是整份解析——中文注释里常有英文引号，整份解析会被一个没配平的引号带到文件末尾。
白名单只有 5 条，每条都写了理由（品牌名、语言自称、导出文件名、`data` 初值）。

## 二十三、里程碑版本怎么发（v1.8.0 起）

上线以后，每个阶段性版本都要留两样东西：一份能还原现场的代码包，一个能定位到具体提交的 tag。
手工做这两件事，每次总会漏一步，所以固化成一条命令：

```
node tools/release.js 1.8.0 "中英文双语"
node tools/release.js 1.8.0 --dry-run      # 只检查，不动手
```

它按顺序做四件事：

| 步骤 | 检查什么 | 为什么 |
| --- | --- | --- |
| 1 | 工作区必须干净 | 包里混进半成品，备份的就是一个从来没存在过的版本 |
| 2 | tag 不能已存在 | 覆盖 tag 会让"这个版本到底是哪版"永久说不清 |
| 3 | `me.js` 的 `version` 必须等于要打的 tag | 用户反馈问题时，界面上的 1.8.0 是唯一的定位依据 |
| 4 | 打包 → 建 annotated tag → 推 origin → 回读 `ls-remote` | 推送成功不等于推对了，回读才算数 |

产物：

- 备份 `<工作区>/备份/灵感随时记-v1.8.0-20261112.zip`（**含 `.git`**，约 1.1 MB）
- tag `v1.8.0`（annotated，不是轻量 tag，说明会随 tag 一起推到 GitHub）

一个坑写在脚本注释里：`Compress-Archive` 会把 `.git` 这种点开头的目录**静默跳过**——
不报错、不警告，压出来 90 个源码文件看着很完整，但历史一条都没有。
所以脚本先整套复制到临时目录再压。含 `.git` 多花 800 KB，换一个能完整还原的现场。

## 二十四、保存按钮从顶栏挪到底部（v1.8.2）

### 为什么非挪不可

记录页是 `navigationStyle: custom`，顶栏自己画。原实现用 `space-between` 把「取消 / 标题 / 存下」排开，右内边距只有 `24rpx`（12px）——而微信胶囊在 375 宽屏上占的是「距右 7px 起、宽 87px」的一条，右侧 94–106px 属于系统保留区。

三件事叠在一起：

1. **横向没让位**，按钮直接坐进保留区正中间，肉眼只剩右缘几个像素；
2. **纵向又在同一条带上**（胶囊 `top = 状态栏 + 4`、高 32px，与 44px 顶栏重合）；
3. **`z-index` 对胶囊无效**——它是原生控件，渲染在 WebView 之上，调到 9999 也压不过去。

所以这不只是"看不清"，是"按不到"：落在胶囊下的那部分点击会被系统接管，打开的是微信菜单。

另有一层与重叠无关的原因：禁用态 `#c9bdae` 在 `#fbf8f3` 上只有 **1.8:1**，可读性下限是 3:1。新用户进来看到的是一个淡到需要凑近找的灰字。

### 选了哪一版

评估过六种改法（按胶囊实测让位 / 底部主按钮 / 硬编码右边距 / 挪到左侧 / 缩字号 / 只修对比度），最终取 **底部主按钮 + 可点软态**：

- 顶栏右侧**整条清空**，不碰胶囊，也不用算让位公式——移动端主行动本来就该在拇指够得着的底部；
- 主按钮 **48px 高、335px 宽**，可用区从 60px 变成 335px，文案不必再为字数让步；
- 空内容时**不置灰成死按钮**，改成米底深橙（`--accent-deep` `#8F5730`，5.2:1）的可点软态，按下去会说差什么。灰按钮的问题不是"灰"，是"按了没反应还不知道为什么"。

代价是底部固定区从 58px 长到 114px，内容区变短，提示条也得跟着抬。

### 文案改了哪几处

| 位置 | 改前 | 改后 | 为什么 |
| --- | --- | --- | --- |
| 顶栏右侧 | `存下`（被胶囊压住） | 整条移除 | 位置让给系统控件，不是改字号能救的 |
| 底部主按钮（新建） | — | `存下这条` | 与标题「记一条」形成"产生 → 保留"的闭环；「存下」是悬空动词，用户得自己补宾语 |
| 底部主按钮（编辑） | — | `存下改动` | 编辑态说「存下这条」会被读成"再存一条新的" |
| 空内容按下去 | 无反馈（按钮已灰） | `还没写呢` / `还没选照片` / `还没录` | 沿用原有三条按类型区分的提示，比一句笼统的"写点什么"更准 |
| 底部提示条位置 | `bottom: 240rpx` | `calc(260rpx + env(safe-area-inset-bottom))` | 固定区变高后，旧值在 iPhone X 上会压住主按钮 |

词典里 `record:nav_save` 已删除，换成 `record:save_cta` / `record:save_cta_edit`。删键是有意的：留着一个谁也不用的键，下一个人会以为它还在界面上。

### 顺带修掉的三处

- **标题真正居中**：原来靠两侧 `min-width: 120rpx` 假装，右侧一空就偏左，改成 `.nav-bar` 居中 + 左侧绝对定位；
- **取消可点区** `72rpx → 88rpx`（36px → 44px，低于 44px 是触屏下限）；
- **输入时留白** `cursor-spacing` `140 → 160`：底栏厚了 56px，光标贴键盘太近会被按钮压住。

### 怎么验的

`tools/copy.test.js`（55 条）专门盯"文案改动有没有漏"：旧键是否彻底消失、新旧键中英是否齐备、wxml 是否还引用旧字段、底栏几何是否能容下按钮、软态/实态对比度是否达标、提示条是否还在按钮之上。这类问题的共同点是**跑得起来但看得见错**，只能静态比对。

真机上另需确认一项：文字态键盘弹起时，底部固定区是被顶到键盘上方还是被遮住。本改动沿用了 `.tools` 原有的 `position: fixed; bottom: 0`（1.8.1 的三个 tab 就是这么放的，线上没有"tab 被键盘遮住"的反馈），但按钮更高，建议在 iPhone 全面屏与一台安卓上各看一眼。

## 二十五、「做成图」只显示一张照片（v1.8.3）

### 现象与成因

一条记录有 3 张照片，卡片里是错落的 3 张，点「做成图」导出后只有 1 张，正文还写着"（3 张照片）"。

```
pages/poster/poster.js
const src = rec.type === 'photo' ? (rec.mediaPaths || [])[0] || '' : ''
...
poster.loadImage(canvas, src)          // 只取了下标 0
```

`poster.js` 的绘制层也只接受**一张** `image`（`measure(ctx, rec, { image })`），画的时候按 `cover` 铺满一块 630×420 的区域。也就是说这不是画错，是**从来没打算画第二张**：长图是 1.8.0 之前写的，那时记录页只有单张图，多图是后来才有的，长图没跟着改。

### 改法：把首页那套堆叠搬进 canvas，而不是另写一套

首页的错落堆叠（第十章）有一组手工摆的坐标：2 张一套、3 张一套、4 张一套，外框 330×254、白边 10、旋转 -9°~+6°，再用记录 `id` 做散列抖动。这些数字如果照抄一份进 `poster.js`，两边迟早会分叉——手机上歪 3 度、图里歪 5 度，且没人说得清哪个是对的。

所以先把数字抽到 `utils/stack.js`，卡片只负责拼 CSS，长图只负责画 canvas：

```
新    utils/stack.js     LAYOUTS / hash() / plan() / planAll() / clusters()
改    components/card/card.js    buildStack() 调 stack.plan()，输出逐字节不变
改    utils/poster.js            loadImages() / paintPhotos() / fitDpr()
改    pages/poster/poster.js     一次取全部照片，按真实高度挑倍率
```

抽出来的时候对 12 组（2/3/4 张 × 4 个 id）做过逐字节比对，卡片样式串一个字符都没变——重构不能顺手改视觉。

### 超过 4 张怎么排

一组最多 4 张（再多就糊成一团），多出来的往下再起一摞，组间 28rpx：

| 张数 | 分组 | 结果 |
| --- | --- | --- |
| 1 | 整幅大图 | 与原来一致，420 高 |
| 2–4 | 一组 | 一摞相纸 |
| 5 | 3+2 | 两摞 |
| 7 | 4+3 | 两摞 |
| 9 | 3+3+3 | 三摞 |

不切 `4+1` 是有意的：落单的 1 张会退化成"整幅大图"，夹在两摞相纸中间很突兀。分配规则是"组数 = ⌈n/4⌉，再均分"，所以 5 张是 3+2 而不是 4+1。

### 三个容易翻车的细节

1. **版式按张数算，不按"加载成功几张"算。** 某张图被系统清掉了，`loadImages` 在该位置返回 `null`，版式照旧（少一张不该让后面几张错位），只是那一格画一块米色——和卡片加载前的占位同色。若一张都没加载出来，整块不画，退回纯文字长图，不留一片空相纸。
2. **位图预算。** 9 张照片的长图能到 1892px 高，3 倍下是 2250×5676 的画布、约 50MB 位图，低端安卓容易在 `canvasToTempFilePath` 这一步直接失败；canvas 2d 在部分机型上单边过大还会干脆画不出东西。`fitDpr()` 同时卡两条线——面积 1200 万像素、单边 7000 设备像素，普通高度仍是设备倍率，长图降到 2.9，极端长图（26 行正文 + 9 张照片约 3300px）降到 2.1，下限保 1.5。
3. **只认 photo 类型。** 语音记录的 `mediaPath` 是音频，`pathsOf()` 会把它当"一张图"返回；`measure()` 里加了 `record.type === 'photo'` 才取，否则语音长图会预留一块照片区。

### 怎么验的

`tools/poster.test.js`（63 条）用假 ctx 把"画了几张、画在哪、什么顺序"逐项录下来核对：

- 分组：2–30 张每组都在 2–4 之间且总数守恒（含 5→3+2、7→4+3、9→3+3+3）
- 同源：把 `card.js` 的 `buildStack` 抠出来跑，与 `stack.plan` 逐字比对 9 组
- 数量：9 张就画 9 次 `drawImage`（这次要修的问题本身）
- 顺序：绘制次序 = 层级从下到上（压住关系与卡片一致）
- 容错：中间一张 `null` 只画 2 张、版式仍是 3 张；全 `null` 则整块不画
- 边界：五种 id × 三档张数，相纸都不出 630 宽的内容区；最下面一张不压页脚线
- 倍率：`fitDpr(620, 3) === 3`、`fitDpr(1892, 3)` 落到 2.9、`fitDpr(9000, 3) === 1.5`、面积与单边都不越界

另外用真实浏览器跑了一遍 `utils/poster.js` 的完整绘制路径（含 `rotate`/`clip`/`shadow`），把 1/3/9 张三张海报真的画出来看了一遍——假 ctx 只能证明"调了几次 `drawImage`"，证明不了"投影有没有糊到照片上、白边有没有被裁掉"。

### 真机仍要看的

- 9 张照片：从点「做成图」到出图要多久（9 次 `getImageInfo` + 9 次解码，低端机可能 1–2 秒；有 loading 态，但值得量一下）
- 相纸投影在 iOS 与安卓上的深浅是否一致（canvas 的 `shadowBlur` 两端实现有差异）
- 切到别的页面再回来，`poster` 页会重建并重画一次，图不应错位



## 二十六、切语言后的中英混排（v1.8.4）

### 26.1 混排只有三种来源

排查之前先把范围收窄。一个界面里出现两种语言，只可能是这三件事之一：

| # | 来源 | 长什么样 | 难不难发现 |
| --- | --- | --- | --- |
| A | 文案根本没进词典 | 某句直接写在 wxml / js 里 | 容易，`grep` 中文就能扫出来 |
| B | 进了词典，但**取词发生在模块加载那一刻** | 切完语言，某个页面的标题/toast 还是旧语言 | 难。测试全绿、代码看着没问题，只有用户看得见 |
| C | **一个值里同时写了两种语言** | 「语言 / Language」这样并排 | 最容易忽略，也最扎眼 |

这次用户报的"中英混排"是 C。但排查过程中 B 也挖出来两处，属于"还没显形、将来必踩"的那类。

**B 的机理值得单独记一遍**：切语言走 `wx.reLaunch`，它会重建页面实例，但**不会重新执行 js 模块**。所以

```js
const LABEL = i18n.t('nudge:label')   // ← 模块加载时求值一次，永远停在启动语言
```

这种写法在切语言后一定不变。它当时没被引用，所以界面上看不出来——但只要哪天有人写 `nudge.LABEL`，就多一处查不出来的混排。所以这一版把它们删了，并加了守卫（见 26.6）。

### 26.2 怎么查：把页面真跑起来，逐字段 diff

15 个既有测试都能证明"用 `t()` 取词是对的"，但**没有一个能证明"切完语言后屏幕上每个字都换了"**。因为混排不体现在某处代码错了，而体现在某处**没跟着换**。

所以新增 `tools/lang-audit.js`（`node tools/lang-audit.js`），做法是：

1. 装一套假 `wx`（storage 在内存里、`getAppBaseInfo` 返回指定语言、`setNavigationBarTitle` / `showToast` / `showModal` / `showActionSheet` 全部录下来）
2. 把 **7 个页面 + 2 个组件**真实实例化，跑 `onLoad / onShow / onReady`，再点一轮交互（删除确认、加一句、清空、关于、语言面板、切类型、丢弃确认……）
3. 记下 `setData` 出来的**每一个字符串字段**，以及所有命令式文案
4. 跑三轮：**冷启动中文** → **热切换英文**（不重跑模块，复现 `reLaunch`）→ **冷启动英文**（对照）
5. 逐字段比对

三轮的采集量必须一致（当前：10 个页面 / 671 个字符串字段 / 18 条命令式文案）。数量对不上说明比对本身出了问题——第一次跑就撞上过：对话框中枢是模块级单例，上一轮 bind 的实例没解绑，第二轮的弹窗全打到旧实例上，结果 9 条文案凭空消失，看起来像"切语言后弹窗不弹了"。

判定口径：

| 级别 | 含义 |
| --- | --- |
| `PARALLEL` | 一个值里中英并排（最严重，用户说的就是它） |
| `MIXED` | 英文模式下这个字段里还有汉字 |
| `STALE` | 中英取到同一个值，切了等于没切 |
| `SAME` | 同上，但值本身不含汉字 |
| `MISS` | 英文模式下为空，中文有值 |

**两类东西不能被判成混排**，否则结果全是噪声：

- **用户自己写的内容**（记录正文、标签、搜索词）。一条中文记录切成英文后仍然该是中文，这是产品语义。
- **品牌名**（`灵感随时记`、`不卷的迭代老爸`）。产品名不翻译是通则。

`Nothing for "复盘"` 这种"英文模板 + 用户输入"的组合也要放过——把英文里的汉字逐段拿去和已采集的用户输入比对，全部命中就不算。

### 26.3 这一版修了什么

| # | 位置 | 改前 | 改后 | 性质 |
| --- | --- | --- | --- | --- |
| 1 | `me:row_lang` | `语言 / Language`（中英两侧都是这个） | 中文 `语言` / 英文 `Language` | **真正的混排**，全站唯一一处"同一行两种语言" |
| 2 | `transfer.js` 备份文件名 | 写死 `灵感随时记-{时间}.json` | 走 `transfer:json_prefix`（`灵感随时记-` / `inspirations-`） | 英文界面导出的文件名是中文，用户在文件传输助手里认不出来 |
| 3 | `utils/nudge.js` | `const LABEL / TIP = i18n.t(...)` | 删除（`of()` 里现取） | B 类隐患，当前无人引用 |
| 4 | `utils/backup.js` | `const LABEL_ONLY = i18n.t(...)` | 删除（`of()` 里现取） | 同上 |

## 二十七、多图合成一条 · 剪贴板"没读成" · 收不了的文件（v1.8.5）

上线第二天收到两条反馈，都在「从聊天存」这一个入口里。

### 27.1 问题一：选 6 张图，列表里多了 6 条

`importFromChat()` 原本是"一个文件一条记录"，图片也不例外：选 6 张图 = 6 条 `photo` 记录 = 6 张卡片。

这个拆法是错的，而且错在三层：

1. **语境丢了**。用户一次勾 6 张，这个动作本身就在说"这是同一批"（同一段对话、同一个需求）。拆开之后，一周后看到第 4 张，想不起它属于哪个方案。
2. **卡片流被刷满**。首页按日分组，9 张图等于 9 张卡，当天其他记录全被挤下去。而产品的语义是"一条记录 = 一个念头"。
3. **能力没了**。零散 9 条做不出长图，一条 9 张可以一键成图（v1.8.3 的 `poster.js` 早就支持）。

### 27.2 修法：占位 + 回填，顺序不变

不能"攒到最后再 push"——那样合并后的记录会被甩到列表末尾，和用户在聊天里看到的顺序对不上。所以在**第一次遇到图片的位置放一个空位**（`records.push(null)` 并记住下标），后选的图都往这个坑里填，全部处理完再回填成真正的记录：

```js
if (photoAt < 0) { photoAt = records.length; records.push(null) }   // 占一个坑
photoPaths.push(r.path)                                              // 后面的图填进同一个坑
...
const settlePhotos = () => {
  records[photoAt] = {
    type: 'photo',
    // 单张时文件名还有意义；多张是"同一批"，写任何一张的名字都会误导
    content: kept.length === 1 && photoName ? i18n.t('transfer:from_file', { name: photoName }) : '',
    mediaPaths: kept,
    size: photoSize
  }
}
```

三条边界一起处理掉：

| 情况 | 处理 |
| --- | --- |
| 图片夹在文本中间（`.txt` + 3 张图） | 顺序仍是 `text,photo`，照片记录留在图片第一次出现的位置 |
| 图片全部存不下 | 空坑在收尾时 `splice` 掉，不留一条没有图的照片记录 |
| 多于 9 张 | 理论上到不了（选择器 `count: 9`），真超了就删掉多余的落盘文件，不留孤儿 |

文本、PDF、Word 仍然各成一条——它们本来就是独立内容，合并才是错。

页面侧同步加了两处：`onProgress(done, total)` 让遮罩显示「正在保存 3/9」（原来 9 张图压缩落盘要 2–5 秒，只有一个不动的"处理中"）；成功后如果发现某条有 `mediaPaths.length > 1`，多一行说明——不解释的话，用户会以为"我选了 6 张怎么只多了一个"。

这一行最初写的是「{n} 张图合成了一条，**没有刷屏**」，后来被改掉了，理由见 29 章。

### 27.3 问题二：剪贴板里明明有字，却说"没读成"

现象是点「粘贴刚复制的文字」→ 弹「没读成」，而用户手上确实复制了内容。

### 27.4 根因：loading 遮罩把隐私授权框挡住了

`collectClipboard()` 原来的顺序是：

```js
wx.showLoading({ title: i18n.t('common:reading'), mask: true })   // ← 先挂遮罩
transfer.fromClipboard()                                          // 内部先 requirePrivacyAuthorize
```

剪贴板是隐私接口，第一次调用时微信要先弹隐私授权框。而 `mask: true` 的 loading 是**模态遮罩**，弹窗被压在它后面；用户点不到、或者弹窗直接被判为未完成 → `getClipboardData` 失败 → 归到 `read`/`denied` → 页面只能报「没读成」。

讽刺的是同一个坑在拍照路径上早就踩过并写了注释（`record.js`："相机/相册回来之后才挂 loading，避免用户看到加载圈却等不到界面"），剪贴板这一路漏了。

一个旁证：读剪贴板本身只要几十毫秒，这个 loading 从来就没有存在的必要——它是纯装饰，代价是把功能挡死。

### 27.5 修法：四层，从治因到兜底

1. **不挂遮罩**。`collectClipboard()` 里彻底去掉 `showLoading`，让隐私授权框能正常弹出。文件选择那一路同样把 loading 挪到选择器返回之后（`onProgress` 才会被调到，选择器取消时一次都不调，配合 `closeLoading()` 不刷"没有 loading"的告警）。
2. **重试一次**。隐私弹窗刚关闭时系统可能还没来得及把内容交出来——读到空、或收到非权限类 `fail`，200ms 后再读一次。权限类失败（`deny|auth|privacy|scope|112`）不重试，重试也没用。
3. **把 errMsg 带出去**。原来 `reject({code:'read'})` 把原始错误吞了，线上根本没法判断是哪一种失败。现在带 `detail`，页面 `console.warn` 一行，出问题时这是唯一线索。
4. **手动粘贴兜底**。读不到时不再只弹一个错，而是 `wx.showModal({ editable: true })` 让用户长按自己粘贴——这条路走的是系统输入框，不依赖任何接口，**永远不会死在这一步**。粘贴进来的文字与剪贴板读到的走同一个 `saveCollected()`（截断、落库、刷新、高亮、注入草稿行为完全一致）。

`wx.canIUse('showModal.editable')` 为假的老基础库退回一句说明文案，不至于弹出一个没有输入框的空壳。

### 27.6 守卫

`tools/collect.test.js` 从 41 条加到 63 条，新加的 22 条盯的就是这次两个改动：

- 三张图只产生一条记录 / 带满三张 / **压缩顺序等于选择顺序**（不按名字、不按时间重排）
- 多张时不把任何一张的文件名写进正文 / 体积是合计 / `photoCount`、`merged` 如实回传
- 图片夹在文本中间时顺序是 `text,photo` 而不是 `photo,text`
- 图全失败时占位被删掉，不出现空照片记录
- `onProgress` 每个文件回调一次，序号与总数都对
- 剪贴板：第一次读空、第二次拿到内容算成功；非权限类失败重试后报 `read` 且 `detail` 里带原始 errMsg
- 静态守卫：`collectClipboard` 的函数体里**不许出现 `wx.showLoading`**、必须调用 `pasteManual`、必须复用 `saveCollected`

静态那条是这次最值得留的——**这个 bug 的形态是"顺序写反了"，靠断言行为很难复现，靠看代码形状一眼就能抓**。

### 27.7 合并之后的两个新问题：搜不到、看不出是同一批

合并把"零散存"的问题解决了，又带出两个新的：

**（1）搜不到。** 搜索只查正文和 `#标签`。原来 6 条孤图虽然散，但至少每条还能靠文件名认；合并成一条又没字，就彻底隐身了。

修法不是在搜索里加"按图片搜"（本地没有 OCR，做不了），而是在**卡片上就提醒一次**：照片记录正文为空时，卡片底部出现一行虚线提示「点一下补一句，以后才找得到」，点它直达编辑页并聚焦配文框（`record?mode=edit&id=xxx&focus=1`，`onReady` 里 120ms 后 `focus: true`，和"点加号写一句"是同一个手感）。

为什么放在卡片而不是详情页：详情页的 `need-text` 已经存在了，但**用户得先点进去才看得到**——而合并记录最需要的恰恰是"在列表里就被提醒"。

**（2）列表里看不出是"一批"。** 首页卡片本来就支持多图错落堆叠（`stack.js`），合并记录天然落进这条路径：2/3/4 张各有一套手工摆位，超过 4 张按 3+3 / 4+3 切组，不会出现"一组只放 1 张"的突兀情况。

但**详情页原来是九宫格**（`photo-grid`，2–3 列平铺），和首页完全两种气质。这次统一成同一套版式：

```xml
<photo-grid wx:if="{{!multi}}" paths="{{photos}}" single="auto" />
<view class="stack" wx:else>
  <view class="stack-group" wx:for="{{clusterList}}" style="height:{{g.height}}rpx;margin-top:{{g.gap}}rpx">
    <view class="frame" wx:for="{{g.frames}}" style="{{ph.style}}" catchtap="onPreviewPhoto" data-i="{{ph.idx}}">
      <image class="frame-img" src="{{ph.src}}" mode="aspectFill" />
    </view>
  </view>
</view>
```

坐标来自 `stack.planAll()`——和首页卡片、做成图**同一个函数、同一份数字**，不会再出现"手机上歪 3 度、图里歪 5 度"。与卡片唯一的差别是详情页把所有组都铺开（卡片只摆一组 + 角标 "+N"），因为进来就是看图的。单图仍是整幅大图，点击进 `wx.previewImage`。

### 27.8 收不了的文件：不能只留个壳，更不能一直转圈

现象：从聊天里选视频、压缩包，界面转圈一圈，最后要么多出一条「来自「会议录像.mp4」」的空壳记录，要么干脆什么都不说。

根因是**把所有二进制都当成"值得留壳"**。对 PDF/Word 留壳是对的（用户知道这份文档在这儿，可以自己补一句），但对 `.mp4` 留壳纯属垃圾：点不开、听不了、还占着列表。另有一条隐性风险：文本类走 `readFileSync` **同步**读全文件，选了个 50MB 的 csv 会把界面卡住——进度条一直在转，其实早就该说"这个不读"。

三条修法：

| 情况 | 现在怎么办 |
| --- | --- |
| 视频 / 音频 / 压缩包 / 安装包（`UNSUPPORTED_EXT` 24 种） | 不进列表，收进 `unsupported`，当面报「这 3 个收不了：会议录像.mp4、素材包.zip」 |
| 文本类超过 2MB（`MAX_TEXT_BYTES`） | 不读、不落库，报「导出.csv（超过 2MB）」——反正正文最多只要 1000 字 |
| PDF / Word / Excel / PPT | 仍然留壳，不计入"收不了" |
| 全都收不了 | 单独一个错误码 `unsupported_type`，弹「这些文件收不了 + 能收什么」的说明，而不是只说"没存成" |

文案也分了两种口径：`skipped`（文件坏了/读不出）说"读不出内容"，`unsupported`（格式不收）说"这个格式不收"——**用户需要知道下次别选它，还是这个文件本身有问题**。

还有一处顺手加的护栏：`sniff.classify()` 会自己去读文件头，极端情况下（文件刚被系统清掉）会抛错。抛错就等于整条链断了——`loading` 永远关不掉，用户看到的就是"一直转圈"。现在这条调用包了 try/catch，出错按"读不出"记一笔继续处理下一个。**"界面卡住"这类反馈，十有八九缺的就是这一个 try。**

### 27.9 守卫（续）

`collect.test.js` 81 条，新增 18 条盯这三处：

- 全是不支持格式 → `unsupported_type`，且**不产生任何壳记录**
- 混合选择 → 支持的照常入库、收不了的单独列出、`failed` 不把它们算成"坏文件"
- 超过 2MB 的文本 → 归到 `unsupported` 且 `reason === 'big'`
- PDF 仍留壳、不进"收不了"清单
- 卡片：`needText` 只对"照片 + 空正文"成立；提示走 `triggerEvent('addtext')` 而不是卡片自己跳页；首页两处卡片都绑了事件；跳转串带 `focus=1`
- 详情页：多图走 `stack.planAll`；照片区按 `multi` 分流；每张都能点开大图；**不再**用九宫格铺多图

### 真机仍要看的

- 从聊天里选 6–9 张图 → 只应多出**一条**记录，角标「照片 6 张」，点开是错落堆叠（点任意一张看大图）；「做成图」出来的长图里应有全部 6 张
- 合并出来的那条在首页卡片上应有一行虚线提示「点一下补一句」，点进去键盘应自动弹起
- 从聊天里选一个 .mp4 / .zip → 应直接弹「这些文件收不了」并说明能收什么，**不应**出现「来自「xx.mp4」」的记录
- 选「1 个 3MB 的 csv」→ 应报"超过 2MB"，界面不卡顿
- 选「1 个 txt + 3 张图」→ 应多出 2 条，且照片那条在 txt 下面（顺序与选择一致）
- 选图过程中遮罩应显示「正在保存 3/6」而不是一直「处理中」
- 首次使用（未点过隐私授权）时点「粘贴刚复制的文字」→ 应先弹隐私授权框、同意后正常存入；若仍失败，应看到**可输入的粘贴框**而不是「没读成」
- 老基础库（< 2.17.1）下点粘贴 → 应看到一句说明文案，不是空白弹窗

## 二十八、剪贴板还是"没读成"：两个叠在一起的错（v1.8.5 开发期修）

> ⚠️ **本章 28.2 的结论已被推翻，修法已回滚。** 正确复盘见第 30 章。
> 留在这里是因为 28.1（`wx.canIUse` 判断串写错）是真的，而且值得记；
> 但 28.2 那条"先授权再读是错的"是个错误的诊断，照着改了之后功能才彻底坏掉。

27 章把 loading 遮罩摘掉了，真机上仍然报「剪贴板有内容，还是提示没读成」，而且弹出的不是输入框，是那句「这个系统版本不支持在这里粘贴」。

这说明**兜底本身就是坏的**。查下来是两个独立的错叠在一起。

### 28.1 错一：`wx.canIUse` 的 schema 写错，兜底永远不被启用

```js
const canEdit = wx.canIUse('showModal.editable')   // ← 永远 false
```

官方文档写得很死：`${API}.${method}.${param}.${option}`，而 **`method` 只能是 `return / success / object / callback`**。`showModal.editable` 少了 `object` 这一层，是个非法 schema，`canIUse` 直接返回 `false`。

于是每次失败都走进"系统版本不支持"分支——**兜底不是兜底，是一句道歉**。用户手上明明有文字，却再也没有地方可以粘。

正确写法是 `wx.canIUse('showModal.object.editable')`。但这次没有去改这一个字符串，而是**把兜底换成不依赖基础库判断的方案**：

- 项目里本来就有自绘的 `<dialog-view>`（纸白面板、陶土橙按钮，和系统弹窗气质完全不同的那套），它的输入框是普通 `input`，不受 `editable` 参数支持与否的影响；
- 为它加了 `multiline` 选项，用 `textarea` 渲染（固定 320rpx 高、内部滚动），粘贴长文时能看到全文而不是在一个单行框里左右滑。

一个判断字符串写错，能把整条兜底路径静默废掉，而且**任何单测都发现不了**（代码能跑、不报错、只是永远走错分支）。这是这一章最值得记的一条。

### 28.2 错二：先做隐私授权，再读剪贴板（← 这一条是错的，见第 30 章）


原来的顺序：

```js
require('./media').ensurePrivacy().then(read, read)   // 先授权
```

看着更"规范"——剪贴板是隐私接口，先拿授权天经地义。但 `getClipboardData` 有个隐含要求：**必须在用户主动触发的那一下读**。`ensurePrivacy()` 是异步的（未授权时会弹框），一 `await`，读取就发生在微任务里、甚至发生在用户点完授权框之后，时机已经脱离点击栈。某些机型/系统版本上，这就直接被判成"非用户触发"而 `fail`。

改成：

```js
// 先读。点按钮的那一下就是"用户主动触发"，微信认这个时机。
wx.getClipboardData({ success: settle, fail: onFail })
```

`onFail` 里只有识别到**权限类错误**（`deny|auth|privacy|scope|112`）才回头补一次 `ensurePrivacy()` 再读，且只补一次——授权框本身要用户点，反复补只会连环弹框。

顺序反过来这件事，功能上看不出区别，只在对时序敏感的真机上暴露。**"看起来更规范的写法"不等于更对。**

### 28.3 顺手补上：让失败原因能被看见

这两轮排查最大的障碍不是改代码，是**拿不到 `errMsg`**。`console.warn` 在真机上看不到，用户只能反馈"没读成"，我们只能猜。

现在读到失败原因后，如果是**开发版或体验版**（`wx.getAccountInfoSync().miniProgram.envVersion` 为 `develop`/`trial`），弹窗正文会多一行：

```
［诊断］read / getClipboardData:fail system error
```

正式版这一行是空串——用户不需要看懂 `getClipboardData:fail ...` 这种东西，但排查时没有它就是瞎子。

### 28.4 守卫

`collect.test.js` 90 条，新增 8 条盯这次的两个错：

- `pasteManual` 用 `dialog.show` + `multiline: true`，**函数体里不许出现 `wx.showModal`**
- 全项目代码行里不许再出现 `canIUse`（注释里解释这条坑不算）
- `dialog.wxml` 真的渲染了 `textarea`
- 诊断行有 `envVersion` 且同时认 `develop` / `trial`
- `transfer.js` 里不许再有 `ensurePrivacy().then(read, read)`
- 函数体最后一步必须是直接 `wx.getClipboardData(...)`
- 权限类失败才补授权（`denied && !triedPrivacy`）

另外把三处老断言的切片方式改了：原来按 `indexOf('collectClipboard()')` 到 `indexOf('pasteManual()')` 截取，`pasteManual` 定义位置一变就切出空串——**断言会静默变成空跑**（`''.includes()` 恒假或恒真）。现在改成按函数体正则截取，并加一条"两个函数体都切出来了"的自检。

### 真机仍要看的

- 剪贴板里有字时点「粘贴刚复制的文字」→ 应直接存下，**不应**再弹任何框
- 若仍然读不到 → 应弹出**多行输入框**（不是"系统版本不支持"），且正文里有「［诊断］…」一行，把那行截图给我
- 在多行框里长按粘贴一段长文 → 能看到全文、能滚动、点「好」后正文完整

## 二十九、回执文案里的「没有刷屏」：把设计动机讲给了不该听的人（v1.8.5 开发期修）

上线后第一版回执长这样：

```
收到
已存下 1 条，就在最上面。
6 张图合成了一条，没有刷屏。
4 张照片压到 300KB 以内，省下 5.4 MB。
```

被用户一句问住了：**为什么会用「没有刷屏」这种词面向用户？**

### 29.1 这句话错在哪

错在它是**我的设计动机，不是用户的处境**。

做多图合并时，我脑子里的对立面是"6 张图会变 6 条记录、把首页刷满"。这是对的，那是真实的问题。但写提示时，我把这个**内部动机直接搬到了弹窗里**——等于在跟用户说："你看，你本来会把我的列表搞乱，我替你避免了。"

三个问题叠在一起：

1. **用户从没经历过"刷屏"。** 他选 6 张图，期望的就是这 6 张被存下。合并成一条对他来说是理所当然的结果，不是额外恩惠。
2. **它在暗示用户会犯错。** 「没有刷屏」的潜台词是"你没搞乱，是因为我拦住了"。没人喜欢被这样对待。
3. **它和上一句重复。** 「已存下 1 条」+「6 张图合成了一条」说的是同一件事：一个给结果、一个解释结果。用户读到的就是同一句话说了两遍。

一句话里同时有自我表扬、隐含指责、信息冗余，这大概是坏文案的完整形态。

### 29.2 改成什么

判据只有一条：**这句话在回答用户的哪个疑问？**

用户此刻真正的疑问是"我选了 6 张，怎么只多了一条？那些图去哪了？"——所以答案应该描述**东西存成了什么样、怎么用**，而不是**我为什么这么设计**：

```
6 张图都在这一条里，点开一张张看。
```

「都在」「这一条里」「点开一张张看」——三个信息，零评价。

同一条回执里的压缩那句也一起降级了：

| 原来 | 现在 | 为什么 |
| --- | --- | --- |
| 4 张照片压到 300KB 以内，省下 5.4 MB。 | 顺手把 4 张图压小了，省下 5.4 MB 空间。 | 「300KB 以内」是我设的阈值，用户不关心；「顺手」把它放回副作用的位置——用户要的是"图存下了"，省空间是赠品，不该被当成卖点 |

### 29.3 守卫

`copy.test.js` 62 条，新增一节盯这类毛病：

- i18n 全量文案里不许出现「刷屏 / 不打扰 / 丝滑 / 极致 / 智能 / 告别…」这批词（它们的共同点是描述"我替你解决了什么"）
- 合并回执必须说清"都在这一条里"，且**不许出现「没有 / 不会 / 避免」**——一旦出现，说明又在解释"你没造成什么后果"
- 首句只报条数与位置，不掺评价
- 压缩那句必须带「顺手」，且不许出现 300KB 这类技术阈值

词表守卫有局限（挡不住新造的词），但它能挡住最容易复发的那个方向：**把内部动机当卖点**。这类等着被问"为什么要这么写"的句子，光靠读代码是发现不了的。

### 一条判断留给以后

写任何面向用户的文案前，先问：**这句话如果被用户反问"为什么这么说"，我答得出来吗？**
答"因为这是我做的功能考虑"——那就是内部话，删掉。
答"因为用户此刻在找这个信息"——才留下。

## 三十、把上一章的结论推翻：先授权再读，才是对的（v1.8.5 开发期修）

你一句话把第 28 章推翻了：**"前几天开发过程中，从聊天存，是可以从剪贴板读取数据的，我确定。"**

这条记忆是证据，而且比我当时搜到的社区案例更有价值——同一台手机、同一个功能、时间上的前后对照。

### 30.1 git 给出的答案：这行代码从来没变过

```
git show v1.8.0:miniprogram/utils/transfer.js | grep ensurePrivacy
git show v1.8.1:... v1.8.2:... v1.8.3:... v1.8.4:...
```

v1.8.0 到 v1.8.4，`fromClipboard()` **一个字都没改**，最后一行始终是：

```js
require('./media').ensurePrivacy().then(read, read)
```

也就是说：你说的"那几天能读"，跑的正是这一行。是我在 v1.8.5 把它拆掉，才变成读不到。

### 30.2 我拆它的理由，是编的

第 28 章我写得很笃定："`getClipboardData` 要求必须在用户主动触发的那一下读，`await` 一次授权就脱离了点击栈，某些机型直接 fail。"

**这句话在任何官方文档里都找不到。** 回头查文档，`wx.getClipboardData` 页面上：

- 平台支持清单里明确写着「**微信 鸿蒙 OS 版：支持**」
- 通篇没有"必须由用户手势触发"这类限制
- 参数只有 success / fail / complete，没有任何与时机相关的说明

我把一个自己推测出来的机制，当成已知事实写进了文档，还据此改了代码。

### 30.3 `system permission denied` 到底是什么意思

> **这一节的结论已被第 31 章推翻，不要再引用。** 官方隐私错误码表里没有 `system permission denied` 这一句，所以"隐私协议没确认"同样是没有出处的推断。下面这段只保留为"我当时怎么想的"的记录。

这个 errMsg 极具误导性。它读起来像"操作系统永久禁止小程序读剪贴板"，实际更可能是：**隐私协议这一层还没被确认，接口就被挡回了。**

差别是决定性的：

| 如果是"系统永久禁止" | 如果是"授权没走完" |
| --- | --- |
| 重试没用、补授权没用 | 让用户点一次"同意"就好了 |
| 应该跳过、直接给输入框 | 应该补授权再读一次 |
| 我当时的判断 | 真实情况 |

而 `ensurePrivacy()`（内部是 `wx.requirePrivacyAuthorize`）做的正是"弹系统隐私框、拿用户同意"这件事。**被我拆掉的，恰好是唯一能让那句 errMsg 消失的一步。**

### 30.4 更糟的是：我基于错误结论建了一个会持久化的机制

v1.8.5 里我加了：

```js
if (code === 'sysperm') transfer.markClipboardBlocked()   // 写 storage
// 下次进来
if (transfer.clipboardBlocked()) { this.pasteManual(...); return }   // 30 天内直接跳过
```

这行 `return` 让功能连"再试一次"的机会都没有。你后面看到的"还是不行"，有一部分是它造成的——**我关掉了唯一能得到正确答案的通道，然后拿着"还是不行"当证据，进一步确认自己的结论。**

这是这一章最该记住的一条：**不要把猜测写成持久状态。** 猜测错了还能改代码，写进 storage 的猜测会一直替你做决定。

### 30.5 现在的实现

```js
// 先授权，再读。这一行是 v1.8.4 的真机行为，不要再"优化"掉。
require('./media').ensurePrivacy().then(read, read)
```

- 时序完全回滚到 v1.8.0 ~ v1.8.4
- 失败后仍会**补一次**授权再重读（万一第一次的框被系统吞掉），最多两次，不连环弹框
- `clipboardBlocked` / `markClipboardBlocked` / `CLIP_BLOCK_KEY` **整块删除**，页面上"跳过读取"的短路也删了
- 文案从"微信读不到剪贴板（鸿蒙版的已知问题）"改成"还差一步：允许读取剪贴板"——后者是能操作的，前者是替系统下结论
- 顺手把 26 章那条注释改了：原来写"遮罩把授权框挡掉了（断了根因）"，这同样是未证实的归因，现在只写"遮罩没必要，撞上授权框还添乱"

### 30.6 守卫

`collect.test.js` 95 条，这次把断言的方向整个掉过来：

- `ensurePrivacy().then(read, read)` **必须存在**（以前断言它"已移除"，方向正好相反）
- 模拟"第一次 fail system permission denied、第二次成功" → 必须算成功（以前是断言"不重试"）
- 两次都失败才算失败，且 `code === 'denied'`、`detail` 带原始 errMsg
- 代码里**不许出现** `clipboardBlocked` / `markClipboardBlocked` / `CLIP_BLOCK` / `sysperm`
- 页面上不许有"跳过读取、直接给输入框"的短路

最后两条是"防复发"：这套机制建立在错误结论上，宁可它编译不过，也不要它悄悄回来。

### 30.7 三条教训

1. **不要在已验证可用的代码上"优化"时序。** v1.8.0~v1.8.4 那一行在你的真机上跑通过，我却凭一句没出处的假设换掉了它。改之前该先问："这条结论有出处吗，还是我自己推的？"
2. **errMsg 的字面意思不能当结论——但也不能反过来被"解释"成另一个结论。** `system permission denied` 读起来像永久禁令；我把它改口说成"授权没走完"，同样没有出处：官方隐私错误码表里根本没有这一句（见第 31 章）。把一个看不懂的错误翻译成另一个我熟悉的错误，不是理解，是换了个姿势猜。
3. **用户的记忆是证据，不是需要被说服的误解。** 你说"我确定以前能读"时，正确动作是去查 git 历史；我实际做的是去搜"鸿蒙剪贴板限制"来给已有结论找支持。这是确认偏误的教科书形态——**先有结论，再找证据。**

## 三十一、诊断行被自己挡住了：为什么"还是不能读"查不出来（v1.8.5 开发期修）

你问："为什么还是不能读取剪贴板的内容？"

诚实回答：**我手上没有能定因的证据。** 不是没查，是证据被我自己的两行代码按住了。这一章记的是这两个缺陷，以及官方文档能确认到哪一步。

### 31.1 官方文档能确认的三件事

先摆出处，再谈别的。以下三句都能在原文里逐字查到：

1. **剪贴板确实是隐私接口。** 《小程序用户隐私保护指引内容介绍》"处理的信息 ↔ 接口"对照表最后一行：
   > 读取你的剪切板 ← `wx.setClipboardData`、`wx.getClipboardData`

2. **没声明就禁用。** 《小程序隐私协议开发指南》二.1：
   > 仅有在指引中声明所处理的用户信息，才可以调用平台提供的对应接口或组件。**若未声明，对应接口或组件将直接禁用。**

3. **官方列出的隐私报错只有四种**（指南第五节 + 第六节）：
   - `{ "errMsg": "A:fail api scope is not declared in the privacy agreement", "errno": 112 }` —— 后台没声明
   - `{ "errMsg": "A:fail appid privacy api banned" }` —— 提审勾了"未采集隐私"或未声明，被平台回收
   - 用户拒绝官方弹窗：**103**（与授权弹窗耦合样式）/ **104**（直接弹窗样式）
   - 另有一条行为约束：用户拒绝后 **10 秒内**再调，不再弹窗，直接报错

**`system permission denied` 不在这份表里。** 所以第 30.3 节说它"实际是隐私协议还没确认"，是我第二次凭想象给出的解释——第一次是"必须手势触发"，第二次是这个。同一件事，编了两遍。

### 31.2 第一个缺陷：`ensurePrivacy()` 把失败原因吞了

原来的写法（`utils/media.js`）：

```js
fail: err => {
  console.warn('[media] 隐私授权未通过:', err.errMsg)
  resolve(true)   // ← 失败也当成功，原因只留在控制台
}
```

后果是决定性的：如果用户拒绝了官方隐私弹窗，或者后台漏声明某一项，**我们收到的是 `ensurePrivacy` 的 fail，但它被 resolve(true) 抹平了**，接着 `getClipboardData` 再 fail，我们最终只看到那一句 `system permission denied`。三条可能的原因（112 / 103-104 / 系统层）里，前两条的证据在到达诊断行之前就被扔掉了。

现在拆成两个函数：

```js
ensurePrivacyInfo()  // → { ok, errMsg }，失败原因原样交出去
ensurePrivacy()      // → ensurePrivacyInfo().then(() => true)，老调用方行为不变
```

`chooseImages` 等原有调用方不读返回值，所以不受影响（`media.js:111-140`）。

### 31.3 第二个缺陷：`denied` 分支把诊断行覆盖了

`pages/index/index.js` 原样：

```js
let text = readFailNote(err)        // 先算好诊断行
...
} else if (code === 'denied') {
  title = i18n.t('index:clip_denied_title')
  text = i18n.t('index:clip_denied_text')   // ← 整句覆盖，诊断行没了
}
```

而 `denied` 恰恰是权限类失败的**唯一归口**：`transfer.js` 的 `onFail` 里，`/denied|deny|auth|privacy|scope|112/i` 一匹配就归 `denied`，`system permission denied` 必然命中。

于是形成闭环：**只要失败是权限类，诊断行就永远不显示；而不显示诊断行，就永远不知道该往哪个方向查。** 前面几轮我问你要 errMsg，其实我自己把 errMsg 关掉了。

现在改成拼接，不再覆盖：

```js
const note = readFailNote(err)
text = note ? i18n.t('index:clip_denied_text') + '\n' + note : i18n.t('index:clip_denied_text')
```

### 31.4 现在失败时能看到什么

诊断行格式（仅 `develop` / `trial` 可见，正式版不显示）：

```
［诊断］denied / need=1 | auth=requirePrivacyAuthorize:fail ... | read=getClipboardData:fail ...
```

- `need=1` —— `wx.getPrivacySetting` 说"这个用户还有待同意的隐私政策"。官方文档：该接口自基础库 2.32.3 起支持。
- `auth=` —— `requirePrivacyAuthorize` 那一步的原始 errMsg，不再被吞。
- `read=` —— `getClipboardData` 的原始 errMsg。

**`wx.getPrivacySetting` 在鸿蒙上是否可用，官方 API 页没有列出**，所以代码里用 `typeof` 判断，接口不在就少这一项，不猜它该返回什么（`transfer.js` 的 `privacySnapshot()`）。

### 31.5 仍然未知，以及需要人去核的一件事

- `system permission denied` 到底由微信抛出还是鸿蒙系统抛出：**无出处，未知。** 不再给解释。
- 有一个只能靠人看的配置项：**MP 后台 → 设置 → 服务内容声明 → 用户隐私保护指引 → 「开发者处理的信息」里是否勾了「读取你的剪切板」。** 按官方原话，没勾这一项对应接口"直接禁用"。这一条我无法从代码或文档替你确认。

### 31.6 守卫（collect.test.js 100 条）

新增/改写的断言：

- `ensurePrivacyInfo()` 必须存在，且 `ensurePrivacy` 里不许再出现 `fail → resolve(true)`
- 诊断行必须同时带 `need=` 与 `auth=`（运行时用例：注入 `getPrivacySetting` 返回 `needAuthorization: true` + 授权失败，断言 detail 里两者都在）
- `getPrivacySetting` 不存在时诊断行不炸，只是少一项
- `denied` 分支必须 `clip_denied_text + '\n' + note`，不许再整句覆盖

### 31.7 三条教训

1. **排查之前先确认"我看得见错误吗"。** 前几轮我一直在问"原因是什么"，从没问过"原因有没有被打印出来"。可观测性被自己切断时，所有推理都是在黑箱外面猜。
2. **认错不等于停止猜。** 第 30 章刚写完"不要凭想象下结论"，第 30.3 节就又给了一句"实际是隐私协议没确认"。写复盘时人最容易放松警惕，因为那一段读起来像"已经想通了"。
3. **文档能回答"机制是什么"，回答不了"你后台配了没有"。** 分清这两类问题：前者查文档，后者只能去后台点开看。

## 三十二、剪贴板读不到，最后落在系统的一个开关上（v1.8.5 开发期）

这一章只记已核实的事实，不写"应该就是这样"。

### 32.1 三个确定的观察

1. 鸿蒙手机上调 `wx.getClipboardData`，回 `fail:system permission denied`（真机诊断行）。
2. 同一台手机上，小程序隐私层是干净的：`wx.getPrivacySetting` 回 `needAuthorization: 0`，`wx.requirePrivacyAuthorize` 没有报错，点的时候也不弹隐私框。
3. 微信 → 我 → 设置 → 系统权限 → 前往系统设置，页面上的「剪贴板」一项显示为**禁止**（用户截图）。

三条放在一起，能说的只有一句：**隐私协议不是原因，系统给微信的剪贴板权限是关着的。**

### 32.2 之前两版文档错在哪

- 第 28.2 节说"鸿蒙系统级永久拒绝"——**方向对了，结论错了**：它据此加了 30 天持久化跳过，等于替用户认定"这台机器永远不行"。
- 第 30.3 节说"实际是隐私协议还没确认"——**方向也错了**，而且没有任何出处；官方列出的隐私报错只有四种，`system permission denied` 不在其中。

两次都是同一个毛病：把 errMsg 的字面意思，当成对成因的解释。

### 32.3 代码现在怎么处理这种失败

`transfer.js` 在 errMsg 命中 `system permission denied` 时多带一个 `sysDenied` 标记；首页据此走 `askSystemPermission()`：

- 弹框说清"系统的剪贴板权限是关着的"，不是小程序的隐私授权；
- 「去打开」调 `wx.openAppAuthorizeSetting`（官方：跳转系统微信授权管理页，基础库 2.20.1 起，鸿蒙支持，**只能在点击行为里调用**）；
- 从系统页返回触发 `onShow`，自动重读一次；
- 已经带用户去过一次、回来仍失败，就不再重复同一句，直接给输入框。

### 32.4 仍然不知道的

**"禁止"是出厂默认、还是某次点过"不允许"落下来的**——不知道，不写。系统设置页底部有「隐私数据访问记录」，那是唯一能还原"什么时候变的"的证据，需要人去看。

## 三十三、存下了，人却不在那条记录旁边（v1.8.5 开发期交互修）

用户发来一张截图，问的是"交互哪里粗糙"。图里有三个东西同时存在：顶部一条系统提示"读取了你的剪贴板内容"、列表里两条一模一样的「这次的话3500涨到12000吗」、底部一句「存下了，就在最上面」。

### 33.1 最要紧的一条：反馈说"在最上面"，人却在最下面

`saveCollected()` 存完只做了两件事：`refresh()` 和 `flash(rec.id)`。而入口固定在屏幕最底部，新记录插在列表最上方——**视口里什么都没有**，只有一句 toast 让人自己往上翻。

那句「就在最上面」不是提示，是设计在替自己道歉：它承认结果不在眼前，然后把找的活交给用户。

改法（`reveal()`）：先 `wx.pageScrollTo({scrollTop: 0, duration: 200})`，再点亮那一条。`flash` 从 1.3 秒延到 1.8 秒，卡片的高亮动画也从 1.2 秒对齐到 1.8 秒——原来滚动 200ms 之后只剩 1 秒亮，眼睛刚到就熄灯。

同一条路径上还有两处：

- 从记录页**新建**返回（`flashNew`）：也回顶。但从详情页/记录页**编辑**已有记录返回时不回顶——那条可能就在用户正看的位置，拽回顶部等于把他刚看的地方清了。
- 从聊天存文件（`collectFiles`）：同样回顶，顺手把「已存下 {n} 条，就在最上面。」改成「已存下 {n} 条。」

### 33.2 两条一模一样的记录：连点没有拦，重复也没说

从点下到落库不到 200ms，手抖点两下就是两条。现在两件事一起做：

- **800ms 冷却**（`SAVE_COOLDOWN_MS`）：冷却期内的第二次并进第一次。第一次的 toast 还在屏幕上，所以静默返回不会让人以为"点了没反应"。落库失败时把冷却清零，允许立刻重试。
- **一样就说一样**：落库前取列表最上面那一条（`prevText()`，用 `store.query({})` 而不是 `this.all`——后者受当前筛选影响），内容一字不差时 toast 是「存下了 · 和上一条一样」。仍然存，只是不让人在列表里看到两条一样的还以为是 bug。

### 33.3 点得中，但按下去没反应

| 位置 | 原来 | 现在 |
|---|---|---|
| 顶栏「从聊天存 / 多选 / 我的」 | 命中高约 52rpx（26px），纯文字、无按压态 | 72rpx，`hover-class` 降到 55% 透明度 |
| 筛选 chip | 高 56rpx，无按压态 | 64rpx，按下 72% 透明度（不改底色，避免和选中态打架） |
| 分组头「展开 / 删整组」 | 命中高约 58rpx，两者只隔 12rpx | 70rpx |
| 备份横幅的 × | 命中高约 42rpx | 约 66rpx |

顶栏那三个原本是 `<text>`——`text` 不支持 `hover-class`，所以一并改成 `<view>`（`display:flex` 保持原来的行内效果）。

### 33.4 长句 toast 读不完

原来固定 1600ms。对「存下了」够用，对「6 张图都在这一条里，点开一张张看。」这种 18 字以上的句子，读到一半就熄了。现在 18 字内仍是 1600ms，之后每字 45ms，封顶 3200ms。

### 33.5 顺手补的一个边界

`onUnload` 原来只清了 `highlightTimer` 和撤销定时器，漏了 `toastTimer`：页面销毁后定时器还在跑，会对一个不存在的页面 `setData`。补上。

### 33.6 没做的事（明确列出，不是遗漏）

- **筛选条右侧还有没有内容，仍然看不出来。** 要判断 `scroll-view` 是否溢出得测量宽高，静态样式做不到；加一条常显的渐隐又会在没溢出时说谎。留着。
- **系统那条"读取了你的剪贴板内容"横幅会盖住输入条。** 这是系统浮层，小程序没有接口控制它的位置和时长。
- **左滑删除的发现性仍然只靠列表底部那行字**（「到底了 · 左滑删一条，长按还能改」）。要做首次引导就得记录"是否已教过"，属于新状态，这一轮不动。
- **左滑打开时点卡片先收起**这条本来想改，读代码发现 `onCardOpen` 第一句已经这么做了（`if (this.data.openSwipeId)`），不改。

### 33.7 守卫（collect.test.js 新增 15 条）

- 存完必须调 `reveal(rec.id)`，不许退回只 `flash`
- `reveal` 里必须有 `pageScrollTo` + `scrollTop: 0`，且滚动在点亮之前
- 新建返回回顶、编辑返回不回顶
- 「就在最上面」不允许再出现在代码行与文案里（注释里保留引用，用于记录这段弯路）
- `SAVE_COOLDOWN_MS` 存在、冷却期内 return、失败清零
- `prevText()` 必须在 `store.create` 之前调用
- 内容相同必须走 `clip_dup_saved`
- 顶栏三个入口的 `min-height: 72rpx` 与三处 `hover-class="tap-dim"`
- toast 时长按字数放宽

合计 665 条断言，15 个测试文件全绿，预检 0 问题。

## 三十四、模板库：先把内容做出来，收录是副产品（v1.8.5 开发期）

这一章的起点是一个前提被推翻：用户后台的「页面收录」开关一直是开的，但 `sitemap.json` 里写的是

```json
{ "rules": [{ "action": "disallow", "page": "*" }] }
```

**全站一页都不许索引。** 开关开着、门自己锁着，写多少模板都不会被搜到。

### 34.1 sitemap 的写法（有官方出处）

微信开放社区《根据 sitemap 的规则[0]，当前页面将被索引》给出的四个例子，是这次唯一的依据：

- 例 3：`{"action":"allow","page":"path/to/page"}, {"action":"disallow","page":"*"}` → 只有这一页被索引，其余都不；
- 例 5：带 `params` 的规则 + `disallow *` + `allow *` → **规则按数组顺序、先命中先用**，同一页带参数与不带参数可以给不同结论；
- `page` 写的是页面路径（`path/to/page`），不带扩展名，与 `app.json` 的写法一致；
- 命中后不再往下看，所以 `disallow "*"` 必须放在最后收口。

据此写成（`miniprogram/sitemap.json`）：

```json
{ "rules": [
  { "action": "allow", "page": "pages/tpl/detail", "params": ["k"], "matching": "inclusive" },
  { "action": "allow", "page": "pages/tpl/list" },
  { "action": "allow", "page": "pages/guide/guide" },
  { "action": "disallow", "page": "*" }
] }
```

为什么 detail 要限 `params: ["k"]`：不带 `k` 的 detail 是一页"这个模板找不到了"，属于空页。让爬虫把抓取预算花在空页上不划算，也会让"页面数据与真实呈现不一致"的风险变高（官方明确这类页面不进索引）。

**首页、详情页、记录页一页都没放行。** 它们渲染的是用户自己写的灵感正文，而 sitemap 页的免责声明写明：因配置导致用户个人信息被展示披露，法律责任由开发者承担。

### 34.2 三个新页面，一条共同约束

| 页面 | 路径 | 作用 |
|---|---|---|
| 模板列表 | `pages/tpl/list` | 20 个模板按四类平铺，第一屏就是内容 |
| 模板详情 | `pages/tpl/detail?k=xxx` | 骨架 + 示例 + 「用这个模板记一条」 |
| 使用指南 | `pages/guide/guide` | 四种记法、数据在哪、六条 FAQ |

共同约束：**不读本机数据。** 不 require `store`，不碰 `getStorageSync`，不调任何隐私接口。理由是爬虫进来时 storage 是空的——页面若依赖记录数，就会渲染成空态，而官方写明"页面数据与真实呈现不一致的页面不进入索引"。

模板数据放在 `utils/templates.js`，纯常量：不 require 任何模块、不访问 `wx`。测试里有一条断言直接扫源码：`/\brequire\s*\(/` 不许出现。

另一条：列表页的详情入口必须是真实的 `<navigator>`，不能是 `bindtap` + `navigateTo`。**官方只说明爬虫会抓页面，没有承诺会穷举 detail 的参数组合**（这一点是推断），所以链接得长在渲染结果里，爬虫才跟得下去。

### 34.3 入口放在三处，顶栏不动

- 首页空态：主按钮下面并排两条文字链（「从聊天里存一条」「看看模板」）。没有并成一行会变成两行文字链，空态看起来像目录。
- 「我的」：新增一段「模板与指南」，两行，副标题带真实条数（`templates.count`，加模板自动跟着变）。
- 两个公开页互相链接：列表底部去指南，指南底部去列表。让爬虫从一个入口能走全。

**顶栏没有加第四个入口**——那里已经是「从聊天存 / 多选 / 我的」三个，再加一个会挤到胶囊。

### 34.4 从模板进编辑页：不静默扔掉草稿

`record.js` 新增 `fillTemplate(tpl, draft)`：

- 没有旧草稿 → 直接把骨架写进正文；
- 有旧草稿 → 先弹一次确认：「用这个模板会把输入框里那句换掉」。主按钮是「就用模板」（用户是主动点进来的），次按钮是「留着上次那句」；
- 选了模板就 `clearDraft()`。不清的话，下次开新记录会冒出上一句，和骨架混在一起。
- **不调 `markDirty()`**：骨架不是用户写的，填进去就弹「离开前确认」，会让人以为自己改了什么。骨架也不写草稿——返回就没了，下次再点还有。

这条规则的出处是第 30 章：替用户认定"他不需要那句话"，是最不该顺手做的事。

还有一处收尾。从模板写完一条、保存后，`record.js` 的 `leave()` 是 `navigateBack`，回到的是**模板详情页**——那里只有骨架和示例，看不到他刚写的东西。所以 `detail.js` 补了 `onShow`：发现 `globalData.flashId` 有值就 `reLaunch` 回首页（首页 `onShow` 会消费 flashId 并点亮那条新记录）。flashId 不在详情页清空——清早了，首页就不知道要亮哪一条。

### 34.5 顺手修掉一个预检误报

`tools/preflight.js` 判断"磁盘上有页面目录但没注册"时，原来写的是 `pages.indexOf('pages/' + d + '/' + d)`——假设目录名等于页面名。`pages/tpl/` 下是 `list` 与 `detail`，于是报了「pages/tpl 没有在 app.json 注册」。

改成前缀判断（该目录下任一页面已注册即通过）。这是误报，不是真的漏注册；但它会让人对预检的警告逐渐免疫，所以还是修了。

### 34.6 没做的事

- **后台「页面收录」开关的真实状态仍未确认**。截图只显示了「设置」按钮，没显示开/关。开关关着的话，sitemap 写得再对也不会收；
- **收录周期不知道**。官方没有承诺时间，「3–7 天」是社区经验，不是出处；
- **`scene 1129` 没有做任何特殊处理**。爬虫进来看到的和普通用户一样，这是对的；
- **模板内容只有中文**。英文界面下页面会显示一句"模板内容是中文的"，不给半截翻译；
- **没有做主动推送**。「页面内容接入 → 基础设置」页只有三张卡片（页面收录 / 频率上限 / 页面屏蔽能力），没有推送配置入口。

### 34.7 守卫（tools/tpl.test.js，104 条）

- 模板：20 条、id 唯一且能进 URL、五个字段非空、骨架与示例各至少三行、示例不超过 400 字
- `templates.js` 不含 `require` / `wx.` / `Storage`
- sitemap：`allow *` 不存在、`disallow *` 在最后、allow 的路径都在 `app.json` 里、首页与详情与记录页都没被放行、detail 必须带 `params: ["k"]`
- 三个公开页：不 require store、不读 storage、不调隐私接口
- 列表页有真实 `<navigator>` 且带 `k`；详情页用 `byId` 查表、缺参置 `missing`、分享路径指回自己、返回列表判断栈深

- `fillTemplate`：有草稿先 confirm、确认后 `clearDraft`、不调 `markDirty`
- 入口：首页 `goTemplates`、我的页两行、三页都注册进 `app.json`
- 文案：`tpl:*` 与 `guide:*` 的关键键齐全，`guide q1..q6 / a1..a6` 成对

另外 `tools/i18n.test.js` 的页面清单从写死七个改为**读 `app.json`**：新增页面必须自动被"`t.xxx` 有没有对应文案"这条检查覆盖，否则加了页面、漏了文案，会一路漏到真机上才变成一屏空白。

## 三十五、模板库第二版：按"创作从哪来"重排，每类先露三条（v1.8.5 开发期）

上一版模板库有个明显的问题：它是按"一个人一天里会遇到什么事"分的类——写点东西 / 工作用 / 生活记 / 想清楚。可这个产品的用户是**写作者、设计师、手作人**，他们要的不是"工作还是生活"，而是"**我这个念头现在在哪一步**"。

这一版把分类拆了重排，并把示例里的财务现场全部换掉。

### 35.1 五个类别，顺序就是创作流程

```
灵感与素材 → 作品与过程 → 写下来 → 日常与观察 → 工作用
```

- 前两类是人还没成形的时候：抓住一句闪念、一张素材卡；一件东西做了、做坏了、卡住了；
- 第三类是把它写成文字：故事、人物、场景、对话；
- 第四类是往外看：旅行、一道菜、一本书、一个梦；
- **「工作用」放最后**：周报、会议、复盘、求助、决策——这五条是给公司写的东西，不该和"我自己的东西"抢第一屏。

`CATS` 数组的顺序就是展示顺序（`templates.groups()` 直接按它 map），所以"调整到最后"只改了数组位置，页面一行没动。测试里有一条断言钉住这件事：最后一个分类名必须是「工作用」。

### 35.2 内容：示例里的现场换了人

原来的示例几乎全是财务现场——门店对账、19 个主体、汇率口径、月报合并。这些例子真实、有数字、写得好，但它们回答的是"一个财务总监怎么记事"，不是"一个做东西的人怎么记事"。

现在每类示例都换成了创作者现场，全部保留"具体数字 + 一个只有当事人才知道的细节"这个写法：

| 模板 | 示例里的那件事 |
|---|---|
| 一闪念 | 洗碗时看见倒扣的碗，裂纹像山脉 |
| 素材卡 | 旧木门上翘起的漆，想做成胸针的肌理 |
| 作品档案 | 《潮线》第三只，直径 11cm，釉薄的一侧是故意让它流的 |
| 卡在哪 | 海报改到第七版，问题不在细节，在最初那句模糊的话没写下来 |
| 做坏了的一次 | 薄胎碗收口手快了，塌了一道，干透裂开 |
| 三幕式故事 | 改 logo 改到第三稿，客户说"这不是我的店了" |
| 一个场景 | 裁缝铺下午三点，只有缝纫机的声音 |
| 五个开头 | 做坏的第五只杯子，把手又掉了 |

**「工作用」那五条一个字没改。** 它们本来就该是职场现场：门店对账、国补核销、月报合并、车贷决策。把这一段写成都市生活反而失真。

一份断言专门守这条线：`cat !== 'work'` 的模板，`example` 里不许出现「报表 / 对账 / 门店 / 主体 / 月报」。

### 35.3 折叠：每类先露三条

- `list.js` 里 `PREVIEW = 3`；每条分类在构建时拆成 `head`（前三条）与 `more`（其余）；
- 收起态露出三条和一个整行按钮「展开剩下 2 个 ⌄」，展开后按钮变「收起 ⌃」；
- 按钮高度 `min-height: 84rpx`，整行可点，不是一个小箭头；
- 默认全部收起：首屏从 25 条降到 15 条，五个类别的轮廓一屏能看见。

**这里有一个刻意的技术选择：用 `hidden` 而不是 `wx:if`。**

`wx:if` 为假时节点根本不会进入渲染结果，收起的 2 条模板连 `<navigator>` 都不存在——爬虫顺着列表页走，就永远走不到那 2 个详情页。`hidden` 只是加上 `display:none`，节点和链接都还在。

必须说清楚边界：**`display:none` 里的链接爬虫到底认不认，官方没有任何说明。** 这是推断，不是依据。所以 `list.js` 顶部注释写了补救顺序——如果上线后收录长期是 0，第一个要试的改动就是把折叠整个去掉，而不是去改 sitemap。

### 35.4 信息展示：三处调整

1. **类别名与条数一行，描述另起一行。** 原来 `name + desc + count` 挤在一条 flex 里，`desc` 是单行省略——「做出来的东西，和它是怎么来的」这种句子会被截成三四个字，等于没有描述。
2. **场景描述从一行放到两行。** 一行装不下「买了一堆材料或工具，事后想不明白值不值」，而这半句正是人判断"这条是不是给我写的"的唯一依据。`-webkit-line-clamp: 2`，同时把 `<text>` 换成 `<view>`（`-webkit-box` 在 `text` 上不稳定）。
3. **setData 瘦身。** 原来把整个 `groups`（含每条的 `skeleton` 与 `example`）传进视图层，25 条约十几 KB 的正文，列表页一个字都用不到。现在只传 `id / title / scene`。

### 35.5 id 一个都没删

`id` 会进 URL（`/pages/tpl/detail?k=xxx`），发出去就有人分享。这一版新增 5 个 id（`spark` / `material` / `piece` / `process` / `failed`），另外 5 条是**改标题与内容、不动 id**：

| id | 原来 | 现在 |
|---|---|---|
| `why-three` | 连问三个为什么 | 卡在哪（改成创作卡壳的三层追问） |
| `pro-con` | 一件事的正反面 | 两个方案怎么选（加了"选错的代价"） |
| `analogy` | 打个比方 | 打个比方（示例换成向客户解释包装） |
| `spend` | 一笔开销 | 一笔开销（材料与工具值不值） |
| `five-years` | 五年后的一个周二 | 五年后的一个周二（示例换成五年后还在做东西） |

旧链接打开后看到的是新内容，不会 404。

### 35.6 守卫（tools/tpl.test.js 121 条）

新增的：

- 五个分类、「工作用」必须是最后一个、前三类是创作者视角（灵感 / 作品 / 写下来）
- 每类至少 4 条（少于 4 条则"默认三条"没有可折叠的东西）
- 前四类示例不许出现财务报表类词汇
- `PREVIEW = 3`、`more` 由 `slice(PREVIEW)` 拆出
- 折叠必须是 `hidden` 且**不许出现** `wx:if="{{!g.open}}"`
- 两组 `navigator` 都带 `k`（展开区里的链接也得能被跟到）
- 展开按钮整行可点、带 `data-idx`、`setData` 走 `groups[idx].open` 路径
- 按钮高度 ≥ 84rpx、场景两行 clamp

## 三十六、示例里的现场换了人、一句提示回到了该在的位置、模板入口不再随记录数消失（v1.8.5 开发期）

这一章回答三个问题，每个都先给判据，再给改法。

### 36.1 「工作用」的示例为什么必须换现场

上一轮我给前四类换成了创作者现场，唯独留了「工作用」五条原样不动，理由是"那五条本来就该是职场现场，写成都市生活反而失真"。这个理由只对了一半：

- **对的部分**：工作用确实该是职场，不能说成"做手作时想到的事"；
- **错的部分**：原样保留的是**一个财务总监的职场**，不是职场。门店对账、电子烟供应商资质、越南主体汇率口径、国补核销时点、19 个主体月报合并、车贷 120 万——这些例子写得具体、有数字、有判断，但它们回答的是"一个财务总监怎么记事"。做设计、开店、写代码的人读到时，第一反应是"这不是给我写的"。

判据不是"够不够专业"，而是**示例的作用是让读者把自己的事填进去**。一个读者无法把自己的场景套进去的例子，无论写得多好，都是无效示例。

但**不能因此把具体性抽掉**。把"门店对账表拉到 11 月，差异 3 笔已核"改成"完成了三项任务，其中一项延期"，就从"别人的周报"变成"没人想看的公文"，谁都不代入。所以换的是**现场**，保留的是**具体性**：数字、时间、一个只有当事人才知道的摩擦细节。

五条对照：

| 模板 | 原来 | 现在 |
|---|---|---|
| 周报 | 门店对账拉到 11 月、电子烟供应商资质、越南主体汇率口径 | 首页改版第三稿、三家报价差 18%、"新版那句话谁定还没人认" |
| 会议纪要 | 财务三人 + 采购两人、手机端国补核销时点 | 产品两人 + 开发两人、新版先上哪几页、什么时候冻版 |
| 复盘 | 19 个主体的月报合并 5 天压到 2 天、统一科目映射表 | 三张表做成脚本、每周 4 小时降到 20 分钟、第一周错 2 处 |
| 问题描述 | 本小程序的剪贴板读不到（开发者自己的 bug） | 排期表导图片点了没反应、换手机换网络都一样 |
| 决策记录 | 车贷 120 万，三年还是五年 | 这批图自己拍还是外面拍，外面报价 4000 |

「问题描述」那条额外换掉的理由是另一个问题：它原本讲的是**本产品自己的剪贴板故障**。模板给用户看的是一个可迁移的方法，不是开发者的 bug 现场。

守卫：`tpl.test.js` 新增一条，`/门店|电子烟|国补|汇率|对账|月报|车贷|税务|主体/` 对**全部 25 条**（含工作用）示例零命中。上一轮那条只挡前四类，挡不住工作用往回写。

### 36.2 记录页那行提示：位置、层级、能不能读懂

截图里被框住的是「正文里写 #标签，会在这个标签下自动归好」。三个层面的问题：

**① 视觉层级**：它和右下角的 `0 / 1000` 同级——同样 22rpx、同样是浅灰（`#b8ab99` / `#b3a795`），在 `#fbf8f3` 底上约 2.1:1。但两者重要性完全不同：一个是"还能写多少"，一个是"这个功能怎么用"。把功能说明做成和计数器一样的装饰灰，等于告诉用户它也不重要。而它恰是新用户唯一会写错规则的地方。

**② 位置与时机**：输入区 `min-height: 300rpx`，提示挂在整片空白的最底部左端，计数器在同一高度右端，中间隔着整屏。用户视线起点在顶部占位符，扫不到底部；等他写完往下看，标签该写在哪已经定了，这条提示不再有用。

**③ 操作路径**：原文案说"写 #标签"，但没给可照着抄的样例。而标签正则有实实在在的边界（`utils/store.js:78`）：

```js
const TAG_RE = /#([^\s#，。,.!？、;；:：()（）[\]【】"'“”]{1,12})/g
```

`\s` 在排除集里，所以实测：

| 输入 | 解析出的标签 |
|---|---|
| `#灵感` | `["灵感"]` |
| `# 灵感`（`#` 后一个空格） | `[]` —— **静默失败** |
| `#这是一个超过十二个字的很长的标签名` | `["这是一个超过十二个字的很"]`（截到 12 字） |
| `写 #作品 和 #手作` | `["作品","手作"]` |

也就是说，照着"写 #标签"这三个字去写，最自然的动作是 `# 灵感`——**什么都不发生，而且没有任何反馈**。这是比配色更严重的问题：界面许诺了一个动作，用户照做后世界没有变化。

改法：

1. **合并成一行**：新增 `.meta-row`（`flex` + `baseline`），左边说明、右边字数。一句话和一个数字本来就该同排，一行读完，省掉一整行空白；
2. **提亮到能读**：`#b8ab99` → `#8b8178`（约 3.2:1）。这句是功能说明，不是装饰；
3. **文案给样例不给概念**：`'正文里写 #标签，会在这个标签下自动归好'` → `'# 后直接跟标签名，如 #灵感，存下自动归类'`。样例本身就把"不留空格"演示出来了，不必再讲一遍规则；
4. **计数器加等宽数字**（`font-variant-numeric: tabular-nums`）：写到 99→100 时位数变化不再把整行顶动。

守卫（`layout.test.js` 从 19 条到 22 条）：`.meta-row` 必须同时装着 `tip` 与 `counter`；必须是 `flex`（否则退回上下两行）；`.tip` 不许再用 `#b8ab99`。

### 36.3 模板入口不该随记录数消失

上一版把「看看模板」放在首页空态里，与「从聊天里存一条」并列。这个决定隐含一个假设：**模板是"第一次不知道写什么"才需要的东西。**

假设是错的。第 2 条、第 20 条记录同样会卡在"这个念头该写成什么"，而且记录越多，越需要方法型入口。反过来，入口一直占着首屏也不对——首页第一屏该留给记录本身，底栏已经三个入口，再加一个会挤到胶囊。

所以分层：

| 状态 | 位置 | 形态 |
|---|---|---|
| 无记录（空态） | 主按钮下方，与「从聊天里存一条」并列 | 文字链（不变） |
| 有记录 | 列表**滚到底**处，`end-hint` 之后 | 一行 26rpx 灰字「不知道写什么？看看模板 →」 |
| 任意状态 | 我的 →「模板与指南」 | 两行入口，副标题带真实条数（不变） |

底栏不动。列表底部那一行跟着列表滚，滚到底才看到，既不抢首屏，也不会因为"有了第一条"就消失。

守卫：`tpl.test.js` 取 `class="tpl-exit"` 那段，要求条件里必须有 `!empty`——**这个断言的方向是"入口必须出现在有记录时"**，写反了就等于没加。

### 36.4 这一轮改动的边界

- 只换示例文本，**模板 id 一个没动**（`weekly` / `meeting` / `retro` / `problem` / `decision` 照旧），已分享的链接不会 404；
- 骨架（`skeleton`）一个字没改——骨架是结构，本来就不含行业信息，改的是往里填的示例；
- 记录页只动那一行，输入区、按钮、语音与照片分支都没碰；
- 首页只加一行，`feed`、空态、顶栏、底栏都没改。

### 36.5 没做的

- **没做"检测到 `# ` 就提示"的动态分支。** 技术上可行（`onInput` 里判 `/#\s/`，纯派生状态、不落 storage），但它是新交互，不在这一轮三个问题范围内；留着，等有了"用户真的写错"的证据再加。
- **没做"点提示把 `#` 插进正文"。** 那会改用户正在写的内容，属于功能性改动。
- **模板入口没做成顶栏第四个。** 理由见 36.3。
- 收录效果仍然无法在这一轮验证：需要等真实数据。

## 四十、页脚图标又偏下：这次不是偏移量，是图标 PNG 自己偏心（v1.8.5 开发期）

### 40.1 第 39 章改错了地方

第 39 章判断「图标偏下」是因为把图标中心画在了文字基线上，于是加了 `BRAND_LIFT = 9`。用户真机反馈还是没有对齐。用截图逐像素量了一遍：

| | 外接框 y | 中心 |
|---|---|---|
| 图标图形 | 1968 – 2015 | 1991.5 |
| 「灵感随时记」 | 1961 – 1998 | 1979.5 |

图标中心比文字中心低 12 个截图像素。换算回画布逻辑坐标（截图 1256px 宽对应成品 750 逻辑宽，比例约 1.29）大约是 **9px**。

### 40.2 真因：`getbbox()` 什么都没裁

`_poster/make_brand_asset.py` 原来这样裁切：

```python
bbox = out.getbbox()        # 期望裁掉四周留白
mark = out.crop(bbox)
```

但 `getbbox()` 返回 **(0, 0, 511, 512)** ——整幅。头像 JPG 的压缩噪点让边缘一圈也有 `d > 9` 的像素，alpha 全幅非零，于是「裁切」等于没做，图形以它在原图里的偏心位置直接进包。

量一下新包里的实际分布：

```
alpha 全幅 bbox   (0, 0, 127, 128)      ← 被噪点撑满
alpha>120 实心    (2, 35, 107, 127)     ← 图形真正的位置
图形中心 vs 画布中心   (0.5, 17.5)        ← 偏下 17.5/128 = 13.7%
```

偏下 13.7% × 40px = **5.5px**，叠在 `BRAND_LIFT` 没盖住的那几像素上，就是用户在真机上看到的「沉下去」。

### 40.3 修法：外接框用严阈值单独算

- 求 bbox 时只看 `d > 20` 的线条级像素，噪点（一般 `d < 10`）够不到，便签内部的白（`d = 15`）也不会漏出来撑大框
- 裁完再居中到正方形，四周留 6% 呼吸位
- 输出从 128 提到 **192**：页脚显示 40px，3 倍屏是 120 设备像素，128 只剩 6% 余量；192 能覆盖到 4.8 倍屏
- 脚本末尾自带自检，打印实心 bbox 的中心偏移，现在读数是 `(0.0, 0.0)`

顺带核了一下 `BRAND_LIFT` 本身对不对：用微软雅黑 26px 渲染「灵感随时记」，字形 top = 基线 −22、bottom = 基线 +3，中心在基线上方 **9.5px**。所以 9 这个值没错，错的是图标文件。

### 40.4 现在的上下关系

图标 40px 里图形占 89%（171/192）：

```
图标方框 top = baseline − 29
图形 top     = baseline − 24.6      文字 top     = baseline − 22
图形 bottom  = baseline +  6.6      文字 bottom  = baseline + 3
```

图形上下各比文字多出 2.6 / 3.6px，略大一圈但同心，是图标配文字的正常观感。

### 40.5 守卫与数字

- `poster.test.js` 仍 **99 条**，把资产尺寸断言从 128 改到 192，加载 mock 同步
- 16 个测试文件 **829 条全绿**
- 预检 0 问题，包体 **554.4 KB / 83 个文件**（比上一版 +11.6 KB，就是图标从 12KB 变 23.7KB）

## 四十一、正文里那行 `#灵感` 不再重复显示（v1.8.5 开发期）

### 41.1 现象：一屏里同一个标签出现两次

详情页顶部是 `#灵感`（正文第一行），正文下方又是 `#灵感`（灰底胶囊）。用户问这是不是合理。

### 41.2 为什么：两条互不知情的渲染通路

| 位置 | 数据 | 代码 |
|---|---|---|
| 正文第一行 | `record.content` 原文直接输出 | `detail.wxml:23` |
| 灰底胶囊 | `record.tags`，`parseTags(content)` 正则抽出 | `store.js:102-117` → `detail.wxml:70` |

`parseTags` 是只读的：它把命中的标签塞进 `tags` 数组，**正文一个字符都不动**（`store.js:78` 的 `TAG_RE`，`104-116` 只 `exec` 不 `replace`）。所以同一段文字被画了两遍。

那个 `#灵感` 是用户自己敲进第一行的，不是系统加的——新建时 `content: ''`（`record.js:26`），25 条模板骨架没有一条以 `#` 开头，全工程也没有把 `#` 拼进正文的代码（`poster.js:361` 的 `'#' + item.tag` 只画在图上）。

### 41.3 规则：只有「整行就是标签」才剥

新增 `utils/tagtext.js`，纯函数、不 require 任何东西：

```js
const TAG_LINE_RE = /^\s*(?:#[^\s#，。,.!！?？、;；:：()（）[\]【】"'“”]{1,12}\s*)+$/
```

- `#灵感` 独占一行 → 整行去掉
- `#灵感 #想法` 一行两个 → 一起去掉
- `今天想到 #灵感 这件事` 句中 → **原样保留**，否则句子会被切成两截
- `# 灵感`（带空格）→ 不当标签，与 `store.TAG_RE` 同一个口径
- 剥完压掉连续空行，首尾空行清掉

**数据一个字不改。** 编辑页、`onCopy`（复制）、`share.card`（`inbox` 参数要把文本带过去）都仍然用原文，只有"看"的地方才剥。

一个必须知道的边界：中文没有词边界，`#灵感就是说一句` 在 `TAG_RE` 眼里就是一个 7 字标签，会被抽成胶囊。所以这里也整行剥掉——两处口径必须一致，不能一个剥一个不剥。

### 41.4 改了四处

| 位置 | 改法 |
|---|---|
| 详情页文字 | `detail.js` 算出 `bodyText`，`detail.wxml` 三处正文都换成它；`bodyText` 为空时整块不渲染，不留空盒子 |
| 详情页语音/照片 | 说明文字同样用 `bodyText` 判空 |
| 首页卡片摘要 | `peekOf` 先剥再压缩空白；**整条只有标签时退回原文**，卡片不能空着 |
| 做成图正文 | `poster.bodyText` 同样先剥；只有标签时退回原文，正文区总得有点东西 |

`needText`（没文字时提示"补一句"）仍按原文判断：正文只有 `#灵感` 也算有内容，不该催用户补字。

### 42.2 上面那条为什么以前没有：剪贴板以前从来没读成功过

「"灵感随时记"读取了你的剪贴板内容」不是我们的代码写的——全工程搜不到这句字面量，它是微信在 `wx.getClipboardData` **成功返回**时自己弹的合规提示。

而这条路在用户手机上一直是失败的：从 `fromClipboard` 上线（commit `97ed09f`）到 v1.8.5 排查结束，接口始终返回 `getClipboardData:fail:system permission denied`，根因是系统把微信的「剪贴板」权限设成了「禁止」（README 第 31、32 章）。

**失败不弹提示，只有真读到才弹。** 所以这条提示不是新加的，是功能第一次真的跑通之后，微信的合规提示第一次露脸。截图里它出现，本身就是「剪贴板通了」的证据。

### 42.3 下面那条为什么以前没印象：它一直在，只是被弹框盖住了

`git log -S "clip_saved"` 显示 `index:clip_saved` 从 v1.8.0（commit `4b737eb`）就在，不是 v1.8.5 新增的。

以前点「写一句」的完整流程是：读取失败 → 弹「系统的剪贴板权限是关着的」→ 用户点「手动粘贴」→ 自绘输入框 → 点确定 → 弹框关闭、列表刷新。注意力全在弹框上，那句「存下了」跟着弹框一起闪过去，留不下印象。

另一种可能是用户当时走的是分享入口（`handleInbox`），那条路完全不碰剪贴板，两条提示都不会出现。这一点取决于当时的具体操作，未核实。

### 42.4 上面那条改不了，下面那条可以删

**系统那条：不可控。** 文案、位置、时长都在微信手里，小程序没有开关。这里有个硬取舍——只要保留「点一下自动读剪贴板」，这条提示就必然出现。唯一能让它彻底消失的办法是把功能退回手动粘贴，等于放弃卖点。

**我们那条：正常流程直接删掉。** 依据是卡片本来就有更强的反馈：

```css
/* components/card/card.wxss:12-23 */
.card.fresh { animation: fresh 1.8s ease-out; }
@keyframes fresh { 0% { background: #f6e5d5; } 100% { background: #ffffff; } }
```

整张卡片背景从暖橙渐变回白，持续 1.8 秒，配合 `reveal()` 自动滚到顶部——**整卡变色比一个三字黑条醒目，且不遮任何内容**。

改法只在 `saveCollected` 末尾：

```js
// 改前
const same = !!prev && prev.content === raw
this.toast(i18n.t(same ? 'index:clip_dup_saved' : 'index:clip_saved'))

// 改后
if (prev && prev.content === raw) {
  this.toast(i18n.t('index:clip_dup_saved'))
}
```

保留的三种提示：

| 场景 | 为什么必须留 |
|---|---|
| 和上一条一样 | 不说的话，用户看到两条相同的记录会以为是重复落库的 bug |
| 截断 | 内容被切了一半，必须告知 |
| 没读到 | 走 dialog，本来就不是 toast |

`index:clip_saved` 这个键保留没删（中英必须成对，删一侧取值会 undefined），加注释标明已不再使用。

同时改了连点保护的注释：原来写的是「第一次的 toast 还在屏幕上，所以静默返回不会让人以为没反应」——现在不弹 toast 了，这句就不成立了。改成「第一次落库后列表已回顶、卡片开始 1.8 秒闪动」。

### 42.6 没做的

- **没改 `.toast` 的全局样式。** 它被 5 个页面共用（index/detail/record/poster/review），为了首页一条提示去动全站的黑条底，风险大于收益。
- **没延迟 `reveal` 去等系统提示消失。** 系统提示约 2 秒，等它消失再高亮会让用户觉得点了没反应。让卡片和系统提示同时出现更好——一个说「读了」，一个用颜色说「存这儿了」。

### 42.7 附：剪贴板提示关不掉，自动读也不做（2026-11-26 定论）

用户问「剪贴板权限能不能改成允许自动读取」。查完官方文档后，这个问题要拆成三层，混在一起永远谈不清：

| 层 | 谁控制 | 可选项 | 决定什么 |
|---|---|---|---|
| 鸿蒙系统权限 | 手机系统设置 | 禁止 / 每次询问 / 始终允许 | **能不能读** |
| 微信合规提示 | 微信 App | 无档位 | **读了会告诉你** |
| 我们的代码 | 本项目 | 只在 `onSheetSelect` 的 `paste` 分支调 | **什么时候读** |

**已核实**：`wx.getClipboardData` 官方文档（基础库 1.1.0+，标注「微信 鸿蒙 OS 版：支持」）的参数只有 `success` / `fail` / `complete` 三个回调，**没有任何控制提示的字段**；提示文案全工程搜不到字面量。所以系统权限设成「始终允许」只解决第一层，第二层照弹，且没有任何 API 能关。

**已核实**：当前触发路径是 `onSheetSelect` 的 `mode === 'collect'` → `key === 'paste'`，即用户点「写一句」后主动在菜单里选「从剪贴板」。这是全流程里最克制的触发点。

**决定：不做进页面自动读。** 技术上 `onShow` 调一次就行，但用户未做任何操作就被读剪贴板，观感比「我点了才读」差得多，而且提示会在每次打开小程序时弹一遍——正好放大用户此前的「太 low」感受。（这一条是产品判断，不是平台规定；平台是否有明文禁止未核实。）

**也不去掉剪贴板入口。** 那是这个产品最省事的收集方式，去掉等于让用户每次多走「长按 → 粘贴 → 确定」三四步。

**已补上的一句预告（2026-11-26，B 方案）**：`index:collect_paste_desc` 从「在聊天里长按复制，回来点这里」改成「在聊天里长按复制，回来点这里（微信会提示一次读取）」。理由见 42.8：这张横幅只能「不读」才躲得开，改交互的代价是主路径从 1 步变 4 步，不值。所以不动交互，只把突袭变成预期。

原来的顾虑是「会不会把菜单文字撑长」——量过：desc 24rpx，22 个字约 528rpx，行内可用宽约 670rpx，仍是一行；真机最坏是折两行，行高由 `min-height: 100rpx` 兜住。

### 42.8 为什么最后没改交互：加按钮躲不开横幅，只有「不调接口」才行（2026-11-26）

用户拿着「从聊天存」的两行菜单截图问：像这样在行尾加个「粘贴」按钮，能不能避开微信那条「读取了你的剪贴板内容」。

**不能。** 按钮改的是「用户有没有主动动手」，改不了「微信弹不弹」——横幅绑在 `wx.getClipboardData` **成功返回**那一刻，与入口长什么样、有没有二次确认无关。`wx.getClipboardData` 也没有任何控制提示的参数（42.7 已核）。

当时给过三个方案：

| 方案 | 做法 | 代价 | 结果 |
|---|---|---|---|
| A | 这一行改成打开手贴框（长按输入框 → 粘贴 → 确定），不调接口 | 主路径 1 步变 4 步；还要处理 `wx.showModal` 的 `editable` 可能是单行（`multiline` 不在官方参数表里） | 唯一能彻底无提示 |
| B | 不动交互，desc 里预告「微信会提示一次读取」 | 无 | 横幅仍在，但从突袭变预期 |
| C | 主路径 B + 另给一个「自己贴」入口 | 两套心智两套文案 | 不推荐 |

**一开始推 A，属于把「消除提示」当成硬目标却没给它定价。** 修正后的判断是：

1. 这条横幅是微信对所有调用该接口的小程序**一视同仁**的合规提示，全工程搜不到那句字面量。它不说明「这个产品做得糙」，只说明「微信在管这件事」。用户此前抱怨的「两个黑条」里，我们自己的那条（「存下了，就在最上面」）已在第 42 章删掉，剩下这条不是我们的文案。
2. 「从聊天存」这个入口的全部价值是**快**。为了去掉一条合规提示，把最该快的那条路拖慢三倍，交换不划算。
3. A 真要做得扎实，就不是小改动：得自绘带 `<textarea>` 的弹层，并把「读失败降级」也合并过去，否则会出现两套行为。

**结论：维持现状 + B。** 只改一句 desc，不改交互。这条判断的判别标准记在这里，以后别再摇摆：

> 用户被这条横幅打扰一次，和被多按两下，哪个更贵？

若哪天结论反过来（比如审核或用户反馈明确指向这条横幅），A 的执行清单：自绘 `textarea` 弹层 → `collect_paste` 行改指向它 → `pasteManual` 的降级也切到同一个弹层 → 文案 `index:paste_manual_ph` 已有「长按输入框粘贴…」可直接复用。

## 四十三、整组归档：先做按日期那一层，多选那一层往后放（v1.8.5 开发期）

用户在多选态截图上问：要不要在底部「导出 / 删了」之间再加一个「归档」胶囊，让选中的几条一起归档。

### 43.1 三个方案，只有一个成立

| 方案 | 问题 |
|---|---|
| 不加 | 一次要归档 3 条得逐条进详情页或长按菜单，6 次操作；批量清理时用户会直接改用「删了」，因为删除有 5 秒撤销和回收站，反而更省事 |
| 加，但合并成一条 | **不成立**。归档是记录上的状态（`archivedAt`），不是容器，「三条合并归档」没有对应实现。真按合并做，搜索会同时命中聚合条和原件、导出重复、语音和照片的媒体归属不清。用户真要的是「去重合并」，那是另一件事，不该挂在归档上 |
| 加，每条独立归档 | 成立，语义与单条完全一致 |

但多选条上并排出现「归档」和「删了」，两个都是「把这批移走」，会让人开始比较；而且「归档」和「删了」的量级不一样（一个可逆、一个要确认），同一行里节奏不一致。

### 43.2 先做「按日期整组归档」的理由

分组头本来就有「展开 / 删整组」（`index.wxml` 的 `.gright`），旁边加一个「归档整组」是同一套位置、同一套手势，不占多选条宽度，也不新增第二个「要选几条」的心智。用户截图里那 3 条正好都在「今天」这一组——这类需求用整组一步到位。

多选归档仍然有价值，但它唯一不可替代的场景是**跨组**选一批。等整组这层跑一段、确认真有人跨组归档，再补多选那一层。

### 43.3 整组归档不弹确认框

整组删除要确认（`dialog.confirm`），整组归档**不要**：

- 归档本身可逆，最坏结果只是「这一组不在主列表」，翻开归档视图就能一条条取回；
- 失败也没损失，不像删除那样会丢文本；
- 误触由撤销条兜底：5 秒内点「撤回」整组回原位。

给一个最轻的动作配确认框，等于把轻动作做成重的。这条与「删了」形成对照：**不可逆的才拦，可逆的只给退路。**

### 43.4 归档视图里按钮反转

在归档视图点它是「取消归档」，跟卡片长按菜单 `inArchive ? menu_unarchive : menu_archive`（`index.js`）同一套语义。不反转的话，归档页里点「归档整组」等于点了个寂寞。

`filter === 'archive' ? t.group_unarchive : t.group_archive` 直接写在 WXML 里，不在 JS 里算——分组渲染是纯展示，多一个 data 字段就多一处要同步。

### 43.5 顺带修掉的一个静默错误：归档会刷新 `updatedAt`

单条 `setArchive` 原来走 `update(id, { archivedAt })`，而 `update` 一律把 `updatedAt` 刷成当前时间。卡片的「改过」角标和详情页的「改过时间」都靠 `updatedAt - createdAt > 60 秒` 判断（`card.js` / `detail.js`）——**归档一条一周前的记录，会让它凭空多出一个「改过」标记。**

归档是状态，不是编辑。现在 `setArchive` 和新的 `setArchiveMany` 都只写 `archivedAt`，不动 `updatedAt`。这条用测试钉住（`archive.test.js` 里把时钟往前拨一小时再归档，断言 `updatedAt` 没变）。

### 43.6 撤销条从「只记 id」改成「记动作 + 对象」

原来的撤销条只有 `pendingDeleteIds`，撤回时一律 `store.restoreMany`。加了归档就不够用了：同一批 id，删除要恢复软删，归档要 `setArchiveMany(ids, false)`，猜不出来。

改成 `pendingUndo = { kind, ids }`，`kind` 取 `delete / archive / unarchive`，`showUndo(ids, label, kind)` 第三个参数默认 `delete`，原有两处调用不用改。撤销后的 toast 一律用「回来了 / n 条回来了」——**不指方向**，删除撤回和归档撤回都成立。

### 43.7 守卫与数字

- `store.setArchiveMany(ids, on)`：一次 `readAll` + 一次 `writeAll`，已经处在目标状态的记录不计入返回值（撤销条不虚报条数），软删的记录跳过。
- 中英文各 4 个键：`group_archive` / `group_unarchive` / `undo_group_archived` / `undo_group_unarchived`。
- 新增 `tools/archive.test.js` 38 条；全套 **18 个测试文件 909 条全绿**；`preflight` 0 问题（574.0 KB / 84 文件）；`lang-audit` 0 处不一致。
- 宽度：分组头三个操作中文合计约 284rpx、英文约 464rpx，左侧日期标签仍放得下（可用宽约 738rpx）。

## 四十四、把「骨架」换成「提纲」，并给「记一条」页补一个出口（v1.8.5 开发期）

### 44.1 为什么换词

「骨架」是从 `skeleton` 直译过来的开发词。页面上原句是「25 个骨架，分五类」——用户看到这里要先猜一次词义：骨架是什么？能吃吗？

它指的其实是**几行待填的提示**，比如：

```
想到的那句：
当时在做什么：
它让我想到的另一个东西：
要不要接着想：
```

换成「提纲」的理由有三条：

1. 量词「个」可以直接沿用，「{n} 个能照着写的提纲」读得通；
2. 和页面里已有的「示例」（`example`，填完的样子）配成一对——**提纲是待填的，示例是填好的**；
3. 不会让人以为在教写作（「写法」会有这个歧义，且量词得从「个」改「种」）。

改的是**值**，不是键：`tpl:skeleton` 这个键名保留，页面里 `item.skeleton` 的字段名也保留——它们不进用户眼睛，改一次要牵动四处引用。

英文同步：`Skeleton` → `Outline`，`skeletons you can fill in` → `outlines you can fill in`。

### 44.2 顺带去掉导语里写死的条数

原文「**25 个**骨架，分五类……」里的 25 是硬编码。`tpl.test.js` 有一条「模板数量是 25 条」，但那条盯的是数据，不是这句文案——**加第 26 条模板时测试照样绿，导语却还是 25。**

现在导语改成「分五类，每类先看三个，不够再展开；点开一条，照着改成自己的话。」，条数只由同一页的 `countText`（「25 个模板」）提供，不再两处各说一遍。测试加了一条「导语里不许出现数字」。

### 44.3 「模板怎么又没有了」——它一直都在，只是不在你卡住的那一页

模板原本有三个入口：

| 入口 | 位置 | 什么时候看得到 |
|---|---|---|
| 首页列表底部 | `.tpl-exit`，跟着列表滚到底才出现 | 有记录时 |
| 首页空态 | 主按钮下面的第二条文字链 | 一条记录都没有时 |
| 我的 → 模板与指南 | 设置行 | 一直有 |

**「记一条」页从来没有过。** 这不是回退，是缺一个入口——而这一页恰恰是「不知道写什么」发生的地方：人已经打开输入框、光标在闪、脑子里空着，这时候让他退出去、滚到列表最底、再点进来，路径太长了。

所以补第四个入口：「不知道写什么？看看提纲 →」，24rpx，紧跟在输入框下方的说明行之后。

三个约束：

1. **只在 `mode === 'create' && !content` 时出现**。编辑态不给——那时候正文里已经有东西了，再引导换提纲只会把写好的内容盖掉；语音和照片也不给，模板都是文字的；正文一有字就自动收起，那会儿不需要看出路，也不再占地方。
2. **不拦 dirty**。`wx.navigateTo` 只是压栈，本页正文还在内存里，返回就回到原处。真要换提纲是在详情页点「用这个提纲记一条」，那一步会新开一页并处理旧草稿（`fillTemplate` 里已有确认框）。
3. **位置必须在内容流里，不能进底部固定区**——见 44.5。

### 44.5 真机反馈：放底部固定区会被输入法盖住（第 1 版的做法是错的）

第一版把这条链接加在 `.tools` 的第一行（`position: fixed` 的那条），还专门给 `.page` 加了 `.with-tpl` 把留白从 272rpx 抬到 324rpx。真机截图一看：**键盘弹起后，整条底部固定区都不见了**——输入框、说明行、字数都在，提纲链接一个字也看不到。

原因很直接：

- `.tools` 是 `position: fixed; bottom: 0`，贴的是**视口底边**；键盘弹起改变的是「可视区」，fixed 元素不会跟着上浮，于是被键盘整个盖住。
- 而这行字恰恰**只在键盘弹起时才被需要**——用户正是「光标在跳、脑子空着」的那一刻要它。被盖住等于这个入口不存在。
- 反过来，`textarea` 上方的内容（导航、输入框、说明行）在截图里全都看得见：因为 `adjust-position` 默认开启，页面只在光标可能被挡时才上推，而输入框本来就在屏幕上部。**内容流永远在键盘之上，固定层永远在键盘之下。**

所以把它搬进内容流：`.meta-row` 之后、同一个 `<block wx:if="{{type === 'text'}}">` 里。三处配套改动：

| 改动 | 原因 |
|---|---|
| 删掉 `.page.with-tpl` 的 324rpx 留白 | 固定区不再多一行，留白回 272rpx；多出来的是一条普通流内元素，`.page` 的 `padding-bottom` 本来就够 |
| `wx:if` 从 `type === 'text' && mode === 'create'` 收成 `mode === 'create' && !content` | 已经在 text 块内，`type` 判断是废话；补 `!content` 让它在正文有字后自动消失（空稿才需要「不知道写什么」） |

## 四十五、模板页收尾：导语补关键词、详情页加同类内链、两页补落款（v1.8.5 开发期）

### 45.1 导语从「讲规则」改成「讲有什么」

原来那句是「分五类，每类先看三个，不够再展开；点开一条，照着改成自己的话。」——它讲的是**怎么用**，没讲**这页有什么**。从搜索结果落地的人第一眼要回答的问题是「这里有没有我要写的东西」，所以换成了：

> **25 个写作与记录模板，覆盖灵感捕捉、故事写作、周报复盘、会议纪要、读书笔记。**

五个关键词正好对上五个分类（`spark / write / work` 三类的典型场景都点到了）。「每类先看三个」这句删掉不影响使用：展开按钮自己写着「展开剩下 2 个」。

### 45.2 「25」仍然是 `{n}`，不是写回常量

44.2 刚把写死的 25 拆掉，这一轮又要在句子里出现条数，处理办法是**占位符留在文案里，数字由页面填**：

```js
leadText: i18n.t('tpl:lead', { n: templates.count })
```

测试钉两条：文案里有 `{n}` 且不含任何数字；填进去的首字就是 `templates.count`。这样加第 26 条模板时，导语自己会变成 26。

### 45.3 导语既然带了条数，头部那行「25 个模板」就删了

原头部是「导语 + 一行 `countText`（25 个模板）· 模板内容是中文的」。现在导语自己说了 25，两行相隔 14rpx 各说一遍同一个数字，看着像两处没对上的数据（真机上就是这个观感）。

删掉 `countText` 后，`tpl:count` 这个键全工程没人用了，一并删掉——**留着一个不用的键，比留一句过期的文案更麻烦**：下次有人改文案时会以为它在生效。头部只保留英文界面那句「模板内容是中文的」（`showCnNote`）。

### 45.4 详情页底部：同类内链，用 redirect 不用 navigateTo

从分享卡片或搜索结果**直接落到详情页**的人，底部原先只有一个「看全部模板 →」，而那个列表他从没去过。给三条同类，等于「你可能还想写这个」，直接作用在「用这个模板记一条」的转化上。

数据不用新建：`templates.related(id, n)` 取同分类、排除自己、按 `LIST` 原顺序前三条。每类 5 条，减掉自己还剩 4，够取 3。**只取同分类、不跨类补齐**——跨类凑出来的「相关」点进去会发现没关系，比没有更差。

浏览器层面的两个约束：

- **`open-type="redirect"`**，不是 `navigateTo`。页面栈上限 10 层，一条条点下去迟早点不动，返回还要在历史里穿一遍；换页不加深栈，返回直接回列表。
- **仍然是 `<navigator>`**，不是 `bindtap` + `navigateTo`。渲染结果里它是个真链接，爬虫跟得到（与列表页同理）。

底部顺序定为：主按钮 → 说明 → 同类三条 → 「看全部 25 个 →」 → 落款。**先让人写，再让人看**；「看全部」原来那句「看全部模板」跟着下移，并把条数补上（`tpl:all`，同样是 `{n}`）。

`related` 只搬 `id` 和 `title`：这一栏是「去哪儿」，不是「读什么」，把正文搬进 `setData` 纯属浪费（25 条全量正文十几 KB，4.1 已经踩过一次）。

### 45.5 两页补一行落款

第一次从搜索进来的人，看到的是一页内容，不是一个产品。列表页与详情页底部各加一行 22rpx 灰字：

> 灵感随时记 · 不联网的灵感本

一行，不占位、不做成页脚大块。英文界面里品牌名仍写中文（与 `share:title`、`tpl:share_title` 同一条规矩），后半句翻译。

### 45.6 分享标题带品牌，条数同样不写死

`tpl:share_list` 从「25 个可以照着写的模板」改成「**{n} 个可以照着写的模板｜灵感随时记**」。卡片在群里是「一张陌生的图 + 一行字」，没有品牌就只是陌生链接。列表页与详情页（查不到时的回退分支）分享都传 `n`——**回退分支最容易漏**，漏了会把 `{n}` 原样打在卡片上。

### 45.7 导航栏标题：查过了，本来就是对的

上一轮我说「两页导航栏写死中文、英文界面还是中文」，这次逐行核对后**这个判断是错的**：`list.js` 的 `onLoad` 末尾有 `i18n.title('tpl:nav')`，`guide.js` 的 `render()` 末尾有 `i18n.title('guide:nav')`——两边早在建页时就接好了。截图里看到的「模板」「怎么用」是**中文界面下 `tpl:nav` 的值**，不是写死的字符串。

所以这一轮只改**值**：`模板` → `灵感模板库`，`怎么用` → `使用指南`。三个 `.json` 里的 `navigationBarTitleText` 同步成同样的字——它是 JS 跑起来之前的兜底，也是爬虫读到的标题，两者不一致时用户会看到标题闪一下。

### 45.8 守卫与数字

- 新增 `tpl:rel`、`tpl:all`、`tpl:brand`（中英成对）；`tpl:count` 删除；`tpl:lead`、`tpl:share_list`、`tpl:nav`、`guide:nav` 改值。
- `templates.js` 新增 `related(id, n)`——纯函数，不 require 任何东西，守着文件头那四条规矩。
- `tools/tpl.test.js` 138 → **185 条**：第 13 节新增 32 条（related 的同类/排除自己/顺序/边界、内链用 redirect、内链排在主按钮之后、行高、空态清空、品牌行、分享标题带品牌与 `{n}`、三处导航标题与静态 json 一致）。导语那组从「不许有数字」改成「必须有 `{n}` 且填进去等于真实条数」。

## 四十六、首屏空态补一行「只存在这台手机」（v1.8.5 开发期）

### 46.1 起因：不是功能问题，是第一次进来那 5 秒

公众号在推，但效果不明显。查下来的顺序是：先分清是**流量不匹配**还是**落地页漏人**——前者靠改文章选题，后者才靠改页面。这一章只处理后者里最便宜的一处。

原来首页空态只有两句：

> 想到什么，就说一句
> 不用起标题，也不用选分类

两句都是**操作说明**。一个从文章点进来、不认识这产品的陌生人，在首屏看完这两句，仍然不知道「我的东西存在哪、会不会被上传、要不要注册」。而这三件恰恰是这个产品唯一不能被微信自带备忘录替代的地方——它却只写在 `guide:s2`（使用指南第 2 小节），陌生人走不到那儿。

### 46.2 为什么是「不上传」而不是「不联网」

这句话最早想写「不联网」，是错的：语音转文字要联网（`guide:a3` 原话就是「转成文字需要联网」）。首屏写「不联网」，用户第一次用语音转写就会当场撞上矛盾，等于自己挖洞。定稿是：

> 只存在这台手机，不上传，也不用登录

`layout.test.js` 里钉了两条断言守着这件事：**身份行不许出现「不联网」**、**必须出现「不上传」**。以后谁想改回「不联网」，测试会拦住。

### 46.3 三行递减，不是两行

主句不动（36rpx），身份行插在中间（26rpx / `--ink-2`），原来的「不用起标题」降级到 24rpx。层级是 **情绪 → 身份 → 门槛**：

| 行 | 字号 | 字色 | 作用 |
|---|---|---|---|
| 想到什么，就说一句 | 36rpx | `--ink` | 情绪，让人想写 |
| 只存在这台手机，不上传，也不用登录 | 26rpx | `--ink-2` | 身份，回答「这是不是又一个要登录的东西」 |
| 不用起标题，也不用选分类 | 24rpx | `#a2957f` | 门槛，最不重要 |

门槛那行降了字号，但**没有降到 `#b3a795`（约 2.3:1）**——那是装饰灰。记录页 `.tip` 已经在第 4 章踩过一次同样的坑：功能说明不能靠浅灰来分主次。降到 `#a2957f` 就够了。

### 46.4 只在「第一次进来」那个空态出现

`emptyIdentity` 由 `filtering` 决定（`filter !== 'all' || filterTag` 时给空串）。归档空了、某个标签下空了，再说「只存在这台手机」是答非所问——那时用户早过了「这是什么」的阶段，他要的是「我那几条去哪了」。

### 46.5 量过的版式

用 Chrome 按 375px（750rpx 的一半）还原首屏，在 667 与 812 两种屏高各截一张：三行读完眼睛不用上下跳；667 的小屏上，「从聊天里存一条 → · 看看模板 →」与底部固定入口条之间仍有约 190px 余量，**多这一行不会把任何东西挤到入口条底下**。

### 46.6 守卫与数字

- 新增 `index:empty_identity`（中英成对），`index:empty_default` / `index:empty_sub` **文案不动**，只改后者的字号与字色。

## 四十七、英文界面的模板库：展示层补英文，正文仍是中文（v1.8.5 开发期）

### 47.1 截图里的两个问题，不是一件事

用户在英文界面扫码截了一张模板列表：导航栏显示 `Inspiration ...`，页面除导语、`Show 2 more` 之外全是中文。看起来是"英文版本坏了"，其实是两层：

1. **bug**：`tpl:nav` 的英文值 `Inspiration templates` 有 21 个字符，微信导航栏只放得下约 13 个。中文「灵感模板库」6 个字没问题——上一轮改名时只顾了中文长度。改成 `Templates`。
2. **设计取舍露馅**：`templates.js` 原来写死「内容只写中文，模板本身是内容，不进 i18n，英文界面如实说明模板是中文的」。规矩的意图是"不给半截翻译"，但**实际渲染出来正好是半截**：用户还没走到正文，第一屏就已经满眼了，那句提示语站在最上面像在替整页道歉。

清点：5 个分类名 + 5 条分类说明 + 25 个模板标题 + 25 句场景，共 **60 条只有中文**。

### 47.2 档位：展示层翻译，正文不翻

分界线画在"用户靠什么决定点不点"：

| 层 | 字段 | 英文界面 |
|---|---|---|
| 展示层 | 分类名、分类说明、模板标题、场景句 | **有英文** |
| 正文 | 怎么用（tip）、提纲（skeleton）、示例（example） | **只有中文** |

英文用户能一路读到"这条是给我写的"，点进去看见提纲是中文，而提示语已经提前说过了。所以 `tpl:cn_only` 从「模板内容是中文的。」改成「**提纲与示例**是中文的。」——精确到词，用户不会觉得被晃点。

### 47.3 字段放 templates.js，不放 i18n 字典

`templates.js` 文件头第 1 条是**零依赖**（爬虫与 Node 测试要能直接读，任何 storage/i18n 依赖都会让模板页在没数据的机器上变白）。所以英文不写进 i18n，而是加在数据上：`name_en` / `desc_en` / `title_en` / `scene_en`，再由 `pick(obj, base, lang)` 取：

```js
function pick(obj, base, lang) {
  const alt = obj[base + '_en']
  return lang === 'en' && alt ? alt : obj[base]
}
```

`lang` 只认 `'en'`，其余一律中文；缺 `*_en` 时退回中文——宁可显示中文，也不要让英文界面出现空白或字段名。**语言由页面判一次**（`const lang = i18n.isEn() ? 'en' : 'zh'`），`templates.js` 始终不知道"当前语言"是什么。

`groups()` 顺带把 `name_en` / `desc_en` 透出来，列表页不用二次查表。

### 47.4 详情页要覆盖，不能只读

`detail.wxml` 直接读 `item.title` 与 `sceneText`。所以 `show()` 里先取好语言，再把结果**覆盖回 item**：

```js
item: Object.assign({}, item, { title: title, scene: scene })
```

不覆盖的话，导航栏标题、页面大标题、分享标题三处会各自跑到不同语言去。导航标题（`wx.setNavigationBarTitle({ title: title })`）与分享标题（`tpl:share_title` 的 `{t}`）都跟着取好的 `title` 走，「同类还有」那三条也一样要 `pick`。

### 47.5 一次自己的失误：`git checkout --` 冲掉了未提交的 `related()`

补英文时先手改了一版，发现 `desc` 是对象最后一个字段、没有尾逗号，插入后语法错。为了重来，我用了 `git checkout -- miniprogram/utils/templates.js`——**这一步把第 43 章加的 `related()` 一起冲掉了**，因为那批改动还没提交。`tpl.test.js` 立刻报 `TPL.related is not a function`，才发现。

教训：**有未提交改动时不要用 `git checkout --` 清文件**，用 `git stash push <file>`，或者先提交。文件恢复后按测试契约把 `related()` 重新写回来（同分类、排除自己、按 LIST 原顺序、默认 3 条、返回原对象引用），185 条断言随即恢复全绿——测试在这里起到了"磁盘快照"的作用。

### 47.6 守卫与数字

- `templates.js` 新增 `name_en`/`desc_en`（5+5）、`title_en`/`scene_en`（25+25）与 `pick()`；文件头第 4 条规矩改写为「正文只写中文，展示层必须有英文」。
- `i18n.js`：`tpl:nav` 英文 `Inspiration templates` → `Templates`；`tpl:cn_only` 中英都改成「提纲与示例」。
- `tools/tpl.test.js` 185 → **209 条**：第 14 节新增 24 条（60 条英文齐全、不含汉字、不是中文复制品、正文没有英文副本、场景不超过 80 字符以装进两行、`pick` 四种取值、两页都走 `pick`、导航标题用取好的 title、提示语措辞、**英文导航标题 ≤14 字符**防再次截断）。
- 全套 **18 个测试文件 1007 条全绿**；`preflight` 0 问题；`lang-audit` 0 处不一致；`design-lint` 通过。
- 版式自查：用 `templates.js` 的真实英文数据生成 375px 模拟图（`_mock_tpl_en.js` → `m.html`），最长场景 69 字符（`spend`）、最长标题 24 字符（`five-years`），两行内读完，无截断、无孤字。

## 四十八、四轮自查：品牌行说错话、导航栏还会截断（v1.8.5 开发期）

### 48.1 自查比新功能更值钱的一次

第 26–29 四轮改完后统一过一遍，抓到两处**四轮内部的自我矛盾**，都属于"单看每一处都对，放在一起就打脸"。

### 48.2 品牌行写着「不联网」，而首屏刚定下不能说这句话

`tpl:brand` 原值「灵感随时记 · 不联网的灵感本」／「An offline notebook for sparks」，是第 26 轮落款时写的。第 27 轮刚在首屏身份行上专门论证过：**不能说不联网**——语音转写走微信同声传译插件（`utils/asr.js:5`），要联网；`guide:a3` 原话也是「转成文字需要联网」。

更糟的是它在**模板库页脚**——这个产品最常被分享出去的公开页，一句会被最多陌生人看到的错误承诺。改成：

> 灵感随时记 · 只存在这台手机
> Inspiration Notes · Stays on your phone

口径与首屏身份行一致，且仍然只说真话（记录确实只落本机）。

### 48.3 导航栏改用短标签，模板名交给大标题

第 29 轮给 25 条模板补英文后，`detail.js` 仍然把 `item.title` 直接塞进导航栏。量了一下：**25 条里有 10 条英文标题超过 14 字符**，最长 `A Tuesday five years out` 24 字符——微信导航栏只放得下约 13 个拉丁字母，会截成 `A Tuesday fiv…`。上一轮刚修的 `Inspiration templates` 是同一个坑，只是换了地方犯。

改法不是给标题瘦身（那会毁掉意思），而是换职责：

- 导航栏 = `tpl:nav_one`「模板」/「Template」，只回答"我在哪一层"，永不会截断；
- 页面 `.h-title` = 模板名，字号更大、就在下方 60px，本来就该由它承担。

顺带解决一个冗余：原来导航栏与大标题在同一屏上下 60px 内重复同一句话。

### 48.4 「我的」副标题里的术语串味

`record:tpl_link`「不知道写什么？看看提纲 →」**保留未改**：那是用户在记录页卡住时的出口，说"提纲"承诺的是"你会拿到可照着写的东西"，比"模板"更贴近那一刻的需求；且这个词是用户自己选的（第 27 章）。术语分层不是要求全工程只留一个词，而是**同一处不要同时出现两层的词**。

## 四十九、语音不做转文字、模板列表默认全展开、术语收到「模板」一个词（v1.8.5 开发期）

### 49.1 语音：不是"暂时没开"，是决定不做

代码里一直躺着一层语音识别适配（`utils/asr.js`），开关 `USE_PLUGIN = false`，注释写着"想启用就把开关打开并在 app.json 加插件"。这一版把这个决定**落实**了：不做。

理由不是技术难度，是**它会推翻产品唯一立得住的那句话**。同声传译插件是"边录边转"，音频必须送去识别——一旦启用，"不上传""不联网"就都成了假话。而语音记录本来就有替代路径：录完补一句文字（`record:ph_voice_note`），那句话进正文，搜索就能搜到。

所以删掉的是：

| 删掉 | 位置 |
|---|---|
| `utils/asr.js` 整个适配层（约 160 行） | 文件删除 |
| 插件识别器的实时回调分支 | `record.js` `initRecorder` |
| `onRealtimeStop`（识别与录音一起回来的那条路） | `record.js` |
| 边录边转的实时文字块 `.asr-live` | `record.wxml` / `record.wxss` |
| `asr:*` 五个键、`record:ph_asr`、`record:toast_asr_break`、`record:toast_text_only` | `i18n.js` |
| `lang-audit` 里的 `asr` 包名 | `tools/lang-audit.js` |

留下的是系统录音器那条路（`wx.getRecorderManager`），录音、播放、落盘、空间检查全不动。顺手补了一个空守卫：`stopRecord` 里 `if (this.rm)` —— 环境不支持录音时 `this.rm` 是 undefined，原来的 `this.rm.stop()` 会抛异常（这条以前被插件分支挡住，删掉分支后才露出来）。

指南里的问答也跟着改。原来是：

> **录音要不要联网？** 录音本身不联网，文件就在手机上。转成文字需要联网；没网时只保存声音，不影响记录。

这段话在卖一个不存在的功能。现在是：

> **录音能不能转成文字？** 不做语音转文字：声音就存在这台手机上，不联网，也不会被送去识别。想以后能搜到它，录完在下面补一句文字，那句话才是搜得到的。

第二句是重点。不转文字的直接后果是**录音搜不到**，如果不说，用户录了十条回头一条都搜不出来，还以为丢了。

### 49.2 模板列表：默认全展开，但每组保留收起

原来每类只露三条、其余折起来。改成默认全展开，25 条一次给全；每组底部的「收起」保留，读长页的人能手动折。

两个理由：一是爬虫（虽然 `hidden` 节点在渲染结果里，但"认不认"官方没说明，默认展开就没有这层不确定性）；二是这页会被分享给别人，一屏里能看见"五类、每类五条"的规模，比看见"每类三条 + 展开剩下 2 个"更像一份完整的东西。

`PREVIEW = 3` 仍然保留——它决定 head / more 怎么切，也就是收起时露出几条。

### 49.3 术语：一个词到底，页内那一段叫「模板正文」

用户拍板不再保留「提纲」，全库统一说「模板」。逐处改下来，只有详情页里那段正文不能直接叫「模板」——页面上方的大标题就是模板名，中间再出现一个小标题「模板」，会读成"模板里的模板"。所以它叫「模板正文」：

| 位置 | 原 | 现 |
|---|---|---|
| 记录页出口 | 不知道写什么？看看提纲 → | 不知道写什么？**看看模板** → |
| 详情页区块 | 提纲 | **模板正文** |
| 详情页说明 | 提纲与示例是中文的。 | **模板正文**与示例是中文的。 |
| 编辑页提示 | 把这个提纲带进编辑页 | 把这个**模板正文**带进编辑页 |
| 我的页副标题 | {n} 个能照着写的提纲 | {n} 个能照着写的**模板** |

英文同步：`Outline` → `Template text`，`See the outlines` → `See the templates`。

`tpl:skeleton` 这个键名没改——它是内部标识，改它会牵动页面，值换了就够了。
